# Eight files of five hundred megabytes

*Theme: On-call*

The page came in at 02:40 on a Wednesday: `web2: /var 100%`. Tomasz had been on call for five days and asleep for forty minutes.

`/var` on web2 was an 8 GB volume. In daytime it sat at about 3 GB, mostly the journal, the package cache and a fortnight of compressed Apache logs. He ran `du` on the log directory.

```
$ sudo du -sh /var/log/apache2/*
3.0G	/var/log/apache2/access.log
2.2G	/var/log/apache2/access.log.1
88K	/var/log/apache2/access.log.2.gz
...
```

`tail -3 access.log` showed three lines from the same address, all asking for `/api/v2/items?since=` with a different timestamp each time and all with the user agent `catalogue-sync/1.4`. Across one second of the file there were more than a thousand of them. The partner's sync job had apparently lost track of its cursor at some point that evening and was paging through the whole catalogue as fast as the server could answer.

The job had started around ten. Just after midnight logrotate had renamed `access.log` to `access.log.1`, which by then held two hours of it, and had reloaded Apache so it would open a fresh `access.log`. The Debian config says `delaycompress`, so yesterday's file is left uncompressed for one more day in case a process is still writing to it. That's why `access.log.1` was still 2.2 GB of plain text. The other 3 GB had been written since midnight.

His first move was `gzip access.log.1`. It stopped with `No space left on device`, because gzip has to write the `.gz` out in full before it can delete the original. He deleted the file instead. That one was safe to `rm`: after the midnight reload no Apache process still had it open, so the blocks were freed straight away and `df` showed 2.2 GB come back. Next he added a `Require not ip` for the partner's address to the API vhost, ran `apachectl configtest`, and reloaded. The log went back to growing at its normal rate. At 03:25 he wrote the handover and went back to bed.

> web2 /var full at 02:40. catalogue-sync (partner, their IP in the ticket) looping on /api/v2/items since ~22:00, ~1k req/s. Deleted access.log.1 (2.2G, yesterday's, not held open). Blocked their IP on the API vhost, reloaded. access.log is 3G and I left it alone. Partner emailed. Why does one client get to fill the disk?

Hélène took over the pager at nine and started with the question at the end of Tomasz's note.

---

The answer was that nothing on web2 limited the size of `access.log`. Apache opens the file when it starts and appends a line for every request. The only thing that ever shrinks it is `/etc/logrotate.d/apache2`, and logrotate runs once a day, from a systemd timer set to `OnCalendar=daily`. Between two runs the file grows as fast as the traffic makes it grow. On a normal day that was about 300 MB. On Tuesday night it was 1.1 GB an hour.

logrotate can rotate on size as well: its `maxsize` directive rotates a file early, but only on a run where logrotate finds the file that big, and every rotation ends with the postrotate script `invoke-rc.d apache2 reload`. Apache needs that reload: the manual's section on log rotation explains that the log cannot be moved away while the server runs, "because Apache httpd will continue writing to the old log file as long as it holds the file open", so Apache has to be restarted before it opens a new one.

Hélène wanted the size checked while the log was being written, by something that could switch to a new file without Apache's help. The same page of the manual describes piped logs. If `CustomLog` is given `|` and a command instead of a filename, Apache writes each log line into a pipe, and the command reads the pipe and writes the file. The manual gives the main use as "to allow log rotation without having to restart the server", and the program it names for the job is `rotatelogs`, from `apache2-utils`, already installed on web2.

`rotatelogs(8)` takes a file name and a size such as `500M`. The option that mattered was `-n`, added in 2.4.5: "Use a circular list of filenames without timestamps." With `-n 3`, it writes `logfile` until it reaches the size, then `logfile.1`, then `logfile.2`, then goes back and truncates `logfile`. The log can never take more than the number of files times the size. When traffic spikes, the oldest lines are overwritten.

She checked in `support/rotatelogs.c` when the size is tested. After each read from the pipe (at most 64 KB) and before writing it, `checkRotate()` looks at the size of the open file and moves to the next file once `current_size > config->sRotation`. A file can go over the limit by one read at most.

She tried it on staging with numbers small enough to watch the whole circle: three files of 1 MB.

```apache
CustomLog "|/usr/bin/rotatelogs -v -n 3 ${APACHE_LOG_DIR}/access_log 1M" combined
```

She named the file `access_log`, without the `.log` extension, because logrotate handles everything that matches `*.log` in that directory. If she had kept `access.log`, logrotate would still rename it every night and write its own `access.log.1` over the ring's `.1`.

After the reload, she used `ab`, from the same package, to send staging more traffic than the ring could hold:

```
$ ab -n 30000 -c 50 http://staging-web/robots.txt
This is ApacheBench, Version 2.3 <$Revision: 1903618 $>
...
Complete requests:      30000
Failed requests:        0
Requests per second:    2874.19 [#/sec] (mean)
```

Each request logged a line of about a hundred bytes, `GET /robots.txt HTTP/1.0` from `ApacheBench/2.3`, so roughly 3 MB in all. The `-v` flag makes `rotatelogs` report each switch on stderr, which it shares with Apache, so the messages appeared in `error.log`:

```
File rotation needed, reason: Maximum size reached
Opening file /var/log/apache2/access_log.1
File rotation needed, reason: Maximum size reached
Opening file /var/log/apache2/access_log.2
File rotation needed, reason: Maximum size reached
Opening file /var/log/apache2/access_log
```

`ls -l` showed three files of just over 1 MB each. The first requests of the run had been overwritten by the last ones, and the directory held about 3 MB of access log.

For production she used eight files of 500 MB:

```apache
CustomLog "|/usr/bin/rotatelogs -n 8 ${APACHE_LOG_DIR}/access_log 500M" combined
```

That capped the access log at 4 GB. Everything else on `/var` took about 3 GB, so the volume could reach about 7 GB of its 8. On a night like Tuesday, each file would fill in under half an hour, and the ring would hold the last three and a half hours of requests. That was long enough to find the partner's address. On a normal day of 300 MB, the whole day fitted in `access_log`.

logrotate still reloads Apache every night for `error.log` and the other `*.log` files, and each reload stops `rotatelogs` and starts a new one, which begins again at `access_log`. After a reload the suffixes no longer match the age of the files, so she wrote in the runbook to read them in `ls -lt` order. She also wrote not to `rm` the current file, since `rotatelogs` holds it open and the space would not come back until the next reload; to empty it, use `: > access_log`.

She put the same line in the API vhost on web1 and web2, linked the change in the incident ticket and assigned it to Tomasz for review. He approved it at 14:10, with one comment asking whether the error log should get the same treatment.
