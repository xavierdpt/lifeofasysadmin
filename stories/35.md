# Eight files of five hundred megabytes

*Theme: On-call*

The page came in at 02:40 on a Wednesday: `web2: /var 100%`. Tomasz had been on call for five days and asleep for forty minutes.

`/var` on web2 was an 8 GB volume. In daytime it sat at about 3 GB, mostly the journal, the package cache and a fortnight of compressed Apache logs. He ran `du` on the log directory.

```
$ sudo du -sh /var/log/apache2/*
3.0G	/var/log/apache2/access.log
2.2G	/var/log/apache2/access.log.1
88K	/var/log/apache2/access.log.2.gz
...
```

`tail -3 access.log` showed three lines from the same address, all asking for `/api/v2/items?since=` with a different timestamp each time and all with the user agent `catalogue-sync/1.4`. Across one second of the file there were more than a thousand of them. The partner's sync job had apparently lost track of its cursor at some point that evening and was paging through the whole catalogue as fast as the server could answer.

The job had started around ten. Just after midnight logrotate had renamed `access.log` to `access.log.1`, which by then held two hours of it, and had reloaded Apache so it would open a fresh `access.log`. The Debian config says `delaycompress`, so yesterday's file is left uncompressed for one more day in case a process is still writing to it. That's why `access.log.1` was still 2.2 GB of plain text. The other 3 GB had been written since midnight.

His first move was `gzip access.log.1`. It stopped with `No space left on device`, because gzip has to write the `.gz` out in full before it can delete the original. He deleted the file instead. That one was safe to `rm`: after the midnight reload no Apache process still had it open, so the blocks were freed straight away and `df` showed 2.2 GB come back. Next he added a `Require not ip` for the partner's address to the API vhost, ran `apachectl configtest`, and reloaded. The log went back to growing at its normal rate. At 03:25 he wrote the handover and went back to bed.

> web2 /var full at 02:40. catalogue-sync (partner, their IP in the ticket) looping on /api/v2/items since ~22:00, ~1k req/s. Deleted access.log.1 (2.2G, yesterday's, not held open). Blocked their IP on the API vhost, reloaded. access.log is 3G and I left it alone. Partner emailed. Why does one client get to fill the disk?

Hélène took over the pager at nine and read the last line twice.

---

`/etc/logrotate.d/apache2` matches `/var/log/apache2/*.log` with `daily`, and logrotate's systemd timer is `OnCalendar=daily`. logrotate looks at the files only when it runs. Between two runs Apache appends to `access.log` for as long as the disk allows. logrotate's `maxsize` directive rotates a file early once it passes a size, but only on a run where logrotate finds it that big, and every rotation ends with the postrotate script `invoke-rc.d apache2 reload`. The Apache manual's section on log rotation says it directly: the server can't have its log moved while it runs, "because Apache httpd will continue writing to the old log file as long as it holds the file open", so after the move it has to be restarted in order to open a new one. As long as httpd owns the file descriptor, rotating means signalling httpd.

The same page describes the other arrangement. Replace the filename in `CustomLog` with `|` and a command, and httpd writes log lines into a pipe; a separate process reads the pipe and deals with the file. The manual names the main reason for doing this: "to allow log rotation without having to restart the server." The program that ships for it is `rotatelogs`, from `apache2-utils`, and it was already installed on web2.

She read `rotatelogs(8)`. You can give it a rotation time in seconds or a size with a unit suffix (`B`, `K`, `M` or `G`). The option she needed was `-n`: "Use a circular list of filenames without timestamps." With `-n 3` it writes `logfile`, then `logfile.1`, then `logfile.2`, then goes back and truncates `logfile`. The man page says it arrived in 2.4.5, and the changelog entry reads "add -n number-of-files option to rotate through a number of fixed-name logfiles." A fixed number of files of a fixed size put a ceiling on the log directory: the count times the size.

She wanted to see where it checked the size, so she opened `support/rotatelogs.c`. In the main loop, after each read from the pipe (at most 64 KB) and before the data is written out, `checkRotate()` reads the size of the open file descriptor and requests a rotation once `current_size > config->sRotation`. So the check happens on every write, not once a day, and a file can overshoot the limit by at most one read.

She tried it on staging first, with numbers small enough to see a full cycle:

```apache
CustomLog "|/usr/bin/rotatelogs -v -n 3 ${APACHE_LOG_DIR}/access_log 1M" combined
```

She named the file `access_log`, without the `.log` extension, on purpose. The logrotate glob is `*.log`. If she had kept `access.log`, logrotate would carry on renaming it every night and put its own `access.log.1` in the same place as the ring's `.1`.

After the reload, she pointed `ab` from the same package at the staging host:

```
$ ab -n 30000 -c 50 http://staging-web/robots.txt
This is ApacheBench, Version 2.3 <$Revision: 1903618 $>
...
Complete requests:      30000
Failed requests:        0
Requests per second:    2874.19 [#/sec] (mean)
```

Each request logged a line of about a hundred bytes: `GET /robots.txt HTTP/1.0`, a 200, `ApacheBench/2.3` as the user agent. That's roughly 3 MB in all, enough to go round a ring of three 1 MB files once. `-v` writes its messages to stderr. A piped logger inherits httpd's stderr, and httpd points that at its main error log, so the messages turned up in `error.log`:

```
File rotation needed, reason: Maximum size reached
Opening file /var/log/apache2/access_log.1
File rotation needed, reason: Maximum size reached
Opening file /var/log/apache2/access_log.2
File rotation needed, reason: Maximum size reached
Opening file /var/log/apache2/access_log
```

`ls -l` showed three files, each just over a megabyte. The contents of the first had been overwritten by the most recent requests.

Next she ran `systemctl reload apache2` halfway through a second `ab` run to see what the nightly logrotate reload would do to the ring. The reload clears httpd's configuration pool, which sends the running `rotatelogs` a SIGTERM and starts a fresh one; `ps` showed a new PID. The new process starts with its file counter at -1, so it opens `access_log` again, in append mode, then moves on to `.1` once that file is full, whether or not `.1` is newer than `.2`. The man page warns about this "unintuitive behavior" in its description of `-n`. After a reload, the suffixes stop matching the age of the files, and the modification times still do. The ceiling was the same either way: three files, each no larger than the limit plus one read.

For production she chose the numbers against Tuesday. On a normal day web2 logged about 300 MB, so the ring would barely move between nightly reloads and the whole day would stay in `access_log`. At Tuesday's rate of about 1.1 GB an hour, each file would fill in under half an hour and the ring would hold roughly the last three and a half hours.

```apache
CustomLog "|/usr/bin/rotatelogs -n 8 ${APACHE_LOG_DIR}/access_log 500M" combined
```

Eight files of 500 MB came to 4 GB, on a volume where everything else took about 3 GB. She put the same line in the API vhost on web1 and web2, dropped `-v`, and added a paragraph to the on-call runbook. It said that `access_log*` on web1 and web2 is a fixed ring written by `rotatelogs`, that to read in order you sort by `ls -lt` and not by suffix, and that you should not `rm` the current file: `rotatelogs` holds it open, so deleting it frees no space until the next reload. To empty it, use `: > access_log`.

She linked the change in the incident ticket and assigned it to Tomasz for review. He approved it at 14:10, with one comment asking whether the error log should get the same treatment.
