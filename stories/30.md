# Forty-One Minutes on Port 2342

*Theme: Attack suspicion*

The flow records came in on Mondays, and Marit read them on Mondays. Most weeks it
was a half hour of skimming. The collector summarised the previous week's sessions
by port, and the ports were the ports she expected: 443 outbound in enormous
quantities, 53 in both directions, 22 to the bastion, 4444 UDP humming between
the three points of presence in Amsterdam, Ashburn and Singapore.

Below 4444 there was a line for TCP 2342. Two sessions, long-lived, one between
Amsterdam and Ashburn and one between Amsterdam and Singapore. Those she knew.

There was a third. Forty-one minutes, inbound to the Amsterdam host, from
203.0.113.86, which resolved to nothing and belonged to a hosting company in
Frankfurt that the company did not use.

She did not know what 2342 was.

The tunnels between the three sites were `anytun`, chosen in 2019 because the
three sites terminated one shared anycast address. Ezra had set it up and then
moved onto the platform team, and the configs had sat in
`/etc/anytun/pop-ams/config` and its two siblings ever since, one command-line
argument per line.

Marit read the Amsterdam one over Ezra's shoulder on a call.

```
-t tun
-n 10.9.0.1/30
-i anycast.example.net
-e server
-S 2342
-M unicast-iad.example.net:2342,unicast-sin.example.net:2342
```

She asked him about `-S` and `-M`. Getting to the answer took a few minutes.

`anytun` does not require you to tell it where the far end is. The `--remote-host`
and `--remote-port` options exist, but the man page says that if you leave them
out, the endpoint "is automatically determined after receiving the first data
packet" — the daemon learns the peer's address from the traffic and keeps it.
Along with the address it keeps a sequence window per sender, for replay
protection, and a routing table mapping prefixes to multiplex ids.

All of that state lives in the host that received the packet. With three hosts
sharing one anycast address, the host that receives the next packet may be a
different one, and it has no entry for that multiplex id: the lookup misses and
the packet is dropped before anything is decrypted. There is a fallback — a host
whose connection list is empty and which was given no `-r` adopts the sender of
the first packet it sees, and logs `autodetected remote host` — but it is guarded
on the list being empty, so it fires once per host and never again. So the
cluster hosts hold TCP sessions to each other and push the table around: `-S`
says which port to listen on, `-M` lists the other members' unicast addresses.
Without it each host knows only the connections it has handled itself, filters
replays against only the sequence numbers it has seen itself, and keeps whatever
peer address it learned until traffic of its own tells it otherwise.

Marit asked what a connecting host gets.

"The current table, straight away. Then updates as they happen."

The man page for `anytun(8)` is not coy about the sync port. Under `--sync-port`
it says the port "is used by anycast hosts to synchronize information about
tunnel endpoints. No payload data is transmitted via this port." Then:

> It is possible to obtain a list of active connections by telnetting into this
> port. This port is read-only and unprotected by default. It is advised to
> protect this port using firewall rules and, eventually, IPsec.

Read-only was the word Ezra remembered. A port you can only read from sounds like
a status page.

Marit tried it from her laptop, which was on the office wifi and had no business
reaching the Amsterdam host at all. It reached it.

```
$ nc pop-ams.example.net 2342 | anytun-showtables
Client 0: 198.51.100.7:4444
Route: 10.9.0.0/30 -> 0
```

`anytun-showtables` takes no options and reads the sync stream on standard input;
its own man page's example is `nc unicast1.anycast.anytun.org 23 |
./anytun-showtables`. It printed the peer address and the route and sat there
waiting for the next update.

That was the status page. It was also not all that had come down the socket.
`showtables` prints what it chooses to print; the reason Marit looked past it was
the sentence in `anytun-controld(8)`, one man page over, about the same stream:
"Please make sure to protect that information as it contains the connection keys."

She ran it again without the tool in the way.

```
$ nc pop-ams.example.net 2342 | head -c 400 | cat -v
00243 22 serialization::archive 19 0 0 0 0 0 0 10 connection 0 0 1
128 14 87 200 12 ... 16 244 30 199 61 ...
```

A five-digit length, a space, and a Boost text archive: the word `connection`,
then numbers separated by spaces, one per byte. In `keyDerivation.h` the
serialisation function is four lines long, and two of them are
`ar& master_salt_;` and `ar& master_key_;`. Fourteen numbers for the salt, then
`16` for the length of what came next, then sixteen more.

She checked those sixteen. The configs use `-E` rather than `-K`, and `anytun`
derives the key from the passphrase by taking "the last n bits of the SHA256
digest", n being the key length, 128 by default — the last sixteen bytes:

```
$ printf %s 'the passphrase from the config' | sha256sum | cut -c33-64
f41ec73d9b02aa5e6c118d4470e3b2da
```

`244 30 199 61` is `f4 1e c7 3d`.

The question was no longer what the port gave away. It was whether 203.0.113.86
had taken it.

Syslog on the Amsterdam host went back ninety days and contained, at boot:

```
anytun[1911]: sync server listening on 0.0.0.0:2342
```

`0.0.0.0`, because the config sets `-S` and not `-I`. `--sync-interface` is the
option that binds the sync server to the host's unicast address; the default is
to bind on everything, and 2019 had not set it. The firewall in front of the site
allowed 4444 and 22 and, from a rule written the same week as the config,
2342 from anywhere, on the grounds that Ashburn and Singapore needed it and their
addresses were not yet stable.

What syslog did not contain was any line about the connections themselves.
Marit's own `nc` from the laptop, four minutes earlier, was not in it either. In
`syncServer.cpp` the accept handler logs `new sync client connected from` at
`PRIO_INFO`, which is level 4; the default log target, when the command line
supplies none, is `syslog:3`. Three prints errors, warnings and notices. The
listening line is a notice and is there. Every connection ever accepted on that
port was one level below the cut.

So the record of what 203.0.113.86 did was the flow record, and the flow record
said forty-one minutes and 51 kilobytes inbound to the collector's best guess.
Fifty-one kilobytes is a lot of a table with one client and one route in it, and
it is also what you get from holding the socket open through a period when
nothing changed and the far end sent nothing at all. Both readings fit. Marit
wrote both of them into the ticket.

The Frankfurt hosting company's abuse address answered eight days later with a
form letter. By then the firewall rule had been narrowed to the two unicast
addresses, `-I` had been added to all three configs under the `-S` line, and
every host had a second log target:

```
-L syslog:4,anytun,daemon
```

The passphrase was rotated on the Thursday, during the window, all three sites at
once, because the role parameter means the sides derive different keys from it
and a half-rotated tunnel does not pass traffic. Ezra did Amsterdam. Marit
watched the new master key go past in `journalctl -f` on Ashburn, in decimal, one
byte at a time, and closed the ticket as *unresolved — mitigated*.
