# Fourteen newlines in a webhook body

*Theme: Debugging with whatever is available*

The payments provider's webhook receiver was rejecting about one delivery in
forty. Not a clean failure — a 400 with `signature mismatch`, then the provider
retrying, then the retry succeeding. Whatever it was, it cleared up on its own,
which is why it had been happening for eleven days before anyone opened a
ticket.

The receiver ran in a container built from a distroless base. No shell, which
meant no exec into the running pod. What I had was an ephemeral debug container
sharing the pod's network namespace, built from an image someone had put
together for exactly these moments and then trimmed until it was almost too
small to be useful. No python. No `jq`. No `nc`. No editor worth the name. It
had `curl`, because the person who trimmed it had drawn the line there.

I had one thing to work with: the raw body of a delivery that had failed,
copied out of the provider's dashboard, sitting in a file I had written with a
heredoc because `vi` wasn't in there either.

```
$ ls -l /tmp
-rw-r--r-- 1 root root 612 Sep 14 09:02 body.json
```

The job was simple to state. Send those 612 bytes to `localhost:8080/hooks/pay`
with the same headers the provider sent, and watch what the receiver does with
them.

## What that used to cost

There is a version of this story from before `--data` existed, and it is worth
knowing because it explains the shape of the option.

`curl` began as a thing that fetched. You gave it a URL and it gave you back
what was there. Sending a body — doing what a browser does when someone fills in
a form and presses submit — was the other half of HTTP and not something the
tool did. If you needed it, you opened a socket by hand. `telnet` to port 80, or
later `nc`, and then you typed the request yourself: the request line, the
`Host` header, `Content-Type: application/x-www-form-urlencoded` because that is
what a form submission is, and then `Content-Length`, which you had to get
exactly right, because the server reads that many bytes and then stops. Count
wrong and you either truncate your own payload or the connection hangs while the
server waits for bytes that are never coming. Then a blank line, then the body,
typed into a terminal that may or may not be doing something helpful to your
newlines.

`--data` is the collapse of all of that into one argument. The docs say it
plainly: it sends the data in a POST request *"in the same way that a browser
does when a user has filled in an HTML form and presses the submit button"*, and
it sets the content type to `application/x-www-form-urlencoded` for you. It has
been in curl since version 4.0 — old enough that the short form `-d` is one of
the handful of curl flags people type without thinking. The two bits of
bookkeeping that used to be yours, the method and the length, become
consequences of the flag being present at all.

That is also why repeating it does something sensible. `-d name=daniel -d
skill=lousy` does not send two bodies or overwrite the first; the pieces are
merged with `&` between them, producing `name=daniel&skill=lousy`, because that
is the shape a form submission has.

## The first attempt

```
$ curl -sv -X POST http://localhost:8080/hooks/pay \
    -H 'Content-Type: application/json' \
    -H 'X-Pay-Signature: t=1757840534,v1=8f2c...e91a' \
    -d @/tmp/body.json
```

The `@` is the part that mattered to me at the time. If the data starts with
`@`, the rest is a filename, and `@-` means stdin — which is how you get a body
into curl when the body is too big, too quoted, or too full of shell
metacharacters to survive being an argument. I had a file, so I used the file.

The receiver said `signature mismatch`. Same as production.

For about ten minutes I took that as good news. I had a reproduction, inside the
pod, on demand. I started looking at clock skew, because the signature header
carries a timestamp and the obvious story for an intermittent failure is a
tolerance window and a drifting clock.

That story was wrong, and what disproved it was rerunning the same command
with `-v` and actually reading the request curl printed:

```
> POST /hooks/pay HTTP/1.1
> Host: localhost:8080
> Content-Type: application/json
> X-Pay-Signature: t=1757840534,v1=8f2c...e91a
> Content-Length: 598
```

598. The file was 612 bytes. Nothing had truncated anything; curl had removed
fourteen characters, and the file had fourteen lines in it.

## What `--data` does to a file

This is in the manual, in the same paragraph that introduces the `@`, and I had
read past it for years:

> When --data is told to read from a file like that, carriage returns and
> newlines are stripped out.

It is not a side effect. In the curl source, `-d @file` goes through
`file2string()`, which reads the file with `fgets` and, for each chunk, finds
the first `\r` and the first `\n` and writes a NUL over them before appending
what is left to the buffer. The lines get concatenated.

For a form submission that is exactly right — a `key=value&key=value` string you
kept in a file across several lines for your own readability should not carry
your formatting onto the wire. For my JSON body it was almost harmless too: JSON
does not care where the line breaks are, and the receiver parsed the smaller
body perfectly happily.

The signature cared. The provider computes an HMAC over the bytes of the body as
sent. Fourteen missing bytes is a different message, so it is a different MAC,
and the receiver — correctly, doing its job — said so. My reproduction was real
but it was a reproduction of *my* mistake, which happened to produce the same
error string as the one I was chasing.

The fix is the option that exists for this:

```
$ curl -sv -X POST http://localhost:8080/hooks/pay \
    -H 'Content-Type: application/json' \
    -H 'X-Pay-Signature: t=1757840534,v1=8f2c...e91a' \
    --data-binary @/tmp/body.json
```

`--data-binary` posts the data *"exactly as specified with no extra processing
whatsoever"* — newlines and carriage returns preserved. It is otherwise
`--data`: same merging with `&` when repeated, same `@` handling, and, the part
that catches people, the same default `Content-Type:
application/x-www-form-urlencoded` unless you say otherwise. The `-H` line above
is not decoration.

`Content-Length: 612`. `200 OK`.

## The actual bug

With a replay I could trust, the intermittent failure took another hour and was
somebody else's code. The receiver read the request body to compute the MAC and
then read it again to parse it; behind a proxy that occasionally delivered the
body in two chunks, the second read saw a short buffer. Deliveries that arrived
as one chunk worked. Deliveries that arrived as two did not, and the provider's
retry — same payload, different timing — usually landed as one chunk and
succeeded. That is what "one in forty, clears up by itself" had been trying to
tell us.

Two things stayed with me from the debug container.

Curl has three of these for a reason, and the reason is the file. `--data-raw`
is `--data` without the `@` meaning anything, for when your payload genuinely
starts with an at sign. `--data-binary` is `--data` without the stripping, for
when the bytes are the point. Plain `--data` is the form-submission one, and its
newline handling is a convenience for the case it was built for. Choosing
between them is choosing whether the file is a message or a convenience.

And a smaller one, from when I fat-fingered the path:

```
$ curl -d @/tmp/bdy.json http://localhost:8080/hooks/pay
curl: (26) Failed to open /tmp/bdy.json
```

Exit code 26, `CURLE_READ_ERROR`, before a single packet leaves the host. In a
shell script that is the difference between a failed delivery and a silent empty
POST, and it is worth checking for — because if the file exists and is empty,
curl does not error at all. It sends the POST with a zero-length body, which is
a perfectly valid request and a much harder thing to notice.
