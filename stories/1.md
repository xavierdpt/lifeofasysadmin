# The Metadata That Did Not Survive the Move

The ticket said "move the artifact mirror to the new storage." Two hundred gigabytes of
vendor firmware blobs, driver packages and signed installers that we fetch on a schedule
so that build hosts never have to reach the internet. It is the least interesting service
I own. It has no database, no API, no state machine. It is a cron job, a list of URLs and
a directory.

The move itself took an afternoon. `rsync -a` from the old volume to the new one,
repoint the export, run the fetch job, watch it not break. I closed the ticket the same
day and felt good about it, which in retrospect is the part of the story that should have
warned me.

Five weeks later the quarterly evidence pull came round and Priya from compliance sent me
a spreadsheet with an empty column in it.

The column was called `origin`. For every file we ship to a build host we have to be able
to say where it came from — not "the vendor," but the exact URL it was retrieved from,
because two years ago an auditor asked us to demonstrate that a particular `.deb` had not
been substituted somewhere between the vendor and our mirror, and we could not. The fix
we shipped after that conversation is the reason this story exists.

The obvious fix would have been a manifest: a JSON file, or a table, mapping filename to
source URL. Ade, who had the mirror before me, refused to build one. His argument, which
he made in the design note and then made again every time someone suggested it, was that
a manifest is a second copy of the truth, and second copies of the truth drift. Somebody
moves a file, somebody renames a file, somebody re-downloads a file by hand at two in the
morning during an incident, and now the manifest says one thing and the directory says
another and you cannot tell which one is lying. He wanted the provenance to be *part of*
the file, so that it could not desync from it, and so that no cleanup script could ever
leave the two out of step.

So he used `--xattr`.

It is a flag curl has had since 7.21.3, and it does almost exactly one thing. When you
are saving to a file, curl writes some of what it knows about the transfer into extended
attributes on that file. The mapping is not long. In curl 8.5.0 you can read the whole
thing in `src/tool_xattr.c`: a table with `user.xdg.referrer.url` from `CURLINFO_REFERER`
and `user.mime_type` from `CURLINFO_CONTENT_TYPE`, and then, separately, the effective URL
written into `user.xdg.origin.url` after being passed through a function called
`stripcredentials()` — which exists for the reason its name suggests, and which quietly
saves you from writing `https://svc:hunter2@vendor.example` onto disk where anyone with
read access can `getfattr` it.

Our fetch line was, and still is, three flags long:

```sh
curl -sS --xattr --remote-time -o "$dest" "$url"
```

and the evidence pull on the other end was a loop around

```sh
getfattr -d --absolute-names "$f"
```

which on the old volume printed

```
user.mime_type="application/vnd.debian.binary-package"
user.xdg.origin.url="https://downloads.vendor.example/pool/main/f/fw-tools_3.2.1_amd64.deb"
```

Ade's scheme was genuinely good. It was also buying a property — metadata that cannot be
separated from its file — at a price nobody wrote down, which is that the metadata is
only as portable as the filesystem underneath it and the tool you use to copy it. I paid
that price for him, five weeks late, on a Tuesday.

The new storage was an NFS export. NFSv3 has no notion of a user extended attribute at
all; there is nowhere in the protocol to put one. So there were two distinct failures
stacked on top of each other, and for a while I could only see the shape of the pile.

The first was mine and it was `rsync -a`. Archive mode preserves the things people
usually mean by "everything" — times, ownership, permissions, symlinks, devices — and
does not preserve extended attributes. Those need `-X`. Every one of the two hundred
gigabytes I moved arrived stripped, and the attributes that had been written over two
years were gone in the sense that matters: they were still on the old volume, which I had
scheduled for deletion, and which had not been deleted yet only because the storage team
is slower than I am.

The second failure was the one that kept it quiet for five weeks. New files fetched onto
the new volume could not get attributes either, and curl *does* tell you about that. The
documentation says so plainly: if the filesystem does not support extended attributes, a
warning is issued. `tool_operate.c` calls `fwrite_xattr()` and, on a non-zero return,
emits

```
Warning: Error setting extended attributes on 'fw-tools_3.2.1_amd64.deb': Operation not supported
```

Nobody ever saw it. Warnings go through `warnf()`, and `warnf()` goes through `voutf()`,
and the first thing `voutf()` does is `if(!config->silent)`. Our fetch line starts with
`-sS`. I had always read that pair as "be quiet but still tell me when something goes
wrong," and for errors that is what it is — `-S` sets `showerror` — but `-s` sets
`silent`, and `silent` is what gates warnings. The two flags are not opposites. The
warning was suppressed by the same character that was suppressing the progress meter.

Exit code zero. File present. Correct bytes, correct mtime, because `--remote-time` uses
a different mechanism entirely and kept working perfectly the whole time. The only
symptom available to anyone was an empty column in a spreadsheet that gets looked at four
times a year.

What I did about it was less interesting than what it cost. The mirror lives on local
disk again, and the export is now a read-only view of it rather than the storage itself.
The rsync in the runbook says `-aX`, and the line under it says *why*, in words, because
`-X` is the kind of flag that gets dropped by the next person who retypes the command
from memory. And the fetch job now reads back what it just wrote:

```sh
curl -sS --xattr --remote-time -o "$dest" "$url"
getfattr -n user.xdg.origin.url --only-values "$dest" >/dev/null 2>&1 \
    || { echo "provenance missing for $dest" >&2; exit 1; }
```

which is not elegant, and which is also the only part of this that would have caught it
on day one.

The files I had already stripped were recoverable, mostly. The URL list the cron job
reads from is in git, so for anything whose name still matched its source we could
reconstruct the attribute and write it back. About four hundred files did not match,
because they had been fetched by hand over two years by people who are no longer here,
and for those the honest answer on the evidence pull was "unknown origin, re-fetched on
the 14th." Priya took it better than I expected. Ade's design had been right for two
years about exactly the risk he built it for — nobody ever had to wonder whether the
manifest was lying — and then I moved the directory, and the provenance stayed behind on
a volume that was three weeks from being wiped.
