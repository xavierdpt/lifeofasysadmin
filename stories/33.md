# Seven minutes on a Wednesday

*Theme: Failed rollback*

The agency hosted twenty-three client sites on one Ubuntu machine, one Apache, one
`sites-available/` file per client. Changes to a vhost went out through a pair of
scripts in `/usr/local/sbin`: `site-deploy` copied the current file into
`/var/backups/apache-sites/` under a timestamp before installing the new one, and
`site-rollback` copied the newest backup back into place and told Apache to reload.
Ines had written both in her first year. `site-deploy` ran several times a week.
`site-rollback` had been run on the day she wrote it and not since.

On Wednesday afternoon Tomasz shipped a change for Harbourline, a chandlery with a
web shop. Two things went into their vhost at once: the certificate the client had
bought for the new year, at `/etc/ssl/harbourline/harbourline-2026.pem`, and a
`RewriteRule` that sent the old `/shop/` paths to the new catalogue. The reload was
clean. At four he tidied up and deleted the 2025 certificate and key.

At 16:38 Harbourline's owner phoned. The rewrite was catching `/shop/checkout` as
well, and nobody could pay. Tomasz said he'd put it back the way it was and ran

```
# site-rollback harbourline
restored /var/backups/apache-sites/20260923-1412/harbourline.conf
```

and reached for the browser to check. The tab spun and came back with *Unable to
connect*. So did the next client's site, and the one after that. The monitoring
channel posted twenty-three alerts.

```
# systemctl status apache2
× apache2.service - The Apache HTTP Server
     Loaded: loaded (/usr/lib/systemd/system/apache2.service; enabled; preset: enabled)
     Active: failed (Result: exit-code) since Wed 2026-09-23 16:39:04 UTC; 41s ago
```

The unit file says `Restart=on-abort`, which restarts the service when it dies on a
signal it didn't catch. The Apache parent had exited with status 1, so systemd left
it down. The last lines of `/var/log/apache2/error.log` said why:

```
[Wed Sep 23 16:39:04.211873 2026] [mpm_event:notice] [pid 1184:tid 139871022368640] AH00493: SIGUSR1 received.  Doing graceful restart
AH00526: Syntax error on line 14 of /etc/apache2/sites-enabled/harbourline.conf:
SSLCertificateFile: file '/etc/ssl/harbourline/harbourline-2025.pem' does not exist or is empty
```

The file he had restored was the copy `site-deploy` had saved at 14:12, before the
change, and it still pointed at the certificate he had deleted at four. He opened
it, changed `2025` to `2026` on line 14 and on the key line below it, and ran the
check that the rollback had skipped:

```
# apache2ctl configtest
Syntax OK
# systemctl start apache2
```

Harbourline's checkout loaded at 16:46. Everything had been down for seven minutes.

---

The next morning Tomasz read `site-rollback`. It was nine lines long. The last
three were:

```sh
cp "$latest/$site.conf" "/etc/apache2/sites-available/$site.conf"
# apache2 -k graceful fails from here (DefaultRuntimeDir), signal it directly
kill -USR1 "$(cat /var/run/apache2/apache2.pid)"
```

He could reproduce Ines's comment. Running the binary from `apache2-bin` directly,
with none of the Debian environment set, gives

```
$ sudo /usr/sbin/apache2 -k graceful
[Thu Sep 24 09:12:40.118042 2026] [core:warn] [pid 30617] AH00111: Config variable ${APACHE_RUN_DIR} is not defined
apache2: Syntax error on line 80 of /etc/apache2/apache2.conf: DefaultRuntimeDir must be a valid directory, absolute or relative to ServerRoot
```

because `/etc/apache2/apache2.conf` is written in terms of `${APACHE_RUN_DIR}`,
`${APACHE_PID_FILE}` and the other `APACHE_*` variables, and those are exported by
`/etc/apache2/envvars`, which `apache2ctl` sources and the bare binary does not.
The Debian README says as much: call `apache2ctl` with the same arguments. Ines had
instead gone round the binary and sent the signal herself.

A graceful restart is what `SIGUSR1` means to the Apache parent. The stopping and
restarting page in the manual describes it: the parent tells its children to finish
the request they are serving and then exit, re-reads its configuration files,
reopens its logs, and starts children from the new configuration as the old ones
leave. A plain restart (`SIGHUP`) kills the children the way `SIGTERM` does, along
with whatever requests they are serving. The manual says the graceful code "was
written to both minimize the time in which the server is unable to serve new
requests … and to respect your tuning parameters". On this machine it ran every
night: Debian's logrotate job calls `invoke-rc.d apache2 reload` after rotating
the logs, and a reload is a graceful restart.

In `server/main.c`, after a restart signal the parent goes round its main loop
again and rebuilds its configuration from the files on disk, with the same calls
it made at startup, and every failure along that path ends in
`destroy_and_exit_process(process, 1)`. `SSLCertificateFile` checks that its file
exists while the directive is being processed, so a missing certificate is one of
those failures. By then the parent has already told the old children to finish up.
Once they have, there is no process left holding port 443.

`apache2 -k graceful` starts a second `apache2` process, and before it can signal
anything it needs the `PidFile`, which is in the configuration, so it reads and
processes the whole configuration first. Only after that does `ap_signal_server`
in `server/mpm_unix.c` read the pid and send `SIGUSR1`. With the restored
Harbourline file in place, that second process would have stopped on the same
`SSLCertificateFile` line and exited, and the running server would never have
received the signal. Debian's `apache2ctl` also runs `apache2 -t` before it:

```sh
restart|graceful)
    if $HTTPD ${APACHE_ARGUMENTS} -t 2> /dev/null ; then
        $HTTPD ${APACHE_ARGUMENTS} -k "$ARGV"
    else
        $HTTPD ${APACHE_ARGUMENTS} -t
    fi
```

and `apache2.service` runs `ExecReload=/usr/sbin/apachectl graceful`, so a
`systemctl reload` goes through the same test. `kill -USR1` skips both the second
process and the test, and hands the untested file straight to the parent that is
serving traffic.

He tried it on the staging VM, which ran the same `apache2-bin` build, with a copy
of the Wednesday file:

```
# apache2ctl graceful
AH00526: Syntax error on line 14 of /etc/apache2/sites-enabled/harbourline.conf:
SSLCertificateFile: file '/etc/ssl/harbourline/harbourline-2025.pem' does not exist or is empty
Action 'graceful' failed.
The Apache error log may have more information.
# curl -so /dev/null -w '%{http_code}\n' https://staging.harbourline.test/
200
# kill -USR1 "$(cat /var/run/apache2/apache2.pid)"
# curl -so /dev/null -w '%{http_code}\n' https://staging.harbourline.test/
000
```

The new `site-rollback` keeps the current file aside before copying the backup in,
asks `apache2ctl configtest` about the result, and puts the current file back if
the answer isn't `Syntax OK`. The reload is `systemctl reload apache2`. The manual
says a passing syntax check does not guarantee the restart will succeed.
`apache2 -t` exits before the post-config step, which is where mod_ssl loads the
certificate and checks it against the key. A key that doesn't match its
certificate passes `configtest` and still stops the parent on reload, with
`AH02565: Certificate and private key … do not match` in the error log.

Tomasz ran the new script on staging against the Wednesday backup. It printed the
`AH00526` line, `restored current harbourline.conf, nothing reloaded`, and exited 1,
and the staging site answered 200. Then he put a line in staging's crontab to run
`site-rollback` against the newest backup on the first of every month.
