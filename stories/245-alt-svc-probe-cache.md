# The Probes Were Green Because They Were Somewhere Else

I wrote the line that caused this. Nobody asked me to say so, and by the end of the
week the timeline had stopped caring who typed what, but I want the record to start
there, because the interesting part of this incident is not the mistake. It is that
the mistake was correct for two years and then quietly stopped being correct without
changing a single character.

## What the ticket said

The ticket said: *customers reporting 502s on `api.example.com` since roughly 09:20,
dashboards green, please advise.*

Dashboards green is the part that made me put my coffee down. We run a synthetic
probe fleet — eleven small VMs in five regions, each one a cron entry and a shell
loop around `curl`, hitting a handful of endpoints once a minute and shipping the
exit code and the total time to the metrics box. It is deliberately stupid. It has
no SDK, no agent, no plugin ecosystem. When people ask why we don't use the vendor's
checks, the answer is that I can read every line of ours in under a minute.

I read every line of ours in under a minute. The probe for the failing endpoint was:

```
curl -sS -o /dev/null -w '%{http_code} %{time_total}\n' \
     --alt-svc /var/lib/synthetic/alt-svc.txt \
     --max-time 5 \
     https://api.example.com/v1/health
```

It was returning `200 0.031`. It had been returning `200` all morning, from all
eleven VMs, while the edge in front of `api.example.com` was returning 502 to
anybody who was not us.

## Why the probes had an alt-svc cache

That `--alt-svc` flag is mine, from a Thursday in 2024, and it was not cargo cult.

The constraint was this: our edge advertises alternative services. When you fetch
from `api.example.com:443` over HTTP/2, the response carries a header like

```
Alt-Svc: h3=":443"; ma=86400, h2="edge-b.example.net:8443"; ma=2592000; persist=1
```

which is the edge saying *you may reach this same origin over these other routes*.
A real browser client learns that once and spends the rest of the day on
`edge-b`. Our probes did not, because alt-svc knowledge in curl lives in a cache
attached to the easy handle, and each probe was a fresh process that lived for
thirty milliseconds and then exited. Every probe went to the front door. No probe
ever exercised the route that most of our actual traffic took within a minute of
arriving.

So we were measuring a path that hardly anyone used, and not measuring the path
almost everyone used. That was the motivation, and it was a real one: we had already
had one incident where `edge-b` was sick for forty minutes and the probes did not
flinch.

`--alt-svc <file name>` was the fix, and what it buys is exactly the thing a
short-lived process cannot do for itself: persistence. Point it at a file and curl
loads the cache at the start and writes it back out at the end, so the second probe
inherits what the first one learned. It is a nine-field, space-separated text file,
documented rather than accidental, and you can read it:

```
# Your alt-svc cache. https://curl.se/docs/alt-svc.html
# This file was generated by libcurl! Edit at your own risk.
h2 api.example.com 443 h2 edge-b.example.net 8443 "20260721 07:44:12" 1 0
```

Source ALPN, source host, source port; destination ALPN, destination host,
destination port; expiry in GMT, in double quotes; the `persist` boolean; and a
priority integer that curl parses and does not currently use. The header comment is
not a suggestion — a line that does not produce all nine fields is dropped without a
word.

The second thing it buys is attribution. When curl uses an alternative, it adds a
request header naming where it actually went:

```
Alt-Used: edge-b.example.net:8443
```

so the edge's access logs can tell a probe that arrived the long way from one that
came in the front. We used that for a capacity question once and I was very pleased
with myself.

The tradeoff, written down nowhere, was this. Alt-svc changes where the packets go
and nothing else. Under the hood curl sets the same internal "connect to" fields that
`--connect-to` sets, and those are documented as affecting only the network
connection: not SNI, not certificate verification, not the `Host` header, not the
application protocol's idea of the origin. Which is the correct design — the whole
point is that `edge-b` is a valid way to reach the origin `api.example.com`, and it
presents that origin's certificate. But it means the detour is invisible from the
outside. The URL in my cron job says `api.example.com`. The TLS handshake validates
`api.example.com`. The exit code is 0, the status is 200, and nothing in the output
of a non-verbose curl mentions that the bytes went to a host in a different
datacenter on a non-standard port.

Two years of that being fine.

## The bill

At 09:14 the platform team started a planned migration of the `edge-b` fleet. The
new fleet came up, DNS moved, traffic drained, and the old `edge-b` nodes were left
running on the old addresses for the rollback window — a completely reasonable,
by-the-book drain. The origin config was updated at the same time: the `Alt-Svc`
header stopped advertising `edge-b.example.net:8443`.

At 09:20 the new fleet's config had a bad upstream timeout and started returning 502.

Our probes, at 09:20, were still on the old `edge-b` nodes. They stayed there.

Two properties of the cache conspired, and both of them are behaviours I had read
about and filed under "fine".

The first: an entry in the cache is a route from a source origin to a destination,
and curl consults it *before* connecting. Once the fleet had learned
`api.example.com:443 → edge-b.example.net:8443`, every subsequent probe went
straight to `edge-b`. The way an alt-svc entry gets retracted is that the origin
sends `Alt-Svc: clear`, which flushes the cached alternatives for that source
origin — but you only receive a header from a server you actually talk to, and we
had stopped talking to the one that had something to tell us. The retraction was
being broadcast on a frequency we had tuned away from.

The second: the entry had `persist=1` and `ma=2592000`. That `ma` is max-age in
seconds, and curl's default when the header omits it is 24 hours; thirty days is
what the edge team had configured, years ago, to cut re-discovery chatter. Curl does
expire entries — it checks on every lookup and drops the expired ones — but the
expiry on that line read `20260821`. We had a month of runway on a decision made in
July.

So: the probes were green because they were somewhere else. Not a false reading. A
true reading of a host nobody was using.

## The part I am least proud of

We found it at 10:05 because somebody grepped the old fleet's access logs for signs
of life before decommissioning it, expecting zero requests, and found exactly eleven
per minute, each carrying `Alt-Used: edge-b.example.net:8443`. Eleven. Five regions.
You do not need a dashboard for that arithmetic.

The immediate fix was obvious — delete the cache file — and I did something clumsier
first. I wanted the file frozen while we thought, so I `chmod 444`'d it and went back
to the incident channel to say so.

It was 0644 again four minutes later, with the same line in it.

The probes run out of root's crontab. Curl's save path opens the target for writing
first, stats it to decide what to do, then writes a randomly named temp file in the
same directory and renames it over the top. The mode of the new file is taken from
the mode of the old one — which is a thoughtful touch, it means your cache file keeps
whatever permissions you gave it — OR'd with owner read-write, because a file the
process cannot read back is useless. `0444 | 0600` is `0644`. Read-only had been
faithfully preserved and then, just as faithfully, made writable again. Against a
non-root probe my `chmod` would have held; against root it was theatre, and the mode
in the `ls` output was the tell.

There is a real read-only knob — a bit you can set on the alt-svc control mask from
libcurl, which makes the cache load but never write. The command-line tool does not
expose it. If you are on the command line, your choices are a file that gets
rewritten or no file at all.

## What we changed

The cron line now reads `--alt-svc ""`. A zero-length file name is documented and
deliberate: curl keeps the cache in memory and neither loads nor saves it. Each
probe re-learns the alternative from the origin's header and then dies with it. We
lose nothing that mattered, because a probe that lives for thirty milliseconds was
never going to benefit from yesterday's routing decision — I had built a mechanism
for remembering, when what I actually wanted was a mechanism for *asking*.

The path-coverage problem that started all this got its own probe, which targets
`edge-b` by name and by port, with the hostname in the URL, where a human can see it.
If that host goes away, the probe fails, loudly, in the way a probe naming a dead
host should.

And a note went into the edge runbook: if you retract an alternative service, the
retraction only reaches clients that come back to the origin. Anything holding a
long `ma` is, by construction, not listening.

## Footnotes for whoever reads this next

- `--alt-svc` is HTTPS-only. Curl will not apply a cached alternative to a plain
  `http://` URL.
- It also stands down entirely if a `--connect-to` rule already matched that
  request. If you are overriding the route by hand, alt-svc does not get a second
  opinion.
- The option can be given more than once: curl loads every file you name, and saves
  to the last one. Two probes sharing one cache file is not a merge — each process
  rewrites the whole file from its own memory at exit, and the last one out wins.
- The cache is written when the handle is cleaned up, not when the transfer
  finishes. A probe killed by a timeout harness writes nothing.
- Our alt-svc cache never contained an `h3` line that did anything, despite the edge
  advertising `h3` for two years. Curl filters candidate alternatives against the
  protocol versions it was actually built with, and `curl -V` on those VMs lists no
  HTTP3. The entries were parsed, stored, written to the file, and never matched.
  I had been reading that file for two years and had never noticed, which tells you
  something about how closely I was reading it.
