# web-07, in Lowercase

*Theme: Hardening and least privilege*

The finding in the audit report was one line long: *Service account `svc-join` is a
member of Domain Admins; its password is stored as a CI variable and delivered to
every new VM in cloud-init user-data.*

Ines Okafor had seen it coming for a year. The provisioning pipeline built a VM, and
the last step of the VM's first boot was this:

```sh
echo "$AD_JOIN_PASSWORD" | adcli join --domain=corp.example.com \
    --login-user=svc-join --stdin-password \
    --domain-ou="OU=Linux,OU=Servers,DC=corp,DC=example,DC=com"
```

It worked, and it had worked for four hundred machines. The trouble was where the
password sat while it worked. User-data is readable from inside the guest through the
metadata service, by any process that can open a socket to 169.254.169.254, for as
long as the VM lives. So every Linux server in the estate could be asked, politely
and without authentication, for the password of an account that could do anything
in the domain.

## The obvious fix, and why it was half a fix

Tomasz, who owned the AD side, suggested the usual remedy: take `svc-join` out of
Domain Admins and delegate it "Create Computer objects" and "Delete Computer objects"
on `OU=Linux` alone. Ines agreed that was better and said so in the ticket. But she
also wrote down what it left in place: the credential would still be on every VM,
still readable from the metadata service, and still reusable. Anyone who pulled it
off one web server could create computer accounts in that OU for as long as the
password lived, and it lived until someone remembered to rotate it.

The root problem wasn't how much power the account had. It was that the machine being
joined had to hold a reusable credential before anyone trusted it. Joining a domain
has two halves that `adcli join --login-user` squashes into one: someone with
authority decides that a computer named `web-07` may exist, and then `web-07` proves
it is that computer and gets its own secret. The first half needs privilege. The
second half needs a single secret for a single account, good for one use.

adcli has split those halves almost from the start. The `NEWS` file in the source
tree lists `--one-time-password` for the `preset` command in release 0.2 and the same
option for `join` in 0.6. The manual page describes the first half:

> `adcli preset-computer` pre-creates one or more computer accounts in the domain
> for machines to later use when joining the domain. By doing this machines can join
> using a one time password or automatically without a password.

## The first draft

Ines's first pipeline change moved the privileged step off the VM entirely. The
provisioning controller, a host that already held credentials for the hypervisor,
got a keytab for a new, narrowly delegated account, `svc-preset`, and ran:

```sh
kinit -k -t /etc/provisioner/svc-preset.keytab svc-preset@CORP.EXAMPLE.COM
adcli preset-computer -C --domain=corp.example.com \
    --domain-ou="OU=Linux,OU=Servers,DC=corp,DC=example,DC=com" \
    web-07.corp.example.com
```

```
computer-name: WEB-07
```

The VM's user-data no longer contained a password, and its first boot ran:

```sh
adcli join --domain=corp.example.com --login-type=computer --no-password
```

It joined. She was about to open the merge request when she read the manual's
wording again: "*automatically* without a password". A computer account in Active
Directory always has a password. If the new VM could log in as `WEB-07$` without
being told one, then the password was something the VM could work out, and anything
the VM could work out, anyone else could work out too.

The answer was in `library/adconn.c`:

```c
char *
_adcli_calc_reset_password (const char *computer_name)
{
	...
	password = strdup (computer_name);
	...
	_adcli_str_down (password);

	return password;
}
```

When no password is given, `preset-computer` sets the account's password to the
computer name in lowercase, and `join` tries that same value when it authenticates as
the computer account. `reset-computer` falls back to it as well. The password of
`WEB-07$` was `web-07`.

In `-v` output this is the line `Using default reset computer password`, easy to miss
in a screenful of LDAP chatter. It meant that between the preset and the VM's first
boot, which could be ten minutes or, for a batch staged on Friday, a whole weekend,
anyone on the network who knew the naming scheme could claim `WEB-07` first:

```sh
adcli join --domain=corp.example.com --login-type=computer \
    --host-fqdn=web-07.corp.example.com --no-password
```

run from their own laptop would authenticate as the preset account, rotate its
password to one only they knew, and walk away with a valid keytab for a server that
didn't exist yet. When the real `web-07` came up, its join would fail, and the
attacker would hold the host principal that other services were about to trust.

The default isn't a bug. It is there so an administrator can pre-stage machines that
join with no secret at all, which is reasonable on a closed build network. It was not
reasonable for this one.

## The second draft

The fix was the option the manual pairs with the command. The controller generates a
fresh secret per machine and gives it to the preset:

```sh
otp=$(openssl rand -base64 24)
adcli preset-computer -C --domain=corp.example.com \
    --domain-ou="OU=Linux,OU=Servers,DC=corp,DC=example,DC=com" \
    --one-time-password="$otp" \
    web-07.corp.example.com
```

and puts that value in the VM's user-data where the `svc-join` password used to be.

On the VM, Ines chose not to use `join --one-time-password=...`. That option takes the
password as an argument, so it would show up in `/proc/<pid>/cmdline` for the length
of the join. The manual says `--one-time-password` is "equivalent to using
`--login-type=computer` and providing a password as input", and the code agrees: with
the login type restricted to the computer account, adcli calls its password function
for the machine account, and `--stdin-password` makes that function read from
standard input and strip the trailing newline. So the first-boot script became:

```sh
fetch-otp-from-userdata | adcli join -v --domain=corp.example.com \
    --login-type=computer --stdin-password
```

She ran it on a test VM and kept the verbose output for the merge request:

```
 * Using domain name: corp.example.com
 * Calculated computer account name from fqdn: WEB-07
 * Calculated domain realm from name: CORP.EXAMPLE.COM
 * Discovering domain controllers: _ldap._tcp.corp.example.com
 ...
 * Authenticated as computer account: WEB-07
 * Using GSS-SPNEGO for SASL bind
 * Found computer account for WEB-07$ at: CN=WEB-07,OU=Linux,OU=Servers,DC=corp,DC=example,DC=com
 * Trying to change computer password with Kerberos
 * Changed computer password
 ...
 * Added the entries to the keytab: host/web-07.corp.example.com@CORP.EXAMPLE.COM: FILE:/etc/krb5.keytab
```

Two lines were the point of the change. `Authenticated as computer account` (without
the `default/reset` prefix adcli prints when it falls back to the computer name) meant
the VM had logged in as `WEB-07$` with the secret it was given, and no user account
had been involved. `Changed computer password` meant that secret no longer existed. As
soon as it had authenticated, adcli used a Kerberos password change to replace the
one-time value with a freshly generated 120-character password that exists only in
`/etc/krb5.keytab`.

Then she replayed the same user-data from a second VM, adding
`--host-fqdn=web-07.corp.example.com` so it would claim the same name, the way someone
who had read the metadata service would:

```
adcli: couldn't connect to corp.example.com domain: Couldn't authenticate as machine account: WEB-07: Preauthentication failed
```

A one-time password stolen after the join is worth nothing. Stolen before the join, it
is worth one computer account in one OU, and the theft shows up as soon as the real
machine's first boot fails. That is a long way from Domain Admins.

## What the review changed

Tomasz raised one objection on the merge request: rebuilds. The pipeline sometimes
reinstalled a host under the same name, and `preset-computer` refuses an existing
account. The tool is explicit about this: "The computer accounts must not already
exist." `reset-computer` would have put the account back on the lowercase-name
password, which was the hole they had just closed. So the rebuild path runs
`adcli delete-computer` from the controller before the preset. The trade-off went
into the runbook: the rebuilt host is a new directory object, so any group membership
granted to the old `WEB-07` has to be granted again.

`svc-join` was disabled the following Tuesday. The audit response quoted the replay
error in full, because it showed the control working rather than just claiming it did.
