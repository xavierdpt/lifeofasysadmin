# Step 4 of the reboot runbook

*Theme: Upgrade*

The kernel update on mx2 went in at 06:40 and the box was back before 06:43.
Priya watched postfix come up, watched amavis come up, watched amavisd-milter
come up, and went to get coffee. At 07:10 the deferred queue was at 300 and
climbing by about one message a second.

Nothing was down. `mailq` was full of the same thing over and over — senders
being told

    451 4.7.1 Service unavailable - try again later

— and `/var/log/mail.log` was repeating one warning underneath it:

    warning: connect to Milter service local:/amavis/amavis.sock: Permission denied

Postfix will say that when it cannot reach a milter it has been told to consult.
What it does about it is `milter_default_action`, which defaults to `tempfail`,
so every inbound message was getting a 451 and every sending MTA was politely
agreeing to come back later. The mail was not lost. It was just all still
outside.

The path in the warning is short because `smtpd` runs chrooted into
`/var/spool/postfix`, so `smtpd_milters = local:/amavis/amavis.sock` is the
chroot's view of a socket that the rest of the system calls
`/var/spool/postfix/amavis/amavis.sock`. Priya looked at it from outside:

    # ls -l /var/spool/postfix/amavis/amavis.sock
    srwxr-xr-x 1 amavis amavis 0 Mar 12 06:42 /var/spool/postfix/amavis/amavis.sock

Owned by `amavis`, and no write bit for anyone else. Connecting to a unix socket
needs write permission on it, and `smtpd` runs as `postfix`. That was the
`Permission denied`, in full.

She restarted amavisd-milter, mostly for something to do.

    # ls -l /var/spool/postfix/amavis/amavis.sock
    srwxrwx--- 1 postfix postfix 0 Mar 12 07:14 /var/spool/postfix/amavis/amavis.sock

`postfix:postfix`, mode 0660. She flushed the queue and 1,400 messages went out
in under a minute.

## Who was supposed to do the chown

Nothing inside amavisd-milter sets the socket's owner; `amavisd-milter -h` lists
`-s` for the milter socket and `-S` for the amavis socket, with no option for
permissions anywhere in between. libmilter binds the listening socket as
whatever user the process is running as — here `amavis`, because the init script
starts it `--chuid amavis` — under whatever umask that process is carrying.

Debian handles the gap in `/etc/default/amavisd-milter`, which mx2 had been
carrying since before Priya arrived:

    MILTERSOCKET=/var/spool/postfix/amavis/amavis.sock
    MILTERSOCKETOWNER="postfix:postfix"
    MILTERSOCKETMODE="0660"

Those are exactly the values the socket had after her restart, so the mechanism
worked — at 07:14. The question was what it had been doing at 06:42.
`README.Debian` describes the two settings in a sentence with the answer buried
in its last clause: they "allow you to change the username as well as the
permissions of the socket **after it has been created by the daemon**."

The init script does it the moment `start-stop-daemon` reports success:

    start-stop-daemon $START

    case "$?" in
            0)
               log_end_msg 0
               if [ "$MILTERSOCKETTYPE" = "pipe" ]; then
                 if [ "$MILTERSOCKETOWNER" ]; then
                   chown "$MILTERSOCKETOWNER" "$MILTERSOCKET"
                 fi
                 if [ "$MILTERSOCKETMODE" ]; then
                   chmod "$MILTERSOCKETMODE" "$MILTERSOCKET"
                 fi
               fi
               ;;

`start-stop-daemon` reports success as soon as the process it started has forked
and the parent has exited. Priya went back through the boot log for 06:42 with
that in mind, and there it was, between two lines she had scrolled past twice:

    chown: cannot access '/var/spool/postfix/amavis/amavis.sock': No such file or directory

The `chown` had run. There had been nothing there to chown.

mx2 was on amavisd-milter 1.6.1, and 1.6.1 binds its socket in the child.
`main()` registers the callbacks, forks, writes its pid file and calls
`smfi_main()`; the socket appears a little way inside that, when libmilter's
`mi_listener()` gets to its first statement:

    if (mi_opensocket(conn, backlog, dbg, false, smfi) == MI_FAILURE)
            return MI_FAILURE;

So the parent's exit — the event the init script treats as "started" — happened
strictly before the socket existed, and the `chown` in the very next line of
shell was racing a `bind(2)` in a process that had just been forked. The child
usually got there first. On a cold boot with the disk busy, sometimes it did
not, and then the socket kept the ownership libmilter gave it and postfix could
not open it.

Priya could not fix the ordering, so she wrote it down instead, as step 4 of a
five-step runbook:

    4. ls -l /var/spool/postfix/amavis/amavis.sock
       If it is not postfix:postfix 0660, restart amavisd-milter
       and check again. Mail is deferring until it is.

It caught the same morning again fourteen months later, and cost nine minutes
instead of thirty-four.

## Three reboots on the new build

The rebuild onto Ubuntu 24.04 was routine: same config files, same
`/etc/default/amavisd-milter`, amavisd-milter 1.7.2-1 out of the archive. Priya
rebooted it, went to step 4 with the restart already typed, and found
`postfix:postfix` 0660. She rebooted twice more to be sure and got it twice
more.

`CHANGES` had the reason under a 2019 date:

    20190121:
            The milter socket is created before amavisd-milter is daemonized.
            This allows to return an error in case of impossibility to create
            the milter socket and package maintainers can adjust milter socket
            permissions immediatelly after the main process exits.

            Thanks to: Matus Uhlar

In 1.7.0 the release note for it is five words — "Fork after initializing milter
socket" — and in `main.c` it is one call moved above another:

    #ifdef HAVE_SMFI_OPENSOCKET
        if (smfi_opensocket(false) != MI_SUCCESS) {
            logmsg(LOG_ERR, "could not open milter socket %s", mlfi_socket);
            exit(EX_SOFTWARE);
        }
    #endif

        /* Run in the background */
        if (daemonize) {

Bind, then fork. `mi_opensocket()` returns `MI_SUCCESS` immediately when the
listener is already valid, so `smfi_main()` still calling it later costs
nothing, and the guarantee the init script had been assuming for a decade is now
true: when the parent is gone, the socket is there.

The other half of the changelog entry showed up when Priya deliberately pointed
it at a directory that did not exist. Because the failure now happens before the
fork, `exit(EX_SOFTWARE)` reaches `start-stop-daemon` as a status instead of a
cheerful zero, and because `daemonized` is still `0`, `log.c` puts the message
on the terminal as well as into syslog:

    # amavisd-milter -s /var/spool/postfix/amavis/amavis.sock -S /var/lib/amavis/amavisd.sock
    could not open milter socket /var/spool/postfix/amavis/amavis.sock
    # echo $?
    70

Under 1.6.1 that same failure had happened in the child, after the init script
had already printed a green `[ ok ]`.

She deleted step 4, renumbered the flush to 4, and put the date of the changelog
entry in the commit message.
