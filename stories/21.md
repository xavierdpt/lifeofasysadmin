# Step 4 of the reboot runbook

*Theme: Upgrade*

The runbook for mx2 had five steps and everyone only ever cared about step 4.

    ## After a reboot of mx2
    1. Confirm postfix is listening on 25 and 587.
    2. Confirm amavis is up (systemctl status amavis).
    3. Confirm amavisd-milter is up.
    4. ls -l /var/spool/postfix/amavis/amavis.sock
       If it is not postfix:postfix 0660, restart amavisd-milter
       and check again. Mail is deferring until it is.
    5. Flush the queue.

Priya had run it four times in two years and step 4 had bitten twice. Both times
the symptom was the same: everything up, everything green, and postfix filling
the log with

    warning: connect to Milter service local:/amavis/amavis.sock: Permission denied

and handing every inbound sender `451 4.7.1 Service unavailable - try again
later`, because `milter_default_action` defaults to `tempfail` and a milter you
cannot reach is exactly the case that parameter covers. Ten minutes of that and
the queue was four figures. Restart amavisd-milter, run `ls -l` again, watch the
socket come back as `postfix:postfix` with mode 0660, flush, done.

So when mx2 came back from the maintenance window on the new build — Ubuntu
24.04, amavisd-milter 1.7.2-1, everything else carried across from the old box
that had been running 1.6.1 — Priya went straight to step 4 with the
`systemctl restart` already in the scrollback, and the socket was correct.

She rebooted it again to be sure. Correct again. Third time, correct again.

The runbook said this happened sometimes. If it had stopped happening,
something had changed, and she wanted to know what before deleting a step that
had saved the queue twice.

## Where the ownership comes from

Nothing in amavisd-milter sets the socket's owner. There is no option for it —
`amavisd-milter -h` lists `-s` for the milter socket and `-S` for the amavis
socket and nothing about permissions. libmilter creates the listening socket
with `bind(2)` under whatever umask the process is carrying, as whatever user
the process is running as, which here is `amavis`. Postfix's `smtpd` runs
chrooted as `postfix`. Connecting to a unix socket needs write permission on it,
and `amavis`-owned with a 022 umask does not give `postfix` that.

Debian's answer is in `/etc/default/amavisd-milter`, which Priya had inherited
verbatim:

    MILTERSOCKET=/var/spool/postfix/amavis/amavis.sock
    MILTERSOCKETOWNER="postfix:postfix"
    MILTERSOCKETMODE="0660"

and `README.Debian` describes what those two do in a sentence that, read
carefully, contains the whole problem: they "allow you to change the username as
well as the permissions of the socket **after it has been created by the
daemon**."

The init script does it in the obvious place — the moment `start-stop-daemon`
reports success:

    start-stop-daemon $START

    case "$?" in
            0)
               log_end_msg 0
               if [ "$MILTERSOCKETTYPE" = "pipe" ]; then
                 if [ "$MILTERSOCKETOWNER" ]; then
                   chown "$MILTERSOCKETOWNER" "$MILTERSOCKET"
                 fi
                 if [ "$MILTERSOCKETMODE" ]; then
                   chmod "$MILTERSOCKETMODE" "$MILTERSOCKET"
                 fi
               fi
               ;;

`start-stop-daemon` reports success when the process it started has forked and
the parent has exited. The question step 4 existed to answer is whether the
socket is there yet at that instant.

## Two calls, in the other order

Priya pulled the source. In `amavisd-milter/main.c`, the last thing `main()`
does before going into the background:

    #ifdef HAVE_SMFI_OPENSOCKET
        if (smfi_opensocket(false) != MI_SUCCESS) {
            logmsg(LOG_ERR, "could not open milter socket %s", mlfi_socket);
            exit(EX_SOFTWARE);
        }
    #endif

        /* Run in the background */
        if (daemonize) {
            if (daemon(1, 1) != -1) {
                daemonized = 1;
            } else {

The socket is bound, then the fork happens. By the time the parent is gone and
`start-stop-daemon` returns, `/var/spool/postfix/amavis/amavis.sock` exists and
the `chown` in the next line of the init script has something to chown.

1.6.1 did not have those lines. It called `smfi_register()`, forked, wrote the
pid file, and called `smfi_main()`; libmilter's `mi_listener()` opens the socket
itself, at the top:

    if (mi_opensocket(conn, backlog, dbg, false, smfi) == MI_FAILURE)
            return MI_FAILURE;

So the socket got created some microseconds into the child, in a race with the
`chown` that the init script was already running in the parent's shell. On a
loaded boot the child usually won. Twice in two years it had not, and the boot
log from those mornings said so in a line nobody had ever connected to the mail
outage:

    chown: cannot access '/var/spool/postfix/amavis/amavis.sock': No such file or directory

The socket then stayed `amavis`-owned, `smtpd` got `EACCES`, and every sender
saw a 451.

`CHANGES` dates the fix to 20190121 and gives the reason in the submitter's own
terms:

    20190121:
            The milter socket is created before amavisd-milter is daemonized.
            This allows to return an error in case of impossibility to create
            the milter socket and package maintainers can adjust milter socket
            permissions immediatelly after the main process exits.

            Thanks to: Matus Uhlar

It shipped in 1.7.0, one line in the release notes: "Fork after initializing
milter socket." Priya had crossed it in a distribution upgrade, in a batch of
eleven packages, on a Tuesday.

The second half of that changelog entry turned out to matter as much as the
first. `smfi_opensocket()` failing now kills the process before the fork, so
`start-stop-daemon` sees the exit status instead of a cheerful zero, and because
`daemonized` is still `0` at that point, `log.c` prints the message to the
terminal as well as to syslog:

    # amavisd-milter -s /var/spool/postfix/amavis/amavis.sock -S /var/lib/amavis/amavisd.sock
    could not open milter socket /var/spool/postfix/amavis/amavis.sock
    # echo $?
    70

Under 1.6.1 that failure happened in the child, after the parent had already
exited 0 and the init script had already printed the green `[ ok ]`.

Priya checked that `mi_opensocket()` returns `MI_SUCCESS` immediately when
`listenfd` is already valid, so `smfi_main()` calling it a second time costs
nothing, and then edited the runbook.

    ## After a reboot of mx2
    1. Confirm postfix is listening on 25 and 587.
    2. Confirm amavis is up (systemctl status amavis).
    3. Confirm amavisd-milter is up. If the unit failed, the socket could
       not be created — read the message, it names the path.
    4. Flush the queue.

She committed it with the 1.7.0 changelog entry pasted into the message, so
whoever went looking for the old step 4 would find where it went.
