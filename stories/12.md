# Exit Code 18 on the Bastions

*Theme: Hardening and least privilege*

The ticket was three lines long, which is how Priya knew it would be harder than it
looked. *Bastion hosts: file integrity monitoring required by the new baseline. Use
AIDE. Close when reports are arriving.* It was her second week. Tomasz had assigned it
to her with the comment "good way to learn the bastions," and she had no reason yet to
distrust him.

The package part went fine. `apt install aide` on `bastion-01`, which pulled in
`aide-common`, and the next morning a mail arrived from the daily check saying it had been
terminated because no AIDE database was present. The
installer had a debconf question about initialising the database, but it was asked at
medium priority and defaulted to *no*, and nobody had seen it scroll past. Fair
enough: an integrity checker has nothing to compare against until someone takes the
first snapshot.

So she took one.

```
$ sudo aide --init
  ERROR: missing configuration (use '--config' '--before' or '--after' command line parameter)
```

That surprised her. She found the explanation in `README.Debian`: the Debian build of
aide is compiled with no default configuration file, on purpose, "to prevent an
accidental invocation of aide from messing with the Debian database." You say which
config you mean every time.

```
$ sudo aide --config /etc/aide/aide.conf --init
...
AIDE successfully initialized database.
...
Number of entries:      187443
```

Six minutes later she had `/var/lib/aide/aide.db.new`. The daily check reads
`/var/lib/aide/aide.db`, as `database_in` in `aide.conf` says, and aide won't let the
input and output database be the same file, so she copied it across:

```
$ sudo cp /var/lib/aide/aide.db.new /var/lib/aide/aide.db
```

She did the same on the other three bastions, commented "baseline taken, reports
should start tomorrow," and moved on.

The report arrived the next morning. It was not the one she wanted.

```
******************************************************************************
*            AIDE returned with exit code 18. Input/Output error!            *
******************************************************************************
```

The error section underneath had one line:

```
  ERROR: /etc/aide/aide.conf:11: open (read/write) failed for file '/var/lib/aide/aide.db.new': Permission denied (line: 'database_out=file:/var/lib/aide/aide.db.new')
```

All four bastions said the same. She stared at "Permission denied" for a while. The
check ran from a systemd timer. Timers ran as root. Root doesn't get permission
denied on a file in `/var/lib`.

She brought it to Tomasz, who asked her to run one command.

```
$ ls -l /var/lib/aide
-rw-r--r-- 1 root root 38112945 Sep 14 16:02 aide.db
-rw-r--r-- 1 root root 38112945 Sep 14 16:02 aide.db.new
$ ls -ld /var/lib/aide
drwx------ 2 _aide root 4096 Sep 14 16:02 /var/lib/aide
```

"The directory belongs to someone called `_aide`," he said. "Your two files belong
to root. Now look at who the timer runs as."

```
$ systemctl cat dailyaidecheck.service
...
[Service]
Type=oneshot
User=_aide
Group=_aide
AmbientCapabilities=CAP_DAC_READ_SEARCH CAP_AUDIT_WRITE
...
```

That was the part she hadn't known. Since 0.18 the Debian packaging creates a system
user, `_aide`, and the README says it "tries hard to run aide as that user." To
compensate, the unit hands it `CAP_DAC_READ_SEARCH`, which bypasses read permission
checks and directory search checks. That's how an unprivileged process can hash
`/etc/shadow` and walk into every `0700` directory on the box. It doesn't grant
write. `_aide` can read the root-owned `aide.db` she'd copied into place, so the
comparison side would have worked. But the default `COMMAND` in `/etc/default/aide`
is `update`, which also writes a fresh database to `database_out`. aide opens that
file read-write, and a root-owned `0644` file is just as closed to `_aide` as it is
to anyone else. That's exit 18, `IO_ERROR`.

"Why go to the trouble?" she asked. "It's a security tool. It's the one thing you'd
expect to run as root."

Tomasz opened the source package's `debian/patches/` directory and pointed at two
files, `CVE-2025-54389.patch` and `CVE-2025-54409.patch`. The first changed aide to
escape control characters in file names before it prints them in logs and reports.
The second fixed the code that decodes extended-attribute values when aide reads its
database back. "Look at what aide spends its night doing," he said. "It opens every
file on the machine, including the ones in `/tmp` and every user's home directory. It
reads their names, their xattrs, their contents, and it prints things about them.
Anyone with a shell on a bastion gets to decide what some of those inputs look like.
That's exactly the kind of program you don't want holding every privilege root has.
It needs to *read* everything, so it gets read-everything plus the audit
capability. It doesn't get to write outside its own files, so a parser bug in aide
can't be turned into a write to `/etc`."

"So I broke it by being root."

"You broke it by being root *without handing the result back*. That's what
`aideinit` is for."

She'd seen `/usr/sbin/aideinit` in the package listing and taken it for a
convenience alias. It's a short shell script, and he read through it with her. It
parses `database_out` and `database_in` out of the config itself, so you don't
repeat the paths. It checks for `capsh`. If it's there, which it was, the actual
`aide --init` runs under a `capsh` invocation that switches to `--user=_aide` and
adds `cap_dac_read_search` and `cap_audit_write` as ambient capabilities. That's the
same identity and the same two privileges the timer uses, so the files it creates
belong to the account that will have to rewrite them. Output goes to
`/var/log/aide/aideinit.log`, errors go to `/var/log/aide/aideinit.errors`, and the
script appends the return code to the log either way. Then it asks before replacing
the baseline.

"Try it as it stands," Tomasz said. "Before you fix the ownership."

```
$ sudo aideinit
Overwrite existing /var/lib/aide/aide.db.new [Yn]? y
Running aide --init...
AIDE --init return code 18
$ cat /var/log/aide/aideinit.errors
  ERROR: /etc/aide/aide.conf:11: open (read/write) failed for file '/var/lib/aide/aide.db.new': Permission denied (line: 'database_out=file:/var/lib/aide/aide.db.new')
AIDE --init return code 18
```

"Same wall," he said. "It's running as `_aide`, same as the timer. It found your
root-owned leftovers the same way the timer did." The package's own `postinst`
contains the fix, for sites upgrading from before the `_aide` user existed:
`chown _aide:root` on the two database files. She did that, and ran it again.

```
$ sudo chown _aide:root /var/lib/aide/aide.db /var/lib/aide/aide.db.new
$ sudo aideinit
Overwrite existing /var/lib/aide/aide.db.new [Yn]? y
Running aide --init...
Overwrite /var/lib/aide/aide.db [yN]?
```

She noticed the capital letters had flipped. Overwriting `aide.db.new` defaults to
yes, because it's a scratch file. Overwriting `aide.db` defaults to *no*. The man page
says why in one sentence: "In most cases you will want to check for any problems
before doing this." `aide.db` is the baseline, the record of what the machine is
supposed to look like. Replacing it means accepting, without a report, every change
made since the last one. aide itself won't do that step; it refuses to write to the
file it reads from. `aideinit` will do it, but only if you type `y`, or pass `-f` to
say you mean it in advance.

On a bastion that had been in service for two years, she didn't want a baseline taken
from a state nobody had reviewed. She wanted one taken from a state she could vouch
for. So she typed `y` on `bastion-01` only after Tomasz had compared the package
checksums with `debsums -c` and it came back clean. She did the other three the same
way, one at a time.

```
$ ls -l /var/lib/aide
-rw-r--r-- 1 _aide root 38114020 Sep 15 11:40 aide.db
-rw-r--r-- 1 _aide root 38114020 Sep 15 11:40 aide.db.new
$ tail -1 /var/log/aide/aideinit.log
AIDE --init return code 0
```

The next morning's reports were framed differently, with *No changes detected!* in
the banner on three hosts. On the fourth it said *Changed entries detected!*: someone
had edited `/etc/ssh/sshd_config` overnight. That was a conversation for a different
ticket, and the first thing the new baseline caught.

Before closing, Priya added a line to the bastion runbook:

> Initialise or rebuild the AIDE baseline with `sudo aideinit`, never with bare
> `aide --init` as root. The daily check runs as `_aide` with read-only capabilities
> and can't rewrite files root created in `/var/lib/aide`. Answer the `[yN]` prompt
> only after the host's state has been verified.

Tomasz approved it with one edit. He changed "never" to "not," because of the house
rule about runbooks sounding like threats, and closed the ticket for her.
