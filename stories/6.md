# Step four of the failover plan

*Theme: Disaster recovery and failover*

Step four of the site failover plan was a single line, and I had read it at every
annual exercise for three years without reading it at all:

> 4. Stop hv-07 (`systemctl poweroff`). libvirt-guests shuts the guests down
>    cleanly; wait for the host to power off before taking the final storage snapshot.

The rest of the plan was built on that sentence. The snapshot shipped to the second
site was supposed to be *clean*: every filesystem unmounted and every database
checkpointed. That was the whole reason we stopped the host rather than just cutting
replication. Restoring from a clean snapshot is a boot. Restoring from a dirty one is
a recovery, and nobody had budgeted time for a recovery.

Magda was running the exercise with me on the bridge call. I typed the poweroff and
followed the journal.

```
libvirt-guests.sh[88214]: Running guests on default URI: web-01, web-02, cache-01, ..., ledger-01, ledger-02, ledger-03
libvirt-guests.sh[88214]: Shutting down guests on default URI...
libvirt-guests.sh[88214]: Starting shutdown on guest: web-01
libvirt-guests.sh[88214]: Starting shutdown on guest: web-02
...
libvirt-guests.sh[88214]: Shutdown of guest web-01 complete.
libvirt-guests.sh[88214]: Shutdown of guest cache-01 complete.
...
libvirt-guests.sh[88214]: Waiting for 3 guests to shut down, 100 seconds left
libvirt-guests.sh[88214]: Waiting for 3 guests to shut down, 95 seconds left
```

Fourteen guests went down in under twenty seconds. The last three sat there while the
counter ran down from the 120 seconds that the packaged `/etc/default/libvirt-guests`
ships with, and all three were the ledger machines.

```
libvirt-guests.sh[88214]: Waiting for 3 guests to shut down, 5 seconds left
libvirt-guests.sh[88214]: Timeout expired while shutting down domains
```

Then systemd carried on with the host shutdown and took the QEMU processes down with
it. From inside the guests that looks exactly like somebody pulling the power cord.
"They're just slow," Magda said. "Ledger has that big flush on stop." We both
wanted that to be true, and the second site did its best to agree: PostgreSQL on
ledger-02 replayed its WAL and came up. But ledger-01 runs the nightly export to
the bank. It writes a flat spool file that it only renames into place at the end, and
that machine came back with a half-written file and no rename. We re-ran the export by
hand, wrote "passed with findings" on the exercise, and I took the finding.

## "Slow" didn't hold up

The next morning I cloned ledger-01 onto a lab hypervisor and asked it to shut down.

```
$ virsh shutdown ledger-01-clone
Domain 'ledger-01-clone' is being shutdown

$ virsh domstate ledger-01-clone
running
```

I tried again after a minute and got the same answer, and after five minutes the same
answer again. No flush was running. The guest console showed nothing at all: no
"The system is going down" broadcast, no init scripts stopping. The guest had simply
not heard anything. The web servers had.

The comment in libvirt-guests' own defaults file had warned about this, and I had
read past it every year:

> Please be careful with this settings since there is no way to distinguish between a
> guest which is stuck or ignores shutdown requests and a guest which just needs a long
> time to shutdown.

It turned out to be the second case: a guest that ignored the request.

## What `virsh shutdown` actually sends

My mental model had been "virsh shutdown asks the guest to shut down", as though a
message went in and the guest read it. The libvirt QEMU driver is more literal than
that. If the domain has a guest agent channel, it uses the agent. If not, it falls
back to ACPI, and ACPI shutdown here means the QMP command `system_powerdown`. QEMU
answers that by pressing the virtual machine's power button. That's all it does:
there's no message and no request, just an electrical event on a chassis that
doesn't exist. None of our guests had the agent, so every one of them got the button.

A quick `virsh dumpxml` confirmed `<acpi/>` was in the domain's `<features>`, so the
virtual board did have a power button to press. Inside the clone, the kernel had found
it too:

```
$ grep -A4 'Power Button' /proc/bus/input/devices
N: Name="Power Button"
P: Phys=LNXPWRBN/button/input0
...
```

So the hardware was there, the driver was there, and the press was arriving. The rest
I only understood once I opened `drivers/acpi/button.c`. When the button fires, the
kernel's driver does two things and nothing else:

```c
	input_report_key(input, keycode, 1);
	input_sync(input);
	input_report_key(input, keycode, 0);
	input_sync(input);

	acpi_bus_generate_netlink_event(device->pnp.device_class,
					dev_name(&device->dev),
					event, ++button->pushed);
```

It reports a `KEY_POWER` keypress on an input device and broadcasts an event over
netlink. It doesn't shut anything down. That's deliberate. What a power button
*means* is policy: suspend on a laptop, halt on a server, nothing at all on a kiosk
in a shopping centre. The kernel leaves that decision to userspace. On the web
servers, systemd-logind makes the decision, and `HandlePowerKey=poweroff` is its
default. Ledger was the odd one out. The vendor's stack wouldn't run under systemd,
so the three machines were built in 2019 from a Devuan `debootstrap --variant=minbase`
template with sysvinit and nothing else. That meant no logind and no elogind. And
acpid, the older program that exists for exactly this job, is `Priority: optional`,
so minbase never installed it. Nothing in userspace was listening, and the key was
being pressed into an empty room.

## The daemon in between

acpid predates logind by about a decade, and its README tells you why it's shaped
the way it is. The old section, dated 2004, reads:

> ACPID used to try to handle events internally. Rather than try to climb an
> ever-growing mountain, ACPID now lets YOU define what events to handle.

Early acpid tried to know what every button and battery event should do. Its authors
gave that up and turned it into a dispatcher. It reads kernel events and matches each
one against the regular expressions in `/etc/acpi/events/`. When a rule matches, it
runs that rule's action through `/bin/sh`. It also rebroadcasts every event on
`/var/run/acpid.socket`, so any number of programs, from a desktop power manager to
a shell pipeline, can hear the same press. It started out reading `/proc/acpi/event`.
When the kernel deprecated that file in favour of netlink and the input layer, acpid
2.x moved over too, and the kernel on these guests no longer has the proc file at all.

I installed it on the clone and pressed the button from the host again.

```
# apt-get install acpid
...
$ virsh shutdown ledger-01-clone
Domain 'ledger-01-clone' is being shutdown
$ virsh domstate ledger-01-clone
running
```

It still did nothing. acpi_listen, which connects to the socket and prints whatever
acpid hears, showed me why:

```
# acpi_listen
button/power PBTN 00000080 00000000
button/power LNXPWRBN:00 00000080 00000001
```

acpid was hearing the press, twice in fact: once from the input layer (`PBTN` is
acpid's own name for `KEY_POWER`) and once from netlink, with the ACPI device name and
a press counter. But `/etc/acpi/events/` was empty. Devuan doesn't fork acpid; it
ships Debian's own package, straight from Debian's pool, and that package installs the
power-button rule and its `powerbtn.sh` only under `/usr/share/doc/acpid/examples/`.
Ubuntu used to patch them back into `/etc`, and the changelog entry where it stopped
gives the reason: on a normal system logind is always running, the stock script does
nothing when it sees logind, so there's no point installing it by default. That's the
right call for almost everyone, and exactly the wrong one for us. The example script
also spends most of its length checking for desktop power managers, none of which will
ever run on a ledger box.

So I wrote the rule myself, for a server:

```
# cat /etc/acpi/events/powerbtn-server
event=button/power PBTN
action=/sbin/shutdown -h now "Power button pressed"
```

The regex matches anywhere in the event string. A bare `button/power` would match both
lines, and I'd get two `shutdown` calls for one press. Anchoring it to the input-layer
form gives exactly one action per press, and that form is spelled the same whatever
the firmware calls the button.

To watch it happen, I stopped the service and ran acpid in the foreground with event
logging turned on:

```
# service acpid stop
# acpid -f -l
starting up with netlink and the input layer
1 rule loaded
waiting for events: event logging is on
```

Then, from the host:

```
$ virsh shutdown ledger-01-clone
Domain 'ledger-01-clone' is being shutdown
```

and in the guest:

```
received input layer event "button/power PBTN 00000080 00000000"
rule from /etc/acpi/events/powerbtn-server matched
executing action "/sbin/shutdown -h now "Power button pressed""
received netlink event "button/power LNXPWRBN:00 00000080 00000001"
...

Broadcast message from root@ledger-01-clone (Tue Mar 17 09:42:11 2026):

Power button pressed
The system is going down for system halt NOW!
```

Eleven seconds later `virsh domstate` said `shut off`, and the clone had run the
export service's stop script on the way down. That stop script was the one step that
would have saved the bank file in March.

## What changed

Three things came out of it. The ledger template and the three live machines got
acpid with that one rule, rolled out through config management so it would survive the
next rebuild. The DR plan's step four got a precondition that we test rather than
assume: before the exercise, `virsh shutdown` a throwaway instance of every template
on the host and time it. A template that doesn't stop within a minute blocks the
exercise. And we put qemu-guest-agent on the backlog, because once a guest has the
agent channel, libvirt tries the agent before it tries the button. That's a second,
independent way for the request to get in.

When I walked Magda through the clone's output, it wasn't the missing daemon that
stung. It was the timeout. For three years we had watched fourteen machines stop in
twenty seconds and three take the full two minutes, and we had written the difference
off as "slow". Those three machines had never been slow. Every year they had waited out
the timer for a shutdown that was never going to start.
