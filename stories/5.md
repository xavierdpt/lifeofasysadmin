# The disc that started at cylinder 400

*Theme: Legacy archaeology*

The drive came in a padded envelope with a luggage tag tied through the mounting
holes. The tag said, in fountain pen: *Lab 3 RiscPC. Linux side has the arm
controller code. Please keep.* The donor was a lecturer who had retired before
anyone now in the department had been hired, and the robot arm was on a shelf in
the basement with its cable cut.

Ngozi ran the imaging bench for the university archive. The routine was the same
for every donated disk: write blocker, `ddrescue`, checksum, `chmod 444` on the
image, and after that nobody touched the original again. The drive read cleanly. It
was a 512 MB IDE disk, and the image came out as `lab3.img`, 536,739,840 bytes, with
no bad sectors.

The next step was cataloguing, and Tomasz, the student on placement that term,
started it the way anyone would have.

```
$ fdisk -l lab3.img
Disk lab3.img: 511.88 MiB, 536739840 bytes, 1048320 sectors
Units: sectors of 1 * 512 = 512 bytes
Sector size (logical/physical): 512 bytes / 512 bytes
I/O size (minimum/optimal): 512 bytes / 512 bytes
$ blkid lab3.img; echo $?
2
$ file lab3.img
lab3.img: data
```

There was no `Disklabel type:` line and no partitions. `blkid` found nothing and
said nothing. Tomasz tried `losetup -P` so the kernel could look for partitions
itself, and no `loop0p` devices appeared. "I think somebody wiped it before they
posted it," he said. "It's just data."

"Look at the tag," Ngozi said. "It was a RiscPC. The first thing on the disk isn't
Linux's, so it isn't going to start with a PC partition table."

---

A RiscPC booted RISC OS from ROM, and RISC OS assumed it owned the whole hard disk.
Its filing system, Filecore, formats the disk as a single volume. There is no MBR
and no partition table in sector 0 in the PC sense. What Filecore does have is a
boot block at byte `0xC00`, which is sector 6, and a *disc record* inside it that
describes the geometry and the size of the volume. Ngozi had seen a few of these
before, and she knew where to look.

```
$ xxd -s 0xdc0 -l 64 lab3.img
00000dc0: 093f 1000 0f0a 0100 0009 4006 012d 0000  .?........@..-..
00000dd0: 0000 4e0c 2b1a 4c61 6233 2020 2020 2020  ..N.+.Lab3      
00000de0: 0000 0000 0000 0000 0000 0000 0000 0000  ................
00000df0: 0000 0000 0000 0000 0000 0000 0990 012e  ................
```

She read it out for Tomasz. `09` is log2 of the sector size, so 512 bytes. `3f` and
`10` mean 63 sectors per track and 16 heads. The four bytes at `0xdd0` are the size
of the Filecore volume, little-endian: `0x0c4e0000`, which is 206,438,400 bytes. The
disc name was `Lab3`, space-padded. The disk was 536 MB, so the Filecore volume
ended well before the end of the disk.

"So RISC OS only used the first 200 MB of it. Then what's after that?"

"Look at the last four bytes." The final byte, `2e`, was the boot block's checksum.
The three before it were what Filecore calls the non-ADFS partition descriptor, and
they were how Linux had got onto the machine at all. The low nibble of `0xdfc` gives
the type of whatever sits after the Filecore volume, and 9 means Linux. The next two
bytes give the cylinder where it starts: `0x0190`, cylinder 400.

That hook predated Linux. Acorn's own Unix, RISCiX, used the same descriptor with
types 1 and 2. The kernel still has `PARTITION_RISCIX_MFM` and
`PARTITION_RISCIX_SCSI` next to `PARTITION_LINUX` in `block/partitions/acorn.c`.
When ARM Linux came to the RiscPC in the late nineties, it used that existing hook
instead of asking people to reformat. RISC OS kept the start of the disk. Linux got
the tail end, and a small table of its own at the first sector of that tail.

Cylinder 400 at 16 heads and 63 sectors is sector 403,200:

```
$ xxd -s $((403200*512)) -l 32 lab3.img
0c4e0000: dea1 afde 0200 0000 fe9c 0800 1eab afde  ................
0c4e0010: 009d 0800 003b 0100 0000 0000 0000 0000  .....;..........
```

Tomasz spotted it first: `deafa1de`, byte-swapped. Then `deafab1e`. The whole table
is triples of magic, start and size. The magic says *Linux native* or *Linux swap*,
and the start is counted from the table's own sector, not from the start of the disk.

"You could do all of this with a hex dump and a calculator," Ngozi said. "People
did, the first time. That's why somebody wrote the tool."

---

```
$ sudo apt install acorn-fdisk
$ acorn-fdisk --version
arm-fdisk v3.0.6
```

It still reported the old name. The README in the source package is signed by
Russell King, dated 1998, and calls it *ARM FDISK Version 3.0*. Debian still ships
it. The QA group keeps it building, and the most recent change is from 2023, moving
the binary to `/usr/sbin`. The package description is a single sentence: *partition
editor for Acorn/RISC OS machines*. Every Linux on a RiscPC had to deal with a disk
RISC OS already owned. On top of that, most expansion-card disk controllers of the
period used their own layout: ICS IDE, PowerTec SCSI, EESOX SCSI. The util-linux
`fdisk` read none of them. So the tool is one front end with a separate back end for
each scheme. With no `-t`, it tries each back end's detector in turn, and the
PC/BIOS one comes last. Its block I/O layer is written to build on RISC OS too,
where device names look like `ADFS::4`. That let you partition the disk from RISC OS
before there was a Linux on the machine to do it from.

```
$ acorn-fdisk -l lab3.img

Disk lab3.img: 16 heads, 63 sectors, 1024 cylinders
Units = cylinders of 1008 * 512 bytes

   Device Boot   Begin    Start      End   Blocks     Id   System
lab3.img1            0        0      400     201600    100  Filecore
lab3.img2          400      400      401          1    101  Linux Table
lab3.img3          401      401      960     282239     83  Linux Native
lab3.img4          960      960     1040      40320     82  Linux Swap
```

Partition 1 is the Filecore volume and partition 2 is the two-sector Linux table.
The real partitions start at 3. The kernel's own Acorn parser numbers them the same
way, so on the RiscPC this disk would have shown up as `hda3` and `hda4`.

Tomasz was already typing a `losetup` command and multiplying 401 by 1008. Ngozi
stopped him. Cylinder units round *up*, because the listing computes
`(sectors + display_factor - 1) / display_factor`, and the Linux partition doesn't
start on a cylinder boundary. It starts two sectors after the table, which is
itself at the start of cylinder 400. Cylinder 401 would have put him 1,006 sectors
past the superblock. The interactive mode can switch units, and because the image
is `0444` and they weren't root, `acorn-fdisk` opened it read-only. It tries
`O_RDWR` first and falls back to read-only when that fails.

```
$ acorn-fdisk lab3.img

Device lab3.img is partitioned using Filecore/Linux scheme

Command action
   d    delete a partition
   m    print this menu
   n    add a new partition
   p    print the partition table
   q    quit without saving changes
   r    reopen partition, specifying type
   t    change a partition's system id
   u    change display/entry units
   w    write table to disk and exit

Command (m for help): u
Changing display/entry units to sectors

Command (m for help): p

Disk lab3.img: 16 heads, 63 sectors, 1024 cylinders
Units = sectors of 512 bytes

   Device Boot   Begin    Start      End   Blocks     Id   System
lab3.img1           -1        0   403199     201600    100  Filecore
lab3.img2       403199   403200   403201          1    101  Linux Table
lab3.img3       403201   403202   967679     282239     83  Linux Native
lab3.img4       967679   967680  1048319      40320     82  Linux Swap

Command (m for help): q
```

(The "1024 cylinders" is a guess. An image file has no drive geometry, so the tool
falls back to 16/63/1024, even though the last partition clearly runs past cylinder
1024. The offsets come from the disc record, not from that line.)

The table matched the hex dump: 403,200 plus 2 is 403,202, and the partition is
564,478 sectors long.

```
$ sudo losetup -r -f --show -o $((403202*512)) --sizelimit $((564478*512)) lab3.img
/dev/loop3
$ sudo file -s /dev/loop3
/dev/loop3: Linux rev 0.0 ext2 filesystem data, UUID=5d0e8c41-7b2a-4f93-a6c1-2e8b04d7f915
$ sudo mount -o ro /dev/loop3 /mnt/lab3
```

It was revision 0 ext2, the original on-disk format, and it mounted without
complaint. `/etc/fstab` on the old root listed `/dev/hda3` as `/` and `/dev/hda4`
as swap, which matched `acorn-fdisk`'s numbering. `/home/pmr/robotarm` held the
controller code, a `NOTES` file, and a Makefile that assumed a cross-compiler nobody
had installed in twenty years.

---

Afterwards, Tomasz asked why the kernel hadn't simply found all this when he ran
`losetup -P`. There is a parser for it: `adfspart_check_ADFS` reads sector 6, checks
the same checksum and the same nibble, and lays the partitions out exactly as
`acorn-fdisk` had. But `CONFIG_ACORN_PARTITION` defaults to on only when building
for the Acorn architecture itself, and the kernel annotations in Ubuntu's source
package set it to `n` on every architecture they build. The knowledge is in the
kernel tree, just not in the kernel on the imaging bench.

He also asked why `acorn-fdisk` was so fussy about that checksum. It won't
recognise a Filecore disk whose boot block fails the check. Before it writes, it
reads the boot block again and refuses with *filecore boot sector has been changed
by another program* if the checksum has moved since it was loaded. Ngozi's answer
was that the tool had been built for a disk with two owners. Every edit to the Linux
end meant rewriting three bytes in the middle of RISC OS's boot block. If RISC OS
had touched that block in between, blindly writing it back would have damaged the
half of the disk that booted the machine.

Out of curiosity he also ran it with `-t PC/BIOS` to see what a PC-minded tool would
have made of the disk. It told him: *The master boot sector does not contain a valid
signature. This will be corrected when writing partition information to disk.* He
quit without writing.

In the catalogue entry, Ngozi wrote down what the next person would need, in the
order they would need it. RISC OS Filecore volume, 400 cylinders, disc name `Lab3`.
Non-ADFS descriptor type 9 at cylinder 400. ext2 rev 0 at sector 403,202, length
564,478. Swap at sector 967,680. Read with `acorn-fdisk` in sector units, not
cylinders. She added the SHA-256 of the image and filed the luggage tag with it.

There was one more thing in the working directory. Every run had left
`/tmp/part.debug` behind, a trace of each detector the tool had tried and what it
had found. The README asked for that file with any bug report, *gzip & uuencode*d,
and warned that other compression formats would be ignored. She deleted it. The
address the README gave for sending it was older than Tomasz.
