# Seven Weeks of Exit 3

*Theme: Cascading failure*

The package I removed was six megabytes and had nothing to do with mail.

In April we retired an internal tool on mx1 — an attachment indexer that had
been reading ticket attachments out of the helpdesk queue and had stopped being
useful two reorganisations ago. I removed it, ran `apt autoremove` because that
is what you do, and read the list before answering yes:

```
The following packages will be REMOVED:
  7zip p7zip p7zip-full ...
```

I read it. I remember reading it. `p7zip-full` had come in as a dependency of
the indexer, it was going out with the indexer, and mx1 is a mail gateway:
Postfix in front, amavisd-new as the content filter, clamd behind it. Nothing on
that box opens archives by hand. I pressed y.

## What the filter is for

amavisd-new sits between the MTA and the scanners, and its job is not simply to
hand the message to clamd. Before anything is checked, it takes the message
apart: MIME parts out to a work directory, each part identified with `file(1)`,
each part that turns out to be a container expanded, and the expanded contents
identified and expanded again, down to `$MAXLEVELS` — 14 on Debian. Only
then do the checks run, and they run on the whole tree.

The reason is visible in the shipped `README.banned`, which is a dump of part
paths from real mail. One of them:

```
p.path: "P=p003,L=1,M=multipart/mixed | P=p002,L=1/2,
         M=application/x-zip-compressed,T=zip,N=foto.zip |
         P=p006,L=1/2/3,T=exe,T=exe-ms,N=foto/expander.exe"
```

Three segments, separated by pipes: the message, the zip attached to it, and a
file inside the zip. The banned-file rules are matched against that string. The
Debian defaults in `/etc/amavis/conf.d/20-debian_defaults` include

```perl
  qr'.\.(exe|vbs|pif|scr|bat|cmd|com|cpl)$'i, # banned extension - basic
  qr'^\.(exe-ms)$',                       # banned file(1) types
```

and neither of them can match anything at all unless the third segment exists.
A policy about what may arrive by mail is worth exactly as much as the unpacker
that produces the names for it to read. Without the expansion step you are back
to the shape of a 1998 mail filter: a scanner handed an opaque blob, an
administrator with opinions about `.exe` attachments and no way to act on them
once somebody puts the `.exe` in a container.

Which unpacker does the expanding is a table, `@decoders`, one tuple per short
type. Some entries carry an internal Perl routine; most name external programs,
with alternatives, and the tuples stack so that a later one can back up an
earlier one:

```perl
    ['rar',  \&Amavis::Unpackers::do_unrar, \$unrar],
    ['cab',  \&Amavis::Unpackers::do_cabextract, \$cabextract],
    [['zip','kmz'], \&Amavis::Unpackers::do_7zip,  ['7za', '7zz', '7z'] ],
    [['zip','kmz'], \&Amavis::Unpackers::do_unzip],
    ['7z',   \&Amavis::Unpackers::do_7zip,  ['7zr', '7za', '7zz', '7z'] ],
    [[qw(xz lzma jar cpio arj rar swf lha iso cab deb rpm)],
             \&Amavis::Unpackers::do_7zip,  ['7zz', '7z'] ],
```

That last tuple is the site's insurance policy. Eleven types that already have
their own unpacker get 7-Zip as a second chance, and four types — `jar`, `swf`,
`lha`, `iso` — appear nowhere else in the list and have 7-Zip as their only
chance. The names are resolved once, at startup, by walking `$path` and
stat-ing. A running amavisd holds the answers in memory and does not look again.

## Seven weeks

So on the fourteenth of April the daemon was still running with `/usr/bin/7z`
written into six tuples, and the file had been gone for four minutes.

It kept trying. `do_7zip` builds a listing command first — `7z l -slt -w<tmpdir>
-- <part>` — and the fork succeeds, the exec does not, and the child writes its
own epitaph before exiting 3:

```
run_command: child process [30211]: run_command: failed to exec
  /usr/bin/7z l -slt -w/var/lib/amavis/tmp/amavis-20250506T081144-05612/parts
  -- .../parts/p002: No such file or directory
```

The parent reads an empty pipe, reaps the status, and dies with
`can't get a list of archive members: exit 3;` — with nothing after the
semicolon, because the last non-empty line of output was never written.
`decompose_part` catches that, decides the part is atomic after all, and logs at
level -1, which is below the default `$log_level = 0` and therefore always
written:

```
Decoding of remittance.iso (ISO 9660 CD-ROM filesystem data) failed,
  leaving it unpacked: do_7zip: can't get a list of archive members: exit 3;
```

That line was in `/var/log/mail.log` on mx1 from April the fourteenth. Nobody
reads mail.log.

On the second of June somebody added a domain to `50-user` and restarted amavis,
and `find_external_programs` ran again on a host where `7z` no longer existed.
This time the table was built without it, and the startup banner said so:

```
No ext program for   .zip, tried: 7za; 7zz; 7z
No ext program for   .7z, tried: 7zr; 7za; 7zz; 7z
No ext program for   .iso, tried: 7zz; 7z
No decoder for       .7z
No decoder for       .iso
No decoder for       .jar
No decoder for       .lha
No decoder for       .swf
```

Zip survived: the tuple below it holds `do_unzip`, which is Perl, and it was
promoted. It is logged as `Internal decoder for .zip` at level 1, and at our
`$log_level` of 0 it was not logged at all. The asymmetry is deliberate — what
amavisd found is a level 1 detail, what it failed to find is level 0 — and the
effect on that morning's banner is that the only decoder lines in it were the
absences.

And the `exit 3` lines stopped, because from then on nothing was attempted.

## The far end

On the twenty-fourth of July accounts payable received a remittance advice with
a 1.1 MB `remittance.iso` attached. The ISO held one file,
`remittance_advice.pdf.exe`. amavisd treated the ISO as a leaf, clamd scanned
the ISO as a leaf and had no signature for it, and the log line was:

```
Passed CLEAN {RelayedInbound}, [198.51.100.24]:45188 <billing@...>
  -> <ap@...>, Queue-ID: 4XBcRt2yTpz3wYk, mail_id: kO7mQeLwx2nS,
  Hits: 1.911, size: 1184532, 812 ms
```

The clerk opened it. The workstation was reimaged; the payment run that had been
scheduled for the twenty-fifth went out on the twenty-ninth, by which point two
suppliers had rung the finance director. What the double-extension rule would
have matched, had there been a third segment in the part path to match against,
is `remittance_advice.pdf.exe`, and the destiny for banned mail on this host is
`D_DISCARD`. The mail would not have reached her at all.

Working backwards took most of a day and ended in `/var/log/dpkg.log.6.gz`:

```
2025-04-14 09:41:22 remove 7zip:amd64 23.01+dfsg-11 <none>
```

I installed `7zip`, restarted amavis, set `$log_level = 1` in `50-user` long
enough to read the banner back, and got the line I wanted:

```
Found decoder for    .iso  at /usr/bin/7z
```

The check that runs on mx1 now greps the last amavisd startup banner for
`No decoder for` and pages if the set of short types it finds differs from the
set recorded the day it was written. It has fired once since, for `.zoo`, after someone
tidied up the `zoo` package.
