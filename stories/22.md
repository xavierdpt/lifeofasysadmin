# Seven Weeks of Exit 3

*Theme: Cascading failure*

The package I removed was six megabytes and had nothing to do with mail.

In April we retired an internal tool on mx1 — an attachment indexer that had
been reading ticket attachments out of the helpdesk queue and had stopped being
useful two reorganisations ago. I removed it, ran `apt autoremove` because that
is what you do, and read the list before answering yes:

```
The following packages will be REMOVED:
  7zip p7zip p7zip-full ...
```

I read it. I remember reading it. `p7zip-full` had come in as a dependency of
the indexer, it was going out with the indexer, and mx1 is a mail gateway:
Postfix in front, amavisd-new as the content filter, clamd behind it. Nothing on
that box opens archives by hand. I pressed y at 09:41.

## What the filter is for

amavisd-new sits between the MTA and the scanners, and its job is not to hand
the message to clamd. Before anything is checked it takes the message apart:
MIME parts out to a work directory, each part identified with `file(1)`, each
part that turns out to be a container expanded, and the expanded contents
identified and expanded again, down to `$MAXLEVELS` — 14 on Debian. The checks
then run against the whole tree.

The reason is visible in `README.banned`, which ships with the source and is a
dump of part paths taken from real mail. One of them:

```
p.path: "P=p003,L=1,M=multipart/mixed | P=p002,L=1/2,
         M=application/x-zip-compressed,T=zip,N=foto.zip |
         P=p006,L=1/2/3,T=exe,T=exe-ms,N=foto/expander.exe"
```

Three segments, separated by pipes: the message, the zip attached to it, and a
file inside the zip. The banned-file rules are matched against that string, and
the Debian defaults in `/etc/amavis/conf.d/20-debian_defaults` include

```perl
  qr'.\.(exe|vbs|pif|scr|bat|cmd|com|cpl)$'i, # banned extension - basic
  qr'^\.(exe-ms)$',                       # banned file(1) types
```

Both of those describe the third segment. If the second segment is the end of
the path — if the zip was never opened — the rules have nothing to read and the
message is clean by default. That is the whole of the dependency: a policy about
which attachments may arrive is an opinion until an unpacker turns the container
into names.

Which unpacker does the expanding is a table, `@decoders`, keyed by short type.
A few entries carry an internal Perl routine; most name external programs, with
alternatives, and the tuples stack so a later one can back up an earlier one:

```perl
    ['rar',  \&Amavis::Unpackers::do_unrar, \$unrar],
    ['cab',  \&Amavis::Unpackers::do_cabextract, \$cabextract],
    [['zip','kmz'], \&Amavis::Unpackers::do_7zip,  ['7za', '7zz', '7z'] ],
    [['zip','kmz'], \&Amavis::Unpackers::do_unzip],
    ['7z',   \&Amavis::Unpackers::do_7zip,  ['7zr', '7za', '7zz', '7z'] ],
    [[qw(xz lzma jar cpio arj rar swf lha iso cab deb rpm)],
             \&Amavis::Unpackers::do_7zip,  ['7zz', '7z'] ],
```

Four tuples in the shipped list name 7-Zip, and the last one is the site's
insurance policy. It covers twelve short types. Eight of them have their own
unpacker further up and are only borrowing a second chance. The other four —
`jar`, `swf`, `lha`, `iso` — appear nowhere else in the table, and 7-Zip is the
only thing that will ever open them.

The programs are located once, at startup, by walking `$path` and stat-ing each
candidate. A running amavisd holds the answers in memory and never looks again.

## Seven weeks of noise

That matters for what happened next, which is nothing.

At 09:41 the binary went away. The daemon was already running, so it kept the
string `/usr/bin/7z` in those four tuples, and went on dispatching ISO
attachments to a decoder that was no longer installed. `do_7zip` builds a
listing command first — `7z l -slt -w<tmpdir> -- <part>` — and after the
removal the fork still succeeded and the exec did not. The child logged its own
epitaph and exited 3:

```
run_command: child process [30211]: run_command: failed to exec
  /usr/bin/7z l -slt -w/var/lib/amavis/tmp/amavis-20250506T081144-05612/parts
  -- .../parts/p002: No such file or directory
```

The parent read an empty pipe, reaped the status, and died with `can't get a
list of archive members: exit 3;` — nothing after the semicolon, because the
routine appends the last non-empty line of the program's output and there had
not been one. `decompose_part` caught that, decided the part was atomic after
all, and logged it:

```
Decoding of Scan_2291.iso (ISO 9660 CD-ROM filesystem data) failed,
  leaving it unpacked: do_7zip: can't get a list of archive members: exit 3;
```

That one was a supplier's scanned delivery notes, on the sixth of May, and it
was harmless. It was also the shape of everything that followed. An ISO reaching
mx1 was being written to the work directory, failed on, and passed to the banned
rules as a single opaque part — the part path ending at segment two, the rules
matching nothing, the message delivered. The filter had stopped examining ISO
contents at 09:41 on the fourteenth of April and said so in `/var/log/mail.log`
every time, at log level -1.

The minus sign is not a quiet level. The scale runs the other way from the one
you expect: `$log_level` is a ceiling, ours was the default 0, and a line is
written when its own level is at or below that ceiling. Debug chatter at 4 and 5
stays out. Errors at -1 get through whatever the ceiling is, and below them
amavisd keeps -2 and a single -3, which prefixes its message with `FATAL:`.
So the lines were in `/var/log/mail.log` for seven weeks, in a file that on a
mail gateway takes a few hundred thousand lines a day, and nobody reads
mail.log.

## The restart that changed the logging

On the second of June somebody added a domain to `50-user` and restarted amavis.
`find_external_programs` ran again, on a host where `7z` no longer existed, and
this time the table was built without it:

```
No ext program for   .zip, tried: 7za; 7zz; 7z
No ext program for   .7z, tried: 7zr; 7za; 7zz; 7z
No ext program for   .iso, tried: 7zz; 7z
No decoder for       .7z
No decoder for       .iso
No decoder for       .jar
No decoder for       .lha
No decoder for       .swf
```

Zip came through it: the tuple below holds `do_unzip`, which is Perl, and it was
promoted to primary. It is announced as `Internal decoder for .zip` at level 1,
and our ceiling was 0, so that line was not written. The asymmetry is deliberate
— what amavisd found is a level 1 detail, what it failed to find is level 0 —
and the effect on that morning's banner is that its only decoder lines were the
absences.

For ISO attachments, the restart changed nothing that a recipient could see.
They had been arriving unexamined since April and they went on arriving
unexamined. What the restart took away was the `exit 3` lines, because there was
no longer anything in the table to attempt.

## The far end

On the twenty-fourth of July accounts payable received a remittance advice with
a 1.1 MB `remittance.iso` attached. The ISO held one file,
`remittance_advice.pdf.exe`. amavisd wrote the ISO to the work directory and
left it there, clamd scanned it as a single file and had no signature for it,
and the log line was:

```
Passed CLEAN {RelayedInbound}, [198.51.100.24]:45188 <billing@...>
  -> <ap@...>, Queue-ID: 4XBcRt2yTpz3wYk, mail_id: kO7mQeLwx2nS,
  Hits: 1.911, size: 1184532, 812 ms
```

The clerk mounted it and ran the file. The workstation was reimaged the same
afternoon; the payment run scheduled for the twenty-fifth went out on the
twenty-ninth, by which point two suppliers had rung the finance director.

Had the ISO been opened, the part path would have carried a third segment named
`remittance_advice.pdf.exe`, `file(1)` would have called it `exe-ms`, and two
separate rules in `20-debian_defaults` would have matched it. `$final_banned_destiny`
on this host is `D_DISCARD`. The message would not have been delivered.

Working backwards took most of a day. It ended in `/var/log/dpkg.log.6.gz`:

```
2025-04-14 09:41:22 remove 7zip:amd64 23.01+dfsg-11 <none>
```

I installed `7zip`, restarted amavis, set `$log_level = 1` in `50-user` long
enough to read the banner back, and got the line I wanted:

```
Found decoder for    .iso  at /usr/bin/7z
```

The check that runs on mx1 now greps the most recent amavisd startup banner for
`No decoder for` and pages if the set of short types differs from the set
recorded on the day it was written. It has fired once since, for `.zoo`, after
someone tidied up the `zoo` package.
