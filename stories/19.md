# A June Timestamp on a September Tape

*Theme: Slow burn*

The digitisation unit at the county archive runs two storages. `libnas` is a
pool of virtual tapes on the NAS in the machine room, written every night.
`offsite` is an LTO-8 drive bolted under the desk; on Monday mornings someone
carries last week's cartridge to a safe deposit box three streets away and
brings back the one from a fortnight ago.

Ines built the second half of that in March 2023, and it was four lines in the
`backup` user's crontab:

```
# weekly off-site copy - one current full of every DLE
0 6 * * 0  /usr/sbin/amvault --latest-fulls --dest-storage offsite dig
```

`amvault` ships in `amanda-common`, which is the package that holds the parts
both ends of an Amanda installation need — the libraries, the perl modules
under `Amanda/`, the chunker, and the handful of `/usr/sbin` tools that are
neither purely client nor purely server. It is, as its own man page puts it,
conceptually `amfetchdump | taper`: it reads dumps back off one storage and
writes them onto another, and the catalog remembers that both copies exist.

It ran every Sunday for three and a half years. It never failed.

## What it will not do

The first thing `amvault` does with its arguments is refuse to accept none of
them:

```
usage("specify something to select the source dumps") unless
    $opt_src_write_timestamp or $opt_fulls_only or $opt_latest_fulls or
    $opt_incrs_only or @opt_dumpspecs;
```

`Amanda/Vault.pm` says why, in a comment beside the equivalent check further
down: *we do not want the wildcard "vault it all!" behavior*. There is no
`--everything`. A vault run is a copy of a subset, and the operator has to name
the subset, because the subset is the off-site policy and Amanda declines to
guess it.

There are two natural ways to name it, and they are not the same question.
One is "duplicate this run" — `--src-timestamp`, the timestamp of the amdump or
amflush that wrote the dumps, with `latest` meaning the most recent such run.
The other is "keep a current full of each thing" — `--latest-fulls`, which the
usage text glosses as *copy the latest full of every dle*, and the man page more
precisely as "the latest full of every DLE in the disklist that do not have the
skip strategy".

That second option exists because the alternative was unbounded. `--fulls-only`
copies every level-0 in the catalog, which for a site with a year of retention
means writing the same June full onto every off-site cartridge forever; the
workaround before was to generate one dumpspec per DLE from the disklist and
feed them in by hand. `--latest-fulls` is the bounded version: one full per
entry, sized by the disklist rather than by history, which is exactly what fits
on a cartridge you can carry.

Ines wanted one current full of each thing. She chose correctly. The word doing
the work is *latest*, and it means latest in the catalog.

## Eight hundred gigabytes of scans

`fileserv:/srv/scans` is where the book scanner writes. It was 400 GB in 2023.
Nobody graphs it; it only ever goes up.

In June 2026 the nightly report started carrying a line in its NOTES section:

```
NOTES:
  planner: fileserv /srv/scans 20260614223002 0 ["dumps too big, 918372448 KB, full dump delayed, doing incremental"]
```

That is `delay_dumps()` in the planner doing its job. The estimated full no
longer fits in what is left of the night's tape, so rather than fail the run,
the planner swaps the level-0 estimate for the degraded one and takes an
incremental instead, meaning to come back for the full tomorrow. Tomorrow the
arithmetic is the same. The line appeared three times in June, five times in
July, and from the second week of August it was in every report.

Amanda was not failing. Every run finished, every DLE was backed up, the
incrementals were small and fast and the report was green. The only thing that
had changed was that `/srv/scans` had stopped getting fulls, and the newest
level-0 of it in the catalog stayed where it was.

Sunday after Sunday, `amvault --latest-fulls` looked up the latest full of every
DLE in the disklist, found the same June dump for that one, and wrote it out
again. Faithfully. The cartridge that went into the deposit box in September
held a copy of the June scans and the June scans only, and the four months of
incrementals that would have carried them forward had never been selected by
anything, because an incremental is not a full.

## The Tuesday

The controller firmware on the NAS was updated on a Tuesday afternoon and the
volume group holding the vtape pool did not come back. This is the day the
deposit box is for, and for about an hour everyone felt reasonably good about
it.

Ines put the newest cartridge in the drive and ran a dry run to see what she
had:

```
$ amvault -n --latest-fulls --dest-storage offsite dig
DIG-088 4 fileserv /srv/scans 20260607223001 0 918372448
DIG-091 1 fileserv /srv/www 20260913223004 0 4103992
...
Total Size: 1284773120 KB
```

`-n` prints the plan without moving anything: label, file number, host, disk,
then the dump timestamp, the level and the size. The second field from the end
of each line is what she was looking at. `/srv/www` said September. `/srv/scans`
said `20260607223001`.

Vaulting does not rewrite that number, and `Amanda/DB/Catalog.pm` is explicit
about it: the `dump_timestamp` corresponds to the initiation of the original
dump run, while `write_timestamp` is when the file was written to the volume,
and "when parts are migrated from volume to volume (e.g., by amvault), the
`dump_timestamp` does not change". The September tape was a September write of
a June dump, and had been saying so in the catalog all along:

```
$ amadmin dig find --sort sd fileserv /srv/scans
date        host     disk       lv storage pool   tape or file  file part status
2026-06-07  fileserv /srv/scans  0 libnas  vtapes DIG-088          4 1/3  OK
2026-06-07  fileserv /srv/scans  0 offsite lto    OFF-0031         1 1/2  OK
2026-06-07  fileserv /srv/scans  0 offsite lto    OFF-0032         1 1/2  OK
...
2026-09-13  fileserv /srv/scans  1 libnas  vtapes DIG-141          2 1/1  OK
```

The `storage` column is the one that answers the question. Every `offsite` row
for that DLE had a June date on it. `amadmin find` will sort by it — `s` for
storage, `d` for dump timestamp — and nobody had ever asked.

## What went in the ticket

Recovery ran off the June full and stopped there. Eleven working days of
scanning between the last on-site incremental and the outage were re-shot from
the physical volumes, which were still in the building; the rest of June through
September came back off the scanner workstations, where the operators keep local
copies for proofing that IT has asked them twice to stop keeping.

The crontab line is gone. `dig`'s `amanda.conf` now reads, in part:

```
vault-storage "offsite"

define storage libnas {
    ...
    vault "offsite" 0
}

define storage offsite {
    ...
    dump-selection ALL ALL
}
```

With `vault-storage` set and a `vault` entry on the primary storage, `amdump`
queues each night's dumps for the vault storage itself, at every level, zero
days after the dump. Ines kept `amvault` in the crontab too, with the other
selector, for the mornings when the drive is busy and the queue does not drain:

```
15 7 * * *  /usr/sbin/amvault --src-timestamp latest --dest-storage offsite dig
```

The first run of it printed `Using latest timestamp: 20260924223002` and then
sixty-one lines starting `Wrote OFF-0044:`, one per part, including the
incrementals.
