# Total 1000 Entries

*Theme: Capacity and scaling*

The ticket came in from a member of the radio club who had been trying to reach a
packet BBS in another country all week. His mail to the club list was two lines long:
pings to the BBS used to come back, then they started hanging instead of failing, and
could somebody look at the gateway.

Ines had been running the club's AMPRNet gateway for six years — a small Debian box in
a rack at the university, an IPIP tunnel called `ampr0`, and `ampr-ripd` keeping the
44net routes in it current. She read the ticket on the tram and expected it to be the
BBS's problem.

```
# ip route get 44.135.94.7
44.135.94.7 via 169.228.66.251 dev ampr0 src 44.143.8.1 uid 0
    cache
```

The route was there. The endpoint it pointed at had not answered anything in months;
the portal listed that subnet as withdrawn in the spring, when the operator gave his
allocation back. A withdrawn subnet is supposed to stop having a route. With no route,
the packets would leave by the ordinary default and get an honest refusal from
somewhere on the internet. With a route into the tunnel, they went to an IPIP endpoint
that no longer decapsulated anything, and died there without a word. That was the
hanging.

## What the daemon is for

The routes in a 44net gateway are not a network anyone can compute. Each participating
site owns a chunk of 44/8 and sits behind whatever public address it happens to have
that year; reaching another site means encapsulating in IPIP and sending it to that
site's public address. The mapping between the two is a list, and for years the list
was a file: fetch `encap.txt` from the central gateway on a cron job, run it through a
script, and turn every `route addprivate 44.135.94/24 encap 169.228.66.251` line into
an `ip route add ... dev tunl0 onlink`. Sites moved on their own schedule and your copy
was as fresh as your crontab.

`ampr-ripd` replaced the download. The central gateway broadcasts the whole table as a
RIPv2 set over the tunnel, in packets of at most twenty-five entries each, and the
daemon listens for them and injects what it hears straight into the kernel by netlink,
stamped with routing protocol 44 so its routes can be told apart from everything else
in the table — `ip route show proto 44` is the whole inventory. Ines still had a copy
of the encap file: `-s` writes one to `/var/lib/ampr-ripd/encap.txt`, in the same
`route addprivate` format as the old download, so a gateway that reboots has routes
before the first broadcast arrives.

The other half of what RIP buys you is the part the cron job never had. A site that
goes away is announced as gone: the entry comes back with a metric above 14, and
`process_entry()` deletes the route. A file you re-download tells you a line is
missing; a broadcast tells you a line is dead.

## The number that had stopped moving

The Debian package builds with `-D HAVE_DEBUG` left in the Makefile, and its unit file
starts the daemon with `-d`, so it stays in the foreground and systemd collects
everything it says. Ines had never had a reason to read it.

```
# journalctl -u ampr-ripd --since -10min | tail -4
ampr-ripd[834]: Processing RIPv2 packet, 25 entries (total 1000 entries).
ampr-ripd[834]: Can not find an unused route entry.
ampr-ripd[834]: Can not find an unused route entry.
ampr-ripd[834]: Processing RIPv2 packet, 25 entries (total 1000 entries).
```

She walked the journal backwards. In February the totals were in the nine hundreds and
climbing a few a week, the way they had climbed since she inherited the box. On the
fourteenth of March the number reached 1000 and every line after it said 1000.

`ampr-ripd.c` is one file, and the reason is at the top of it:

```c
#define RTSIZE		1000	/* maximum number of route entries */
```

with `route_entry routes[RTSIZE];` below — a fixed array, and `list_add()` scanning it
for a slot whose timestamp is zero. When there is no such slot the loop runs off the
end and prints the line she had just read.

## Why the kernel had more routes than the daemon did

The part that made the symptom look like the BBS's fault is the order of two calls in
`process_entry()`:

```c
	route_update(rip->address, netmask, rip->nexthop);
	list_update(rip->address, netmask, rip->nexthop);
```

The kernel is told first, and it is told unconditionally. Every new subnet announced
after the fourteenth of March got its route installed exactly as before. Traffic to
new sites worked, which is why nobody had a ticket to file about it.

What those subnets did not get was a slot in the daemon's own table, and the table is
what the daemon consults for everything except installing. The withdrawal path looks
the subnet up with `list_find()` and only calls `route_del()` if it finds it. The
expiry sweep in the alarm handler walks `routes[]` and deletes anything whose timestamp
is more than `EXPTIME` — 600 seconds — behind the clock. `route_delete_all()`, which
runs on SIGTERM and on SIGHUP, walks `routes[]` too. A route that never got into the
array could be created but not retired, aged out, or cleaned up on exit. When the
operator of 44.135.94.0/24 handed his allocation back, the central gateway announced
it at metric 15 as it should have, and the club's gateway heard it, looked it up, did
not find it, and left the route in the kernel.

That also explained the restart the club's other operator had tried in July, which he
remembered as "not making any difference". It had not. The stale routes were the ones
the daemon could not see to delete.

The evidence had been on disk the whole time. Ines ran the daemon with the example's
`-x` hook, `ip route | grep 'proto 44' >/var/lib/ampr-ripd/routes`, which fires after
any change:

```
# wc -l < /var/lib/ampr-ripd/routes
1043
# grep -c addprivate /var/lib/ampr-ripd/encap.txt
1000
```

Forty-three routes in the kernel that the daemon had no record of. Both files were also
being rewritten every thirty seconds, because a failed `list_add()` still sets the
`updated` flag, so every broadcast looked like a change: the encap file re-saved, the
`-x` command re-run, all day, for six months. The mtime on `/var/lib/ampr-ripd/routes`
had been within thirty seconds of `now` every time anyone had ever looked at it, which
is exactly how a file that is churning constantly looks like a file that is working.

## Raising the ceiling

`RTSIZE` is a compile-time constant in a single-file program. Ines pulled the source,
changed the 1000 to 4000, and built it the way the Makefile does:

```
$ gcc -Wall -O2 -D HAVE_DEBUG -o ampr-ripd ampr-ripd.c
```

Then she stopped the old daemon, flushed the routes it had left behind with
`ip route flush proto 44` — the protocol number exists so that this command can be
typed without taking out the university's own routing — dropped the stale
`encap.txt`, and started the new binary.

```
ampr-ripd[2210]: Processing RIPv2 packet, 25 entries (total 1031 entries).
ampr-ripd[2210]: Processing RIPv2 packet, 12 entries (total 1043 entries).
```

The last thing she did before closing the ticket was add a line to the box's telegraf
config to scrape that total out of the journal into the club's Grafana, next to the
tunnel byte counters that had been graphed since 2019. The reply to the member said
the BBS had moved off 44net in April and gave him its current address.
