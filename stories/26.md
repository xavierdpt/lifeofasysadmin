# The spike at 08:26

*Theme: Performance investigation*

The ticket was four words long: "morning sync is slow." It came from Priya on the
third floor, who starts her day by pulling a few gigabytes of instrument data off
the departmental share onto her workstation, and who had noticed that some
mornings it took four minutes and some mornings it took twenty. She had attached
a screenshot of a progress bar, which is not evidence, and a time: 08:26.

Forty-one lab workstations. They are switched off at night — actually switched
off, at the wall, by the last person out, because the building's power budget is
a thing somebody upstairs cares about. That detail is why the machines run
anacron at all. Cron will happily hold a 06:25 entry for cron.daily and never
fire it, because at 06:25 the machine is a box of cold metal. Anacron takes the
other approach: it asks, for each job, whether the job has run in the last *n*
days, and if not it runs it now. Its whole model is in one sentence of
`anacron(8)` — "Unlike cron(8), it does not assume that the machine is running
continuously."

So the first question was not "why is the share slow" but "what else are these
machines doing at 08:26."

## Reading the log

Anacron logs to syslog under facility `cron` at priority `notice`, which on these
boxes means the journal has it. Priya's machine is lab-3-14:

```
$ journalctl -u anacron.service -S "2026-09-15 07:00" -U "2026-09-15 09:00"
07:33:41 lab-3-14 anacron[1841]: Anacron 2.3 started on 2026-09-15
07:33:41 lab-3-14 anacron[1841]: Will run job `cron.daily' in 5 min.
07:33:41 lab-3-14 anacron[1841]: Will run job `cron.weekly' in 10 min.
07:33:41 lab-3-14 anacron[1841]: Jobs will be executed sequentially
07:38:41 lab-3-14 anacron[1841]: Job `cron.daily' started
08:26:02 lab-3-14 anacron[1841]: Job `cron.daily' terminated
08:26:02 lab-3-14 anacron[1841]: Job `cron.weekly' started
08:41:55 lab-3-14 anacron[1841]: Job `cron.weekly' terminated
08:41:55 lab-3-14 anacron[1841]: Normal exit (2 jobs run)
```

There is the 08:26, to the second, and it is not the share at all. It is
cron.weekly starting on her own workstation — which on this image means
`updatedb.plocate` walking two local disks and a `borg create` of `/home` — at
the exact instant cron.daily finished. Her download writes into `/home` on the
disk both of those are reading. On the mornings she started before 08:26 she got
four minutes; on the mornings she started after it she got twenty.

I had been carrying an assumption for years, and the log had just contradicted
it. The two numbers in `/etc/anacrontab` are a period and a delay:

```
1	5	cron.daily	run-parts --report /etc/cron.daily
7	10	cron.weekly	run-parts --report /etc/cron.weekly
@monthly	15	cron.monthly	run-parts --report /etc/cron.monthly
```

I had read 5 and 10 as a stagger: daily first, weekly five minutes behind it,
monthly five minutes behind that, the three of them spread out so they never
overlap. That is not what the numbers are. The delay is measured from the moment
anacron started, not from the end of the job before it. `main.c` computes
`start_sec + jr->delay * 60` and sleeps until then. Both deadlines — 07:38:41 and
07:43:41 — were already in the past by 08:26. The sleep for cron.weekly returned
immediately.

Put another way: a stagger only survives if each job finishes before the next
job's delay expires. Five minutes between these two, and cron.daily ran for
forty-seven. The README says what the delay was for in the first place:
Anacron was written to be run from the boot scripts, so that jobs whose time has
come run shortly after the machine boots, and "a delay can be specified for each
job so that the machine isn't overloaded at boot time." It buys you a few minutes
of quiet while the desktop session comes up. It was never a scheduler.

## Where the forty-seven minutes went

Forty-seven minutes and twenty-one seconds for cron.daily was its own question.
`run-parts --report` only names scripts that produce output, so a silent script
that takes half an hour leaves no trace in the mail. `--test` lists what would
run, in order, without running it:

```
$ run-parts --test /etc/cron.daily
/etc/cron.daily/0anacron
/etc/cron.daily/apt-compat
/etc/cron.daily/dpkg
/etc/cron.daily/logrotate
/etc/cron.daily/man-db
/etc/cron.daily/plocate
/etc/cron.daily/dept-homedir-quota
```

Timing them one at a time on a spare machine put 44 of the 47 minutes in
`dept-homedir-quota`, a `du -s` over every home directory on a filesystem that
had grown by a factor of six since somebody wrote the script.

`dept-homedir-quota` is a utility to report on department member usage, probably
for billing or auditing. The script walks the whole tree because someone wrote it
to be portable and didn't assume the filesystem had quotas enabled. But the lab
workstations had quotas all along. `repquota -a` just reads what the kernel has
already computed, in milliseconds instead of forty-four minutes. The script was
replaced in-place:

```
#!/bin/sh
repquota -a | grep /home | mail -s "Lab disk usage" dept-billing@
```

Shortening cron.daily would move the spike earlier without removing it, because
cron.weekly is going to start the moment cron.daily stops whatever time that is.
That handover is `-s`, which Debian's anacron runs with: "Anacron will not start
a new job before the previous one finished." It comes from `ANACRON_ARGS=-s` in
`/etc/default/anacron`, which `anacron.service` pulls in through
`EnvironmentFile`, and it is a variable rather than a constant deliberately —
Debian bug #743448 asked for job serialisation to be customisable. Dropping it
would be worse here: the jobs would then start on their own delays and overlap,
two index rebuilds on one disk at once.

The lever that does separate them is the delay column, once you read it as
absolute. The loop in `main.c` does two things per job, in this order: sleep
until that job's delay has passed, and only then wait for the previous job to
finish. The delay is a floor, not an offset. With both fixes — the quota script
and the delays — cron.daily would run for three minutes, cron.weekly would sleep
until an hour and a half after boot, and Priya's pull would not collide with
anything.

## What went in

Two things. The anacrontab delays moved everything further apart:

```
1	5	cron.daily	run-parts --report /etc/cron.daily
7	120	cron.weekly	run-parts --report /etc/cron.weekly
@monthly	180	cron.monthly	run-parts --report /etc/cron.monthly
```

`anacron -T` parses a candidate anacrontab and returns 0 if it is valid, so the
config management run checks the file before it lands:

```
$ anacron -T -t /tmp/anacrontab.new && echo ok
ok
```

The quota script went into a commit with the message "avoid full filesystem scan
in dept-homedir-quota by using repquota(8)", and was deployed on a Thursday
morning. Lab-3-14's journal from the next Monday:

```
07:31:12 anacron[1793]: Will run job `cron.daily' in 5 min.
07:31:12 anacron[1793]: Will run job `cron.weekly' in 120 min.
07:36:12 anacron[1793]: Job `cron.daily' started
07:39:43 anacron[1793]: Job `cron.daily' terminated
09:31:12 anacron[1793]: Job `cron.weekly' started
09:50:08 anacron[1793]: Job `cron.weekly' terminated
```

Three minutes for cron.daily, and cron.weekly starts and finishes an hour and
fifty-five minutes later. I closed Priya's ticket with these two days of journal.
On the mornings after that she ran her pull at 08:00 and it completed in four
minutes every time.
