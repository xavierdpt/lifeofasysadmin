# Three nameservers on a restored handheld

*Theme: Backup and restore*

The restore drill was Marta's idea, and by the fourth quarter of doing it she had
stopped expecting it to be interesting. The fleet was ninety-odd Android handhelds that
the pickers carried around a cold store, and on each one, under the scanner app, sat a
Debian armhf chroot holding the label toolchain: a Python service, a pile of ZPL
templates, and enough of a userland to run `apt-get` against the internal mirror.

The backup regime had two halves, because the chroot did. The base was an archived
tarball, `labeller-base.tar.gz`, built years ago at the Erith depot and still the thing
the recovery procedure named by filename. On top of it went the nightly tar of the data
and the site config. Restoring meant unpacking the base onto a spare handheld,
`apt-get install`ing the current package list into it from the mirror, untarring last
night's data over that, and starting the chroot. The drill was to do all four and see
how long it took to get a label out.

Twelve minutes, mostly untarring. Then the package install, step six, and it sat there.

Not failed — sat. Five seconds of nothing, then the mirror answered and the index
downloaded at the speed the warehouse wifi usually managed. The next fetch did the same.
Five seconds, then fine. Five seconds, then fine.

Five seconds is a number you learn to recognise. It is `RES_TIMEOUT` in
`/usr/include/resolv.h`, the glibc resolver's wait before it gives up on a nameserver
and moves to the next one in the list. `resolv.conf(5)` is explicit about the order: up
to three nameservers may be listed, and "the resolver library queries them in the order
listed" — try one, and if the query times out, try the next. Something was first in that
list and was not answering.

```
$ cat /etc/resolv.conf
nameserver 10.40.0.9
nameserver 10.12.7.1
nameserver 10.12.7.2
```

The second and third were the resolvers the handheld was actually on. The first belonged
to Erith, which had stopped doing labelling eighteen months ago and had been switched
off at the wall not long after.

On these devices `/etc/resolv.conf` is not a file anybody writes. It is assembled by
`resolvconf` from the records under `/run/resolvconf/interface/`, and Marta expected to
find one record there, called `android`, put there by `android-androresolvd`. She found
two:

```
$ ls /run/resolvconf/interface/
android  original.resolvconf
```

The daemon first, because it was the part she understood least. The package description
is blunt about what it is for — a small user space daemon to get the Android DNS server
setting and maintain the resolver config — and ends by saying that it "only makes sense
to install on a Debian chroot running on Android." The problem it solves is the seam
between the two halves of the device. The Android side knows the DNS servers: when a
picker walks out of wifi range at the loading bay and the radio falls back to mobile
data, Android has new values in its `net.dns1` and `net.dns2` system properties within a
second. The chroot's glibc knows nothing about system properties. It reads a file. Before
the daemon, a picker who lost name resolution mid-shift handed the handheld to a
supervisor, who read the new resolver off the Android settings screen and typed it into
`/etc/resolv.conf` inside the chroot, because nothing else carried the value across.

`androresolvd` carries it across. It reads both properties, then loops: `sleep(2)`, read
them again, `strcmp` against what it had, and push an update only if one of them changed.
Marta added `-d` to the launcher on the Android side — the daemon has to be started from
there, not from a login shell in the chroot — and watched it while she walked the spare
handheld out past the bay doors:

```
piping to "/sbin/resolvconf -a android":
nameserver 10.12.7.1
nameserver 10.12.7.2
```

Nothing for a minute and a half, and then, as the wifi dropped:

```
piping to "/sbin/resolvconf -a android":
nameserver 192.168.44.1
```

That is the whole mechanism: `update_resolvconf()` opens a pipe to
`/sbin/resolvconf -a android` and writes `nameserver` lines into it. The daemon holds no
opinion about the rest of `/etc/resolv.conf`. It owns one record, under one name, and
lets `resolvconf` assemble the file. It has worked that way since version 1.1-1 in March
2012, where the changelog entry is three words — "Switched to resolvconf hook" — and the
reason shows at the other end of the process. The handler for `SIGINT` and `SIGTERM`
calls `update_resolvconf(0, "android", 0, 0)`, which runs `/sbin/resolvconf -d android`,
and the init script's `stop` case sends `kill -INT` to whatever
`pidof /usr/sbin/androresolvd` returns. Stop the daemon and its two nameservers leave the
file with it. A daemon that wrote `/etc/resolv.conf` itself would have to remember what
had been there before, and would leave its last guess behind when it died.

So the daemon was innocent. It had contributed exactly the two lines it was supposed to
contribute, and they were second and third. The first line came from the other record,
and that one named its own source: `original.resolvconf`, the copy of whatever
`/etc/resolv.conf` had held before `resolvconf` took the file over. The saved copy lives
in `/etc/resolvconf/resolv.conf.d/original`, and on this chroot it was a snapshot of
Erith, taken the day the base image was built.

The package knew about this. Marta found it in the postinst, under `configure`:

```sh
if [ -f /run/resolvconf/interface/original.resolvconf ];then
    # Ubuntu Precise: these are leftover files that add
    # additional old/outdated nameserver entries.
    rm -f /run/resolvconf/interface/original.resolvconf
    :> /etc/resolvconf/resolv.conf.d/original
fi
```

The changelog dates it to 28 March 2012: "Remove
`/run/resolvconf/interface/original.resolvconf` in postinst to prevent old nameserver
entries from showing up in the future." Sven-Ola had hit the same stale entry, and had
the package delete the record and empty the file it is made from.

Read the first line again, though. The truncation is inside an `if`, and what the `if`
tests is whether the record exists in `/run` *at the moment the package is configured*.
On the ninety handhelds in the cold store, `android-androresolvd` had gone in as an
ordinary upgrade on a running chroot, months after Erith closed: `resolvconf` was up,
`original.resolvconf` was sitting there in `/run`, the test passed, and both halves went
away for good. On the spare in Marta's hand, `apt-get install` had run inside a chroot
that had been unpacked eleven minutes earlier and had never started anything. `/run` was
a bare tmpfs. The test found no file, so nothing was removed and nothing was emptied —
and the `/etc` copy that survived the check was still full of Erith. When the chroot
finally started, `resolvconf` did what it does with a saved original: it laid the record
down in `/run`, first in the list, ahead of anything the daemon had to say.

Marta put the truncation into the restore procedure as step five and a half, between the
base unpack and the package install:

```
rm -f /run/resolvconf/interface/original.resolvconf
:> /etc/resolvconf/resolv.conf.d/original
```

She ran the drill again the next morning from the same base tarball. `apt-get install`
came back without a pause, and the label printed at eight minutes. Then she opened a
change request against `labeller-base.tar.gz` to have the file emptied in the archived
image itself, attached the drill sheet with both sets of timings, and put the spare
handheld back on the charging rack.
