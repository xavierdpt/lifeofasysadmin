# Three nameservers on a restored handheld

*Theme: Backup and restore*

The restore drill was Marta's idea, and by the fourth quarter of doing it she had
stopped expecting it to be interesting. The fleet was ninety-odd Android handhelds
that the pickers carried around a cold store, and on each one, under the scanner app,
sat a Debian armhf chroot holding the label toolchain: a Python service, a pile of ZPL
templates, and enough of a userland to run `apt-get` against the internal mirror. The
chroot was tarred to the NAS nightly. The drill was to take last night's tar, unpack it
onto a spare handheld from the charging rack, and see how long it took to get a label
out of it.

Twelve minutes, mostly untarring. Then she entered the chroot and ran `apt-get update`,
because that was step nine, and it sat there.

Not failed — sat. Five seconds of nothing, then the mirror answered and the file
downloaded at the speed the warehouse wifi usually managed. The next line of output did
the same. Five seconds, then fine. Five seconds, then fine.

Five seconds is a number you learn to recognise. It is `RES_TIMEOUT` in
`/usr/include/resolv.h`, the glibc resolver's minimum wait before it gives up on a
nameserver and moves to the next one in the list. `resolv.conf(5)` is explicit about the
order: up to three nameservers, "the resolver library queries them in the order listed",
and if the first one times out it tries the second. Something was first in that list and
was not answering.

```
$ cat /etc/resolv.conf
nameserver 10.40.0.9
nameserver 10.12.7.1
nameserver 10.12.7.2
```

The second and third were the ones the handheld was actually using. The first was from
the old site — the unit had been decommissioned eighteen months ago, when the labelling
work moved out of the Erith depot, and the address had not answered since.

On a production handheld, `/etc/resolv.conf` is not a file anybody writes. It is
assembled by `resolvconf` out of the records under `/run/resolvconf/interface/`, and on
these devices there is exactly one record, called `android`, put there by
`android-androresolvd`. Marta looked, and `android` was the only interface file present.
So the dead Erith resolver had arrived from somewhere else.

She went at the daemon first, because it was the thing she understood least. The
package description is blunt about what it is for: a small user space daemon to get the
Android DNS server setting and maintain the resolver config, and "this only makes sense
to install on a Debian chroot running on Android." The problem it solves is the seam
between the two halves of the device. The Android side knows the DNS servers; when the
handheld walks out of wifi range at the loading bay and the radio falls back to mobile
data, Android updates its `net.dns1` and `net.dns2` system properties within a second.
The chroot's glibc knows nothing about system properties. It reads a file. Before the
daemon, the runbook for a picker who lost name resolution mid-shift was to hand the
handheld to a supervisor, who read the new resolver off the Android settings screen and
typed it into `/etc/resolv.conf` in the chroot — a step that existed only because
nothing carried the value across.

`androresolvd` carries it across, and does very little else. It reads `net.dns1` and
`net.dns2`, then loops: `sleep(2)`, read both properties again, `strcmp` them against
what it had, and only if one of them changed does it push an update. Marta added `-d` to
the launcher on the Android side — the daemon has to be started from there, it cannot be
run out of a login shell — and watched the debug output while she walked the spare
handheld out past the bay doors:

```
piping to "/sbin/resolvconf -a android":
nameserver 10.12.7.1
nameserver 10.12.7.2
```

Nothing for a minute and a half, and then, as the wifi dropped:

```
piping to "/sbin/resolvconf -a android":
nameserver 192.168.44.1
```

That is the whole mechanism. `update_resolvconf()` opens a pipe to
`/sbin/resolvconf -a android` and writes `nameserver` lines into it. The daemon has no
opinion about the rest of `/etc/resolv.conf`; it owns one record, under one name, and
lets `resolvconf` do the assembling. It has been that way since version 1.1-1 in March
2012 — the changelog entry is three words, "Switched to resolvconf hook" — and the
reason shows up at the other end of the process. The signal handler for `SIGINT` and
`SIGTERM` calls `update_resolvconf(0, "android", 0, 0)`, which runs
`/sbin/resolvconf -d android`, and the init script's `stop` case is a `kill -INT` at
whatever `pidof /usr/sbin/androresolvd` returns. Stop the daemon and its nameservers
leave the file with it. A
daemon that wrote `/etc/resolv.conf` directly would have to remember what had been there
before, and would leave its last guess behind when it died.

So the daemon was innocent: it had written exactly the two lines it was supposed to
write, and they were second and third in the file. Marta went looking for who owned the
first line, and found it in `/etc/resolvconf/resolv.conf.d/original` — the copy
`resolvconf` keeps of whatever `/etc/resolv.conf` contained before it took the file
over. On this chroot that was a snapshot of Erith, taken the day the image was first
built, and `/etc` is inside the tarball.

The package knew about this. Marta found it in the postinst, under `configure`:

```sh
if [ -f /run/resolvconf/interface/original.resolvconf ];then
    # Ubuntu Precise: these are leftover files that add
    # additional old/outdated nameserver entries.
    rm -f /run/resolvconf/interface/original.resolvconf
    :> /etc/resolvconf/resolv.conf.d/original
fi
```

The changelog dates it to 28 March 2012: "Remove
`/run/resolvconf/interface/original.resolvconf` in postinst to prevent old nameserver
entries from showing up in the future." Sven-Ola had hit the same stale entry and
truncated the file at install time.

Which is why the ninety production handhelds were fine. On each of them the package had
been *installed*, the postinst had run, and `original` had been emptied before anyone
ever used the thing. The restored chroot had never installed anything. `tar` had simply
put `/etc` back the way it was, `original` included, full of Erith — and `/run` is a
tmpfs, so the half of the state that lives there came up empty and honest while the half
in `/etc` came up eighteen months out of date.

Marta added one line to the restore procedure, between the untar and the first chroot
entry:

```
:> /etc/resolvconf/resolv.conf.d/original
```

and ran the drill again the next morning with a fresh tar. `apt-get update` returned in
under two seconds. She put the spare handheld back on the charging rack, wrote the
timings into the drill sheet, and raised a change request to have the labelling image
rebuilt with the file already empty, so the next restore would not need the line at all.
