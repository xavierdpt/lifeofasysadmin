# Every five minutes, data type 64

*Theme: Observability*

The mesh is forty-one rooftops across two neighbourhoods, batman-adv over 5 GHz
directional links, run by a volunteer association with a budget of whatever the
grant covers. Priya has been the one holding the SSH keys since March.

The outage that started this took ninety minutes and was, in the end, one node
with a wedged radio. Finding it was the ninety minutes. `batctl o` gave her a
table of originator MACs and hop metrics, which is genuinely the right tool for
"what is the topology doing" and completely useless for "which building is
`02:1a:4f:c8:91:3e` bolted to". She had the answer in a spreadsheet, last edited
by someone who moved to Lisbon. Two of the MACs in it had changed when the radios
were swapped.

At the review she wrote down what she had wanted and hadn't had: for every node
in the mesh, its name, its firmware build, and which roof it was on — from
anywhere in the mesh, including from a laptop plugged into a node at the far
end of a partition.

## The thing she was already doing by hand

The workaround was a shell loop. Take the originator list, and for each MAC, look
up the node's mesh address, ssh in, `cat /etc/openwrt_release`. It worked. It also
only worked for nodes that answered, which is the exact complement of the set she
cared about, and it took as long as forty-one SSH handshakes over a mesh take,
which during an outage is long enough for someone to ask again in the chat.

The deeper problem was that there was nowhere to put a monitoring server. The mesh
has no centre. Gateways come and go when someone's uplink is rate-limited, and the
network partitions along the ridge often enough that "the node with the database on
it" is a node half the network cannot reach.

## alfred

The package is `alfred`, the binary is `alfred`, and the expansion on the tin is
Almighty Lightweight Fact Remote Exchange Daemon. The README quotes Marek Lindner
from 2012 describing it as "a user space daemon to efficiently[tm] flood the
network with useless data - like vis, weather data, network notes, etc", which is
a joke about the design and also an accurate description of it.

It exists because of a removal. batman-adv used to carry its own visualisation
server in the kernel module: every node flooded its neighbour table so any node
could draw the graph. That was a lot of policy to keep in kernel space for one
consumer, and it got taken out and rebuilt in userspace — `batadv-vis` now reads
the neighbour and client tables and hands them to alfred to distribute. Having
built a general "flood a blob of bytes to every node, with no configuration"
transport to carry the vis data, they left the door open: the man page's list of
what you might distribute runs "hostnames, phone books, administration
information, DNS information, the local weather forecast". The addressing is
IPv6 link-local multicast on port 0x4242, which is why there is nothing to
configure — link-local needs no address plan and no server to point at.

Priya installed it on one node and read the help output. Payloads are tagged with
a numeric data type, 0 through 255. She picked 42 for no reason at all:

```
# echo hello | alfred -s 42
bad data type argument
```

Types 0 to 63 are reserved — `ALFRED_MAX_RESERVED_TYPE` is 64 in `packet.h`, and
the client-side parser rejects anything below it before it opens the socket. The
man page says to email the authors to register one. Those are the slots the shipped
producers live in: `batadv-vis` publishes type 1, `alfred-gpsd` publishes type 2.
Everything from 64 up belongs to whoever is running the mesh. She took 64.

## What the nodes push

On each node, a five-minute timer running one line:

```sh
printf '%s\t%s\t%s\n' "$(uname -n)" "$(. /etc/openwrt_release; echo $DISTRIB_REVISION)" "$ROOF" \
    | alfred -s 64
```

`ROOF` comes from a file on the node that someone has to fill in once, on the day
they climb the ladder. That part is not automatable and Priya stopped trying.

The timer matters. alfred forgets data it has not been told again:
`ALFRED_DATA_TIMEOUT` is 600, ten minutes, after which the record is dropped from
the hash. Priya had initially read that as a limitation to work around. It is the
feature she actually wanted. A node that has fallen off the mesh stops being
listed, by itself, within ten minutes — the inventory is a list of nodes that are
currently alive and talking, not a list of nodes somebody once typed into a
spreadsheet. A stale row cannot outlive the thing it describes, because nothing
writes the rows but the things themselves.

## Reading it

From any node, or from her laptop with alfred running against the mesh interface:

```
# alfred -r 64
{ "02:1a:4f:c8:91:3e", "dach-hoffmannstr\t23.05.4\tHoffmannstr 14, rear\n" },
{ "02:1a:4f:c8:8e:02", "dach-kolping\t23.05.4\tKolpingplatz 3\n" },
{ "02:1a:4f:d1:07:aa", "dach-schule-nord\t22.03.6\tGrundschule, north gable\n" },
```

The output is that literal shape — brace, quoted source MAC, quoted payload,
brace, comma — with non-printable bytes escaped as `\xNN`. It is a C array
initialiser, which tells you what the first consumer was expected to be. Awk
handles it fine. `-d` appends the version byte set with `-V`, which she used later
when the payload format changed and half the mesh was still sending the old one.

The third line in that sample is the sort of thing the whole exercise was for. The
school is on 22.03.6 because the flash is 8 MB and the upgrade needs a hand-built
image, which is written down in an issue nobody has picked up. It had been sitting
there for four months. It appeared the first afternoon.

## The two things that bit her

The first was boot ordering. The daemon takes `-i` for the interfaces to listen on
and `-b` for the batman-adv interface, defaulting to `bat0`, and on a cold boot it
was starting before the mesh interface existed:

```
Can't start server: batman-adv interface bat0 not found
```

`-f` / `--force` starts the server anyway and lets the interfaces turn up later;
it went in for exactly this, the 2021.1 changelog entry reading "Allow to force of
alfred startup when the interfaces don't work/exist (yet)". `alfred -S` confirms
what a running daemon thinks it has:

```
- mode: secondary
- interface: bat0
	- status: active
- batman-adv interface: bat0
```

Secondary is the default; the primaries are the daemons started with `-m`, which
accept data from the secondaries around them and synchronise with each other. The
`-b` interface is how a secondary picks which primary to talk to — it asks
batman-adv for the best metric. Give it `-b none` and alfred still distributes
data, it just loses that selection.

The second was the map. She wanted the association's status page regenerated when
something changed, and her first version polled `alfred -r 64` every minute from
cron, which is a lot of nothing most of the time. The daemon can call out instead:
`-c` takes a command to run on data change, and appends the numbers of the data
types that changed to the command line, so the page builder gets invoked as
`/usr/local/bin/build-map 64` and can tell which feed woke it. For watching it
live while she got the payload format right, `-E` registers as an event listener
on the unix socket and prints one line per update as it arrives:

```
Event: type = 64, source = 02:1a:4f:c8:8e:02
```

That one is newer than the rest — event notification over the unix socket landed
in 2022.2, and before it the only way to find out something had changed was to ask
again and diff.

## The status page

It has a table now, forty-one rows on a good day. `batadv-vis -f dot`
feeds the graph beside it through `fdp`, which is why the package recommends
graphviz.

The firmware column is sorted descending by default. The school is still at the
bottom of it. Priya has the 8 MB image about half built.
