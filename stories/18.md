# The list goes in the ticket first

*Theme: Communication under pressure*

The message came in at 09:14 and had already been forwarded twice before it
reached Priya: a rsync job that someone had pointed at the wrong side of the
arrow had emptied `/srv/exports/finance/quarter-close` on `hake`. By 09:20 the
finance director was in the channel asking, in the polite way that means the
opposite, when the files would be back.

Priya knew the shape of the wrong answer. The wrong answer is "I'll restore it,
give me an hour," said before you know which volume holds what, because an hour
later you are explaining that the newest copy is four days old and that this is
the first anyone has heard of it. The volume in question lives in a changer in
another building and the operator who can reach it has a queue.

So the first thing she did was not a restore. She sshed to `hake`, where the
`amanda-client` package puts `amrecover`, and made a scratch directory to work
in so nothing would land on top of what was left:

```
# cd /srv/exports
# (umask 077 ; mkdir .restore)
# cd .restore
# amrecover Daily -s mora
AMRECOVER Version 3.5.1. Contacting server on mora ...
220 mora Amanda index server (3.5.1) ready.
Setting restore date to today (2026-09-22)
200 Working date set to 2026-09-22.
200 Config set to Daily.
200 Dump host set to hake.
$CWD '/srv/exports/.restore' is on disk '/srv/exports' mounted at '/srv/exports'.
200 Disk set to /srv/exports.
```

Nothing there touched a tape. `amrecover` is described in its own man page as an
index database browser that is "furthermore, able to recover files", and the
order of that sentence is the whole point. Every command up to `extract` is a
conversation with `amindexd` on the backup server, answered out of the catalogue
files under `indexdir` that the nightly run wrote there. The catalogue is a list
of paths and dates. Reading it costs a socket and a few milliseconds.

```
amrecover> cd finance/quarter-close
/srv/exports/finance/quarter-close
amrecover> ls
2026-09-21 FY26Q3-consolidated.xlsx
2026-09-21 notes.md
2026-09-18 bridge/
2026-09-18 source-extracts/
```

That was the first thing she could say in the channel, and she said it at 09:26,
with the dates in it: the spreadsheet and the notes were captured as of Monday
night, the two subdirectories as of Friday. Not "it's fine", not "I'm working
on it" — four lines of `ls` output with a date column, which is a thing a
director can act on while a sysadmin is still working.

The date column is doing more than it looks. `setdate` defaults to now, and the
listing it builds is not one backup. The man page spells out the rule: file
listing commands return information on backup images for the set day, then for
the day before at the next lower dump level, and so on, back to the most recent
level 0 on or before that date — showing only the most recent version of each
file. What `ls` printed was a Monday level 1 laid over a Friday level 0, merged
the way a restore would actually reassemble them. `history` says so plainly:

```
amrecover> history
200- Dump history for config "Daily" host "hake" disk "/srv/exports"
201- 2026-09-21 1 DMP041:7
201- 2026-09-18 0 DMP038:3
201- 2026-09-14 1 DMP036:11
200 Dump history for config "Daily" host "hake" disk "/srv/exports"
```

Date, level, volume label, file number on the volume. Two volumes back there is
a full dump; everything since is incremental. Priya could now give a number
instead of a feeling: one volume for what finance actually asked about, `DMP041`,
because the spreadsheet and the notes were both on Monday's level 1.

Then the second question arrived, the one that always arrives: legal had a share
on the same host, was that affected too, and could she pull it back while she was
in there.

```
amrecover> setdisk /srv/exports/legal
501 No index records for disk: "/srv/exports/legal". Invalid?
```

There it is in `amindexd.c`, the reply sent when `get_index_dir` finds nothing
for the DLE. The dumptype for that share had never set `index yes`, and
`amanda.conf(5)` gives that option a default of `no` — you opt in to the
catalogue, per dumptype, and nobody had. The data is on tape; the list of what
is on the tape is not. Recovering from it means `amfetchdump` or `amrestore`
pulling the whole image off the volume and looking inside afterwards.

That distinction is the reason the index exists at all, and it is easiest to see
from the side that doesn't have one. For `/srv/exports` Priya answered "is this
file in the backup, and from when" in eleven seconds from a text file on the
server. For `/srv/exports/legal` the same question costs a changer slot, a drive,
and however long it takes to stream a hundred and forty gigabytes past a tar
process — and you find out the file isn't there at the end, not the beginning.
So she told legal's manager exactly that, in those terms, and did not start it:
first confirm from the application logs whether anything was lost, because the
lookup is not free on that share.

For finance she built the restore list and, before extracting anything, wrote it
out to be read by a human:

```
amrecover> add FY26Q3-consolidated.xlsx notes.md
Added file /finance/quarter-close/FY26Q3-consolidated.xlsx
Added file /finance/quarter-close/notes.md
amrecover> add bridge
Added dir /finance/quarter-close/bridge at date 2026-09-18
amrecover> list /var/tmp/restore-4471.txt
Extract list written to file /var/tmp/restore-4471.txt
```

That file went into the ticket at 09:41 with one sentence above it: *this is
what I am about to restore, and the dates it comes from; tell me now if
`source-extracts` should be in it.* It should not have been — the director had a
newer copy of it on a laptop, and restoring Friday's over the top would have
been the second incident of the morning.

`extract` is where the cheap part ends.

```
amrecover> lpwd
/srv/exports/.restore
amrecover> extract

Extracting files using tape drive /dev/nst0 on host mora.
The following tapes are needed: DMP041
Restoring files into directory /srv/exports/.restore
Continue? [Y/n]: y
Load tape DMP041 now
Continue? [Y/n/t]:
```

Priya left that prompt sitting there and pinged the operator in the other
building with the volume label and the slot. Eighteen minutes later `DMP041` was
in the drive, she typed `y`, and the two files and the `bridge` tree came back
under `.restore`, where she diffed them against what the rsync had left before
moving anything into place.

The ticket closed at 10:37. The last comment on it was a `mv -i` of four paths
out of `.restore`, and a note that `/srv/exports/legal` still had no `index yes`
in its dumptype, filed as its own ticket for the change window.
