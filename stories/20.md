# One Filemark Too Far

*Theme: Portability*

The Solaris box had been backing up the department since before Priya joined it. It
sat in the corner of the machine room with a hand-written label on the bezel, ran
`amdump` out of cron at two in the morning, and had been declared end-of-life four
times by four different managers. The fifth one made it stick. Priya got six weeks to
move Amanda onto an Ubuntu server, and she spent most of the first one on the config.

She was careful about it. `amanda.conf` from the old server came across whole, with
the dumptypes and the tapetypes and the holding disk stanza and every comment anyone
had ever left in it. She changed exactly the things that had to change: the paths
under `/opt/csw` became `/usr`, the holding disk moved to a new LVM volume, and the
device name went from `/dev/rmt/0mbn` to the LTO drive's node on the new host.

```
define device "tapedrive" {
    comment "HP LTO-6, SAS, rear of rack 3"
    tapedev "tape:/dev/nst0"
    device-property "FSF_AFTER_FILEMARK" "true"
}
```

The first `amdump` ran clean. So did the second, and the third. The tapes came out
with the right labels, `amreport` mailed her a table with sensible numbers in it, and
`amstatus` during the run showed dumpers finishing in the order she expected. She
booked the old server's power-down for the end of the month.

What she did on the Saturday before that was `amcheckdump`, because the runbook said
to and because she had never actually watched a restore come off tape on the new
hardware. `amcheckdump` reads the images back from the volume and confirms the archive
stream is valid — its own usage text is blunt that it "does not actually compare the
data located in the image to anything". That was fine. She wanted to know the tape
could be read at all.

```
$ amcheckdump DailySet1
Reading volume DAILY-014 file 1
Validating image gantry.example.net:/etc dumped 20260918015902 level 0
Reading volume DAILY-014 file 2
header on 'DAILY-014' file 2 does not match expectations: got hostname
'nimbus.example.net'; expected 'gantry.example.net'; got disk '/srv/git';
expected '/var/lib/postgresql'
```

It went on like that. File 1 validated. Everything after it came back with the wrong
header, and the wrong header was always the one belonging to the file after the one
Amanda had asked for. At the bottom:

```
5 images failed to be correctly validated.
3 images successfully validated.
```

Besides the first, two had survived by coincidence — multi-part images where the
next part happened to sit where the seek stopped. The tape was written correctly. The
`tapelist` was correct. Amanda knew exactly which file number held which dump, asked
for that file number, and arrived one file past it every single time.

She found it in the device properties before she found it in the source.

```
$ amdevcheck DailySet1 --properties FSF_AFTER_FILEMARK
FSF_AFTER_FILEMARK=1
```

That was her own line, copied faithfully out of the Solaris config. What it means is
in `amanda-devices(7)`: the property "specifies whether the device driver needs a FSF
to go the next file after the filemark is read", and it defaults to "TRUE" on Solaris
and "FALSE" on all others machines. Two operating systems disagree about where a tape
drive is sitting after you read to the end of a file. On Solaris, reading the filemark
leaves the position on the filemark, and getting to the next file takes a deliberate
forward-space. On Linux the driver has already stepped over it for you, and if you
forward-space anyway you skip a file.

The arithmetic is eleven lines of `tape_device_seek_file` in
`device-src/tape-device.c`:

```c
    difference = file - d_self->file;

    /* Check if we already read a filemark. */
    /* If we already read a filemark and the drive automaticaly goes to the
       next file, then we must reduce the difference by one. */
    if (d_self->is_eof && !self->fsf_after_filemark) {
        difference --;
    }
```

`amcheckdump` reads image after image in file order, so every seek but the first
happens with `is_eof` set. With the property false, Amanda subtracts the file the
kernel already advanced past and asks for zero forward-spaces. With it true, it asks
for one, and lands a file too far — which is precisely right on the old box and
precisely wrong on the new one.

Priya had assumed the line was a local fix for the DAT drive the department used in
2011. It was not local to anything. On the Solaris server it agreed exactly with what
`configure` had already compiled in; `config/amanda/defaults.m4` sets
`DEFAULT_FSF_AFTER_FILEMARK="FALSE"` and then switches it to `"TRUE"` for
`*-solaris*` hosts, and nothing else. The line had sat in that file for years doing
nothing at all, because it said the same thing the binary already believed. Carried
across to a Linux build, the same six words became an instruction to contradict the
platform.

Amanda has the property because the platform alone is not a reliable answer. The
ChangeLog entry from 21 April 2009, Jean-Louis Martineau, adds `FSF_AFTER_FILEMARK` to
the tape driver and, in the same commit, adds `-p` to `amtapetype` — "New -p option to
discover driver properties, it can find value for the 'FSF_AFTER_FILEMARK' property."
The configure-time default is a guess good enough for most drives on most kernels; the
`-p` run is how you settle it for the drive actually in the rack. It is a destructive
test — it labels the volume `TEST-001` and writes files to it — so Priya put in the
scratch LTO and ran it there.

```
$ amtapetype -p DailySet1 tape:/dev/nst0
Checking for FSF_AFTER_FILEMARK requirement
device-property "FSF_AFTER_FILEMARK" "false"
```

The line it prints on stdout is shaped to be pasted into `amanda.conf`, which she
appreciated. Her first instinct had been to leave the inherited stanza alone and add
a line below it putting the property back to whatever the Linux build had chosen, and
`amanda-devices(7)` is explicit that this is not a thing you can write: "There is no
way to reset a device property to its default value." Properties take values, and
`false` is a value; *the compiled-in default* is not one. That left deleting her line
or replacing it with the measured answer.

She replaced it, on the grounds that the next person to move this configuration
somewhere else deserved a line that had been tested rather than inherited, and left
the drive model and the date of the `amtapetype` run in the comment above it.

```
$ amcheckdump DailySet1
Reading volume DAILY-014 file 1
Validating image gantry.example.net:/etc dumped 20260918015902 level 0
Reading volume DAILY-014 file 2
Validating image gantry.example.net:/var/lib/postgresql dumped 20260918015902 level 0
...
All images (8) successfully validated
```

The old server went off the floor eleven days later, and Priya added a line to the
migration runbook under *after first successful amdump*: run `amcheckdump`, and read
the file numbers.
