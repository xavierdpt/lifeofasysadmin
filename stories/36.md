# Every Visitor Was 172.18.0.1

*Theme: Isolation boundaries*

The hosting provider's graph showed the shop's egress stepping up on Tuesday afternoon and staying up. It wasn't alarming yet, but it was enough for Tamsin to open a terminal on the VM and ask who was downloading all of it.

Her first try was the obvious one. The Apache container wrote its access log to a bind mount, `/srv/shop/logs/access.log` on the host, so she added up the bytes column per client:

```
$ sudo awk '{b[$1]+=$10} END {for (h in b) print b[h], h}' \
    /srv/shop/logs/access.log | sort -rn | head -3
2148771302 172.18.0.1
3981204 172.18.0.4
```

That total ran from midnight, when the log had last rotated, so it answered "today" rather than "now". It was also, if she read it straight, a claim that one client had pulled two gigabytes and nobody else had pulled anything. She put that down to the awk and reached for the tool that answers "now".

`apachetop` was already on the host, in `/usr/sbin`, left over from before the shop moved into containers. It reads Apache's access log in common or combined format as lines are appended and keeps a moving table of recent hits, sorted like `top`. The table is either the last N hits (`-H`) or the last N seconds (`-T`). The default window is 30 seconds, which is what the README means when it calls the recent-hits lines good for "what is my server doing *right now*". Tamsin wanted ten minutes:

```
$ sudo apachetop -f /srv/shop/logs/access.log -T 600
```

It opens the file and seeks to the end, so it only counts hits that arrive after it starts. She got coffee. When she came back, the header had filled in:

```
last hit: 14:02:51         atop runtime:  0 days, 00:11:04             14:02:52
All:         4873 reqs (   7.3/sec)        98.1M (  151.3K/sec)      20.6K/req
2xx:    4410 (90.5%) 3xx:     301 ( 6.2%) 4xx:   160 ( 3.3%) 5xx:     2 ( 0.0%)
R (600s):    4390 reqs (   7.3/sec)        88.4M (  150.9K/sec)      20.6K/req
2xx:    3968 (90.4%) 3xx:     279 ( 6.4%) 4xx:   141 ( 3.2%) 5xx:     2 ( 0.0%)
```

The table underneath starts out listing URLs. Pressing `d` cycles it to hosts, then to referrers, then back again. The hosts view is the one the README sells for her exact question: "So you can see how much bandwidth is being used by any given IP." She pressed `d` once.

```
 REQS REQ/S    KB KB/S HOST
 4350  7.25 90460  151*172.18.0.1 [172.18.0.1]
   40  0.07  12.4  0.0 172.18.0.4 [172.18.0.4]
```

It was the awk result again, this time live. Every customer, crawler and bot using the shop in the last ten minutes had been folded into one row.

`apachetop` has no idea who connected to anything. `CommonLogParser::parse` in `log.cc` takes whatever comes before the first space on each log line and treats it as the host. If every character is a digit or a dot, the parser also files it as an IP. The screen had shown her what Apache wrote in `%h`, which in Debian's `combined` format is the first field. Apache runs with `HostnameLookups Off`, so `%h` is the address of whatever had the other end of the TCP connection. For this Apache, that was always the same thing. Nginx on the host terminated TLS and proxied to `127.0.0.1:8080`, the container's published port, and the connection into the container arrived from the host's end of the Docker bridge, `172.18.0.1`. The second row, `172.18.0.4`, was the metrics exporter. It ran in its own container on the same Compose network and connected to Apache directly.

So the log could not show her who used the bandwidth. The nginx log on the host still had the real client addresses, and nginx's default `combined` format is laid out the same way as Apache's. `-f` can be given more than once, up to 50 files, and `apachetop` merges them all into one table. She quit with `q` and started it again with both:

```
$ sudo apachetop -f /var/log/nginx/access.log \
                 -f /srv/shop/logs/access.log -T 600
```

Ten minutes later the hosts view had depth:

```
 REQS REQ/S    KB KB/S HOST
 4402  7.34 91380  152*172.18.0.1 [172.18.0.1]
 1911  3.19 61207  102 203.0.113.44 [203.0.113.44]
  388  0.65  6120 10.2 198.51.100.23 [198.51.100.23]
  214  0.36  3391  5.7 192.0.2.81 [192.0.2.81]
```

Every proxied request now appeared twice, once from each log: under its real address from nginx, and under `172.18.0.1` from Apache. The top row added up everything logged under the real addresses. `203.0.113.44` was the answer to the ticket: a crawler with a stock user agent, pulling product images at a hundred kilobytes a second. She noted the address for a rate limit and would have closed the terminal there.

She pressed `d` twice to go back to URLs, mostly out of habit, and read down the list. Tenth from the top was `/server-status`.

The exporter scraped `/server-status?auto` every fifteen seconds. `apachetop` strips query strings unless it is started with `-q`, cutting each URL at the first `?` or `&` so that one page's variants add up to one row. That put the exporter's scrapes on the `/server-status` line, and she expected forty of them in ten minutes. The row said 64.

The rows can be selected. The up and down arrows move an asterisk in the gap between the numbers and the name, `p` freezes the display so the rows stop moving under it, and the right arrow opens the selected row as its own screen. For a URL, that screen splits into the hosts requesting it and the referrers sending people there. She moved the asterisk down to `/server-status`, froze the display, and pressed right.

```
 REQS REQ/S    KB KB/S
   64  0.11 318.0  0.5 /server-status
                       HOST
   40  0.07  12.4  0.0   172.18.0.4 [172.18.0.4]
   12  0.02 152.8  0.3   172.18.0.1 [172.18.0.1]
   12  0.02 152.8  0.3   198.51.100.23 [198.51.100.23]
```

The referrer half of the screen was a single `-`, so she ignored it. The forty from `172.18.0.4` were the exporter, and each was small because `?auto` returns a few lines of plain text. The other two rows were the same twelve requests, seen once by nginx and once by Apache, and each of those responses was about thirteen kilobytes. That is the size of the full HTML page. `n` switches the number columns from requests and bytes to status classes:

```
  2xx   3xx   4xx  5xx
   64     0     0    0 /server-status
                       HOST
   40     0     0    0   172.18.0.4 [172.18.0.4]
   12     0     0    0   172.18.0.1 [172.18.0.1]
   12     0     0    0   198.51.100.23 [198.51.100.23]
```

Twelve 200s to an address on the public internet. From her laptop, off the VPN:

```
$ curl -s https://shop.example.com/server-status | grep '<h1>'
<h1>Apache Server Status for shop.example.com (via 172.18.0.3)</h1>
```

Debian's `status.conf` ships with `Require local` and a commented-out `Require ip 192.0.2.0/24` line, plus a comment saying to uncomment and change it to allow other hosts. The image in the shop's repository had taken that advice:

```apache
<Location /server-status>
	SetHandler server-status
	Require local
	Require ip 172.16.0.0/12
</Location>
```

`git blame` pointed at Rafael, from the week the exporter went in. She sent him the screenshot of the detail view. He answered within a minute: "172.16/12 is RFC 1918, it can't come from outside. Nothing on the internet has those addresses."

That was true, and it was the reason the rule had seemed safe. The trouble was with what gets compared against it. `Require ip` in `mod_authz_host` tests the request's user-agent address, `r->useragent_addr`. The same connection gives `%h` its value in the log, so the address `apachetop` had shown her in the HOST column was exactly the address the rule had checked. Every request that came through nginx arrived from `172.18.0.1`, which is inside `172.16.0.0/12`. The internet did not need a private address. Nginx connected on its behalf, and Apache saw the proxy's address.

The same `status.conf` also turns on `ExtendedStatus`, so the page listed each worker's current request, its first 63 characters, and the client. Every client on it read `172.18.0.1`.

The fix belonged on the Apache side, where the rule was evaluated. `mod_remoteip` replaces the user-agent address with one taken from a header, and it only does so when the connection comes from an address listed as a proxy. Nginx already sent the header; she checked for it before relying on it:

```nginx
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

In the image she ran `a2enmod remoteip` and added:

```apache
RemoteIPHeader X-Forwarded-For
RemoteIPInternalProxy 172.18.0.1
```

`$proxy_add_x_forwarded_for` appends the client's address to any `X-Forwarded-For` the client sent. `mod_remoteip` reads the header from the right, and it stops at the first address that is not a listed proxy. A client that sends `X-Forwarded-For: 172.18.0.4` gets its real address appended by nginx, and Apache stops on that. The exporter's direct connections carry no header and keep `172.18.0.4`. The rest of the configuration stayed as it was. `Require ip 172.16.0.0/12` now meant what Rafael had meant by it.

After the container was rebuilt, she ran `apachetop` against the Apache log alone. The hosts view filled with the same public addresses as the nginx log, and `172.18.0.1` was gone from it. She waited for a scanner to find the page again, then selected `/server-status`, pressed right, and pressed `n`:

```
  2xx   3xx   4xx  5xx
   40     0     3    0 /server-status
                       HOST
   40     0     0    0   172.18.0.4 [172.18.0.4]
    0     0     3    0   198.51.100.23 [198.51.100.23]
```

She pasted it into the ticket beneath the crawler's address and assigned the rate limit to herself.
