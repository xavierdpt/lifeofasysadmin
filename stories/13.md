# Three Names for One Binary

*Theme: Deprecation*

The cleanup started because of a list.

Wren had spent two weeks writing a builder for the department's Kubuntu 24.04
desktop image — 190 machines across four buildings, most of them running KDE
because the physics people had always run KDE and nobody had ever won that
argument. The builder ended with a lint step Wren was quietly proud of: dump
every executable path under `/usr/sbin`, ask `dpkg -S` who owns each one, and
flag anything that looked like it had outlived its purpose. Duplicates. Paths
with no man page. Names that appeared in no other package's dependencies.

The first run produced eleven lines. Ten were explicable. The eleventh was:

```
/usr/sbin/mysqld-akonadi    akonadi-backend-mysql: no manpage, duplicate of /usr/sbin/mysqld
```

Wren had been administering Linux desktops for six years and had never typed
that name.

```
$ ls -l /usr/sbin/mysqld-akonadi
lrwxrwxrwx 1 root root 6 Feb 22  2024 /usr/sbin/mysqld-akonadi -> mysqld
$ readlink -f /usr/sbin/mysqld-akonadi
/usr/sbin/mariadbd
```

Two hops. `mysqld-akonadi` is a symlink to `mysqld`, which is itself a symlink
— `mariadb-server-core` ships it, one line in `debian/mariadb-server-core.links`
reading `usr/sbin/mariadbd usr/sbin/mysqld` — to the actual MariaDB server
binary. Three names, two packages, one inode at the bottom.

So it was a ticket: remove a dead alias from the image. Wren allocated an hour.

## What the packaging says

`dpkg -L akonadi-backend-mysql` is a short list, and the symlink is the only
thing in it under `/usr/sbin`. The package's own source tree explains itself in
four lines. `debian/akonadi-backend-mysql.links`:

```
# https://bugs.kde.org/show_bug.cgi?id=399346
# implementation of
/usr/sbin/mysqld /usr/sbin/mysqld-akonadi
```

A bug number and a shrug. Next to it, `debian/akonadi-backend-mysql.maintscript`
had exactly one instruction:

```
rm_conffile /etc/apparmor.d/usr.sbin.mysqld-akonadi
```

That was the thread to pull. A maintscript that removes a conffile is a package
apologising for something it used to ship. Whatever `mysqld-akonadi` had been,
it had been an AppArmor thing, and the AppArmor thing was already gone.

## Why anyone made a second name

Akonadi is KDE's PIM storage service, and its default posture surprises people
who meet it for the first time: it starts a private MySQL server *per user*, on
a Unix socket under `/run/user/$UID`, with its data in
`~/.local/share/akonadi`. Not a shared system database with per-user schemas. A
whole separate `mysqld`, one for every logged-in person, running as them.

That is a completely reasonable design for a desktop, and it collides head-on
with how AppArmor works. AppArmor attaches policy to *paths*. The
`mysql-server` package ships a profile attached to `/usr/sbin/mysqld`, and that
profile is written for a system database: it permits `/var/lib/mysql` and the
system socket directory. It has no rule for anyone's home directory, which is
where Akonadi puts its data. The per-user server is the same program at the same
path, so it inherited that profile and was denied the one directory it needed.

There were two ways out. Loosen the system database's profile until it also
allowed every user's home directory — which is to say, delete the reason the
profile existed. Or give Akonadi's copy a different path, so it could have a
different profile.

Kubuntu picked the second, in 2008, and said so plainly in the changelog:

```
   - Add kubuntu_01_mysqldakonadi.diff ensuring that akonadiserver uses
     mysqld-akonadi instead of mysqld itself (to bypass apparmor)
```

Reading forward through `changelog` from there is watching one idea get
re-implemented every few releases as each implementation turned out to have a
cost. Jaunty and Karmic hardlinked `mysqld` to `mysqld-akonadi` in
`debian/rules` — cheap, and broken the moment the MySQL package was upgraded
and the hardlink went on pointing at the old inode. Lucid and Maverick switched
to copying the binary, which fixed that and put a second multi-megabyte
`mysqld` in every installation. Natty, March 2011, replaced the copy with a
shell script:

```
akonadi (1.5.0-0ubuntu2) natty; urgency=low

  * Use a wrapper script instead of copying mysqld to mysqld-akonadi.
    (LP: #728584)
    - Update the AppArmor profile accordingly.
```

Hardlink, copy, wrapper. Three mechanisms, one requirement: a path that was not
`/usr/sbin/mysqld`, so that `/etc/apparmor.d/usr.sbin.mysqld-akonadi` could be
a separate file with separate rules. The alias was never a different program.
It was a place to hang a profile.

## The deprecation

Focal, April 2020, one bullet in a release that mostly did other things:

```
  * Switch to using upstream provided apparmor profiles.
```

Upstream's profiles solve the same problem a different way, and the difference
is the whole story. Instead of a profile attached to a second path, upstream
ships *named* profiles — `mysqld_akonadi`, `mariadbd_akonadi` — and a rule in
the `akonadiserver` profile that names the transition explicitly. In
`apparmor/usr.bin.akonadiserver`:

```
  /usr/{,s}bin/mariadbd Px -> mariadbd_akonadi,
  /usr/{,s}bin/mysqld Px -> mysqld_akonadi,
```

`Px` means: when *this* process execs that binary, put the child in that named
profile. The confinement now depends on who did the exec, not on what the
binary was called. A `mysqld` started by systemd gets the distribution's system
profile; the same `mysqld` started by `akonadiserver` gets `mysqld_akonadi`,
which permits `owner @{xdg_data_home}/akonadi/** rwk` and
`owner /{,var/}run/user/@{uid}/akonadi** rwk` — the two things the per-user
server was being denied in the first place.

Which retires the alias. There is no longer any reason for Akonadi's database
to have its own filename, and the conffile that justified the filename is the
one `rm_conffile` deletes. What remains is a symlink, kept because AppArmor
resolves symlinks before it mediates: exec `/usr/sbin/mysqld-akonadi` and the
kernel matches policy against `/usr/sbin/mariadbd`, which is covered by the
`mariadbd` rule above. The old name still works, and it works by being
indistinguishable from the new one.

## Who never answered the email

Wren's hour was nearly up and the ticket still said "remove". The remaining
question was who would notice.

Akonadi keeps its database settings in `~/.config/akonadi/akonadiserverrc`, and
`README.Debian` documents the field:

```
  ServerPath=    ; absolute path to the mysqld executable,
                 ; defaults to /usr/sbin/mysqld, internal server only
```

Defaults to. Wren ran the grep across the NFS home directories:

```
$ grep -l 'ServerPath=/usr/sbin/mysqld-akonadi' /home/*/.config/akonadi/akonadiserverrc | wc -l
34
```

Thirty-four accounts, out of about ninety that had ever started Akonadi. All of
them old — accounts created before 2020, carried forward through three release
upgrades and at least one hardware refresh. Nobody had typed that path. Akonadi
had written it for them, because `DbConfigMysql::init()` resolves the server
path at first start and then persists whatever it resolved:

```cpp
    if (storeSettings) {
        // store back the default values
        settings.beginGroup(driverName());
        ...
        if (!mMysqldPath.isEmpty()) {
            settings.setValue(QStringLiteral("ServerPath"), mMysqldPath);
        }
```

On a Kubuntu machine in 2017, what it resolved was the wrapper script, and the
wrapper script's path went into the file and stayed there. The deprecation
notice, such as it was, went out in a changelog in 2020 to an audience of
config files, which do not read changelog entries and do not reply.

The rest of `init()` decided the ticket, though. Twenty lines above the write-back:

```cpp
    if (mInternalServer && (mMysqldPath.isEmpty() || !QFile::exists(mMysqldPath))) {
        mMysqldPath = defaultServerPath;
    }
```

If the configured path has stopped existing, Akonadi substitutes the one it
found by search — and then, three lines later, writes the new one back. Delete
the symlink and those thirty-four files repair themselves on the next login,
silently, one at a time. The alias is load-bearing for exactly one startup per
stale config.

Wren closed the ticket as *keep*, for a duller reason than any of that: `dpkg`
owns the symlink. Deleting it from the image would make `dpkg --verify` unhappy
on 190 machines and the next `akonadi-backend-mysql` upgrade would put it back
anyway. The lint rule got an exception with a four-line comment and the two
changelog quotes.

The last thing Wren did was check what was actually running. On a test account,
after logging in and waiting for KMail to settle:

```
$ pgrep -af mariadbd | head -1
3104 /usr/sbin/mysqld-akonadi --defaults-file=/home/test/.local/share/akonadi/mysql.conf --datadir=/home/test/.local/share/akonadi/db_data/ ...
$ cat /proc/3104/attr/current
mariadbd_akonadi (enforce)
```

The process was started under a name retired four years ago, from a config file
written before the retirement, and was confined by a profile named after
neither — `mariadbd_akonadi`, because that is where the symlinks land. Three
names, one binary, and the only one that mattered was the one nobody had typed.
