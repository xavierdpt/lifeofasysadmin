# What the dead processes said

*Theme: Attack suspicion*

The egress alert fired at 02:41, again at 03:12 and again at 03:58. Each time it was the same host, `web-07`, opening a TCP connection to `203.0.113.77` on port 443. The address was on no allowlist and had never appeared in that host's flow logs before. The alerts went into a queue that nobody looked at until 04:15, when Tomasz came out of a different page and saw three identical lines stacked up.

By 04:20 he was on the box. It was quiet.

```
$ ss -tnp | grep 203.0.113.77
$ ps -u www-data -o pid,ppid,etime,args
    PID    PPID     ELAPSED COMMAND
  31877     912    05:47:10 php-fpm: pool legacy
  31902     912    05:46:58 php-fpm: pool legacy
  32410     912    03:02:44 php-fpm: pool shop
  32415     912    03:02:41 php-fpm: pool shop
```

There were no connections, no stray shells and nothing in `/tmp`. The machine looked exactly as it should, which is what a machine looks like twenty minutes after whatever happened on it has finished. `ps` answers "what is running now". Tomasz needed to know what had run at 02:41, and `ps` cannot answer that about something that has already exited.

This host had one tool that could. Years earlier someone had installed the `acct` package, and on Ubuntu that means the service runs `accton /var/log/account/pacct` at boot. From then on the kernel appends a fixed-size record to that file each time a process exits. It needs no daemon and no configuration, and it doesn't care whether the process was interesting.

```
$ lastcomm --user www-data --pid | head -20
sh                     www-data __         0.00 secs Tue Sep 15 03:58 49120 31877
...
sh                     www-data __         0.00 secs Tue Sep 15 02:41 48210 31877
rm                     www-data __         0.00 secs Tue Sep 15 02:41 48216 48210
.s                     www-data __         0.00 secs Tue Sep 15 02:41 48215 48210
chmod                  www-data __         0.00 secs Tue Sep 15 02:41 48214 48210
base64                 www-data __         0.00 secs Tue Sep 15 02:41 48213 48210
curl                   www-data __         0.01 secs Tue Sep 15 02:41 48212 48210
sh                F    www-data __         0.00 secs Tue Sep 15 02:41 48211 48210
```

`lastcomm` reads the file backwards, so the newest records come first. Records are written when a process exits, not when it starts, so each group reads upside down: the parent `sh` finished last and is printed first. The last two columns come from `--pid`, which works because the kernel writes version 3 records carrying the PID and parent PID. Those two numbers turn a list of names into a tree. Reading it from the bottom up, `sh` 48210 forked a child that never exec'd anything, which is what the `F` flag means. A dash command substitution around a builtin does that. Then it ran `curl` piped into `base64`, ran `chmod`, ran a program called `.s`, and ran `rm`. The 03:12 and 03:58 groups had the same shape.

The `tty` column showed `__`, meaning no controlling terminal. Nobody had typed any of this. The `S` column was empty for every line, meaning none of these processes had used superuser privileges. That was the first good news of the night, with the obvious caveat that a flag only describes the processes that left records.

Tomasz paused on `.s` and its `0.00 secs`. The firewall had seen that connection stay open for about forty seconds. But the seconds column is CPU time, user plus system, not wall-clock time, and a process sitting on a socket waiting for instructions uses almost no CPU. The number said the process was idle, not that it was short.

What made the output useful was the parent of the first `sh`: 31877. That PID was in the `ps` listing from five minutes earlier, `php-fpm: pool legacy`, a worker that had been up for nearly six hours. The shells had exited, but the process that spawned them was still running, so it had no record of its own in `pacct`. It could only be seen in `ps`. The two tools overlapped at exactly one point, and that point was the web application.

---

Now it was a question for the web logs, and the accounting timestamps told him where to look. `lastcomm` prints start times to the minute, which is enough to narrow a log search:

```
$ grep ' 15/Sep/2026:02:4[01]' /var/log/nginx/legacy.access.log | grep POST
198.51.100.23 - - [15/Sep/2026:02:41:07 +0000] "POST /tools/upload.php HTTP/1.1" 200 12 ...
```

`/tools/upload.php` was a file-manager script that should have been removed along with the legacy admin panel. A POST at 02:41:07 and a shell at 02:41 made the connection clear enough for a triage note.

Next he checked whether this had happened before tonight. The current `pacct` only went back to the previous morning's rotation. Debian's `cron.daily` job runs `savelog` on the file, keeps thirty generations, and gzips every generation older than `.0`. `lastcomm` can't read gzip. It can read standard input, though, and reading from a pipe means it can't seek, so `-f -` switches it to reading forwards. That flips the order: in the output below the oldest record comes first.

```
$ zcat /var/log/account/pacct.1.gz | lastcomm -f - --user www-data --pid
id                     www-data __         0.00 secs Sat Sep 12 23:07 20532 20531
uname                  www-data __         0.00 secs Sat Sep 12 23:07 20533 20531
sh                     www-data __         0.00 secs Sat Sep 12 23:07 20531 19966
cat                    www-data __         0.00 secs Sat Sep 12 23:07 20535 20534
sh                     www-data __         0.00 secs Sat Sep 12 23:07 20534 19966
```

Two and a half days earlier someone had asked the machine who it was and what it was, and had read a file. The parent PID no longer existed; to judge by the pattern, it had been a php-fpm worker since recycled. That was reconnaissance, followed by a patient wait and a return in the middle of the night.

It was also where the tool's limits showed. Tomasz had `cat`. He did not have the path it was given. The record has no field for arguments. It stores sixteen bytes of command name, a user, a group, a tty, the start time, and a set of resource counters. It had `curl` but not the URL, and `.s` but not the file it ran from, which `rm` had removed a moment later. The command name is whatever the process was called when it exited, which a process can change for itself. Here it was `.s`, which was careless of the attacker. The accounting file said *that* something happened, *when*, *who ran it* and *what it came from*, and nothing about what it was told to do.

The reason it looks like this is written into the fields. Process accounting didn't start as a security feature. It started as billing. The GNU accounting manual opens its preface with a joke about a Bell Labs manager who overhears Thompson and Ritchie complaining about machine load and realises users could be charged for their CPU time. The joke works because the underlying fact is true: accounting existed so the operators of shared timesharing machines could see who had used how much of the machine. That's why the record is mostly counters: user time, system time, average memory, I/O, page faults and swaps. That's also why it's written once, at exit, when those totals are final. A billing record doesn't need argv. Auditing, which does, was later built as a separate subsystem.

That design is also why it was the only witness on `web-07` that night. It costs almost nothing, it ignores what the process was doing, and it records every exit whether or not anyone thought ahead. Nobody had written an audit rule for `www-data` spawning shells, because nobody had expected `www-data` to spawn shells.

---

At 04:50 Tomasz disabled the `legacy` pool and reloaded php-fpm, which retired the worker 31877 that everything above traced back to. He blocked `203.0.113.77` and `198.51.100.23` at the edge. Before anything else touched the disk, he copied the accounting files off the host with their timestamps intact:

```
$ sudo tar -C /var/log/account -czpf /root/pacct-web-07-20260915.tgz .
$ sha256sum /root/pacct-web-07-20260915.tgz
```

The reason was the daily cron job. It would rotate `pacct` again in about ninety minutes, and in thirty days it would delete the Saturday file for good. Evidence the system discards on its own schedule has to be secured before that schedule runs.

His handover note for the morning shift listed what was known and, just as carefully, what wasn't. Known: at 23:07 on the 12th and at 02:41, 03:12 and 03:58 on the 15th, processes running as `www-data` with no terminal were spawned by `legacy` pool workers. They ran `id`, `uname`, `cat`, `curl`, `base64`, `chmod`, a binary named `.s`, and `rm`. None used superuser privileges. Not known: what `cat` read, what `.s` did while connected, or whether it left anything behind that is still running outside `www-data`. The last item was why the host was being rebuilt rather than cleaned.

At the bottom he added a line for the platform team: *acct told us which process, when and from where. For what it did, we need execve auditing on the web tier, and we didn't have it.*
