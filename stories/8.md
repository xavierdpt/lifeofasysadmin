# drwxr-x---

*Theme: Upgrade*

The ticket came in on the second Monday of term, from a first-year master's student named Léa Moreau:

> My course page at halley.phys/~lmoreau/ gives "403 Forbidden". I copied the folder layout from Marc's page and his works. Did I do something wrong?

Inès Carvalho read it twice. Halley was the department's teaching server: shell accounts for students and staff, and Apache's `userdir` module, which serves anything a user puts in `~/public_html` at `/~username/`. People had been publishing lab notes and problem sets that way for fifteen years. Over the summer Inès had moved it from Ubuntu 20.04 to 24.04 by reinstalling the system disk and remounting the RAID that held `/home`. Every existing account had come through without a complaint, including Marc's.

Léa's account didn't exist before the move. Inès had created it the previous Thursday, along with eleven others for the new intake, following the wiki runbook she had written years ago:

```
$ sudo adduser --gecos "Léa Moreau" lmoreau
info: Adding user `lmoreau' ...
info: Selecting UID/GID from range 1000 to 59999 ...
info: Adding new group `lmoreau' (1043) ...
info: Adding new user `lmoreau' (1043) with group `lmoreau (1043)' ...
info: Creating home directory `/home/lmoreau' ...
info: Copying files from `/etc/skel' ...
New password:
Retype new password:
passwd: password updated successfully
info: Adding new user `lmoreau' to supplemental / extra groups `users' ...
info: Adding user `lmoreau' to group `users' ...
```

The `info:` prefixes were new, and so was the line about the `users` group. She had noticed both on Thursday and moved on, because the account worked and Léa had logged in.

## The error log said it plainly

Her first guess was the module. A reinstall means a fresh `/etc/apache2`, and she might have forgotten `a2enmod userdir`. But Marc's page loaded, so the module was running. Her second guess was the student's files: a `public_html` created with the wrong mode, or an `index.html` saved with a restrictive umask. She went to the log instead of guessing a third time.

```
$ sudo grep lmoreau /var/log/apache2/error.log
[Mon Sep 14 09:12:40.118273 2026] [core:error] [pid 2211:tid 139862117799616] (13)Permission denied: [client 10.12.4.37:50522] AH00035: access to /~lmoreau/ denied (filesystem path '/home/lmoreau/public_html') because search permissions are missing on a component of the path
```

*Search permissions* means the execute bit on a directory, which lets a process pass through it. Apache hadn't got as far as the files. It was stuck one level up.

```
$ sudo -u www-data stat /home/lmoreau/public_html
stat: cannot statx '/home/lmoreau/public_html': Permission denied
$ ls -ld /home/lmoreau /home/mdurand
drwxr-x--- 6 lmoreau lmoreau 4096 Sep 14 09:03 /home/lmoreau
drwxr-xr-x 9 mdurand mdurand 4096 Sep  2 16:48 /home/mdurand
```

Léa's home directory was `0750`. Marc's was `0755`. Apache runs as `www-data`, which is neither `lmoreau` nor in the `lmoreau` group, so it fell into "other", and "other" had no `x`. Léa had done nothing wrong. Her `public_html` was fine. She couldn't even have seen the problem, because she could enter her own home directory.

Inès listed the lot:

```
$ stat -c '%a %n' /home/* | sort | uniq -c -w3
     12 750 /home/aberthier
     87 755 /home/abonnet
```

Eighty-seven accounts from before the reinstall, twelve from after. Nobody else from the new intake had tried to publish a page yet.

## Where the number comes from

She had typed the same `adduser` command both times, so the difference was in what `adduser` did with it. That's why `adduser` exists: it's a policy layer over the low-level tools. The package README says so directly: it's meant to make it easier "to create local system accounts in the way Debian expects them to be created". `useradd` from shadow-utils writes the `passwd` and `group` entries and does what its flags tell it. `adduser` makes the decisions a site would otherwise leave to whoever happens to be typing: which UID range, whether the user gets a private group, what goes in the new home from `/etc/skel`, which extra groups to add, and what mode the home directory gets. It reads those decisions from `/etc/adduser.conf`, so twelve accounts created by one admin come out the same as twelve created by someone else next year.

That also means a change to the policy changes every account created afterwards, without any change to the command.

The code made this concrete. Inès opened `/usr/sbin/adduser`, which is Perl. It calls `useradd` with `-d` for the home path but without `-m`, then creates the directory itself, chowns it, and chmods it:

```perl
$dir_mode = get_dir_mode();
if( !chmod ($dir_mode, $home_dir) ) {
```

`get_dir_mode` reads `DIR_MODE` from the configuration and, for `--system` accounts, `SYS_DIR_MODE`. She looked at the configuration on the new install:

```
$ grep DIR_MODE /etc/adduser.conf
# The permissions mode for home directories of non-system users.
# Default: DIR_MODE=0750
#DIR_MODE=0750
# The permissions mode for home directories of system users.
# Default: SYS_DIR_MODE=0750
#SYS_DIR_MODE=0750
```

The header at the top of the new file explains the convention: a commented-out line shows the default built into the code. So the new file set nothing, and the program defaulted to `0750`. The old system disk was still in a drawer, and a copy of its `/etc` was in the backups:

```
$ grep ^DIR_MODE /srv/backup/halley-focal/etc/adduser.conf
DIR_MODE=0755
```

The old file had an active setting, written by the package's debconf question at install time. The new one had no active setting, and the built-in default was stricter.

## hirsute, January 2021

`/usr/share/doc/adduser/changelog.Debian.gz` had the history. The entry was older than she expected. It came from January 2021, for Ubuntu 21.04:

```
adduser (3.118ubuntu5) hirsute; urgency=medium

  * Enable private home directories by default (LP: #48734)
    - Set DIR_MODE=0750 in the default adduser.conf
```

Launchpad bug 48734 was filed in June 2006, under the title "Home permissions too open": the installer was creating home directories as `755`, so every user on the system could read them. On a machine like halley, any student could `ls` and `cat` their way through any other student's home, including coursework, draft theses and the occasional `.netrc`. The bug stayed open for fourteen and a half years before Ubuntu changed the default, and later releases carried the same default under the new `SYS_DIR_MODE` too. Halley skipped 22.04, so it missed the change entirely until the summer's reinstall, where it arrived as a missing line in a file nobody diffed.

The `adduser.conf(5)` man page had even anticipated her ticket:

> Note that there are potential configurations (such as /~user web services, or in-home mail delivery) which will require changes to the default.

(The same paragraph gave the default as `0700`, which is Debian's number. Ubuntu patched the config and the code but not that sentence. She made a note to trust `AdduserCommon.pm` over the man page.)

The runbook's `--gecos` had come through the upgrade as well. It has since been renamed `--comment` to match `passwd`'s terminology, and 3.137 still accepts the old spelling without a word, which was one more reason nothing on Thursday had looked different.

## Choosing a number on purpose

The quick fix was `chmod 755` on twelve directories. Inès didn't do it, because it would have reverted exactly the thing bug 48734 had fixed, and the eighty-seven old homes now looked like the actual problem.

What Apache needs is traversal, not listing. `0751` gives "other" the execute bit without the read bit. `www-data` can walk into `/home/lmoreau` to reach `public_html`, but `ls /home/lmoreau` as another student returns `Permission denied`. The Ubuntu changelog mentioned it too: the old debconf "private homes" answer had written `0751`, and 3.118ubuntu5 tightened that to `0750` "to ensure files are truly private", because with `x` on the directory, anyone who knows or guesses a filename can still open it if the file itself is readable. For a server whose whole point was publishing from home directories, that was the trade-off she accepted. She wrote it down where the next admin would find it:

```
# /etc/adduser.conf, local change 2026-09-14, ticket #5518
# Apache userdir (~/public_html) needs www-data to traverse home directories.
# 0751 = traverse without listing. Ubuntu's default 0750 breaks /~user pages.
# Filenames that are guessed can still be opened; see ticket for discussion.
DIR_MODE=0751
```

Then she tested it with a throwaway account before touching real ones:

```
$ sudo adduser --comment "test" --disabled-password zz-modetest >/dev/null
$ stat -c '%a %n' /home/zz-modetest
751 /home/zz-modetest
$ sudo deluser --remove-home zz-modetest >/dev/null
```

She ran `chmod 751` on the twelve new homes. `/~lmoreau/` returned 200.

The eighty-seven old homes went on a separate announcement. She wrote to the department list that on Friday every home directory would change from `755` to `751`. Pages under `/~user/` would keep working. Anyone who relied on someone else browsing their home directory, rather than their `public_html`, should reply before then. Two people replied. One used a shared folder that belonged in a group directory anyway, and the other asked what `751` meant.

She closed Léa's ticket with a single line: *Not your fault. The server's defaults changed over the summer; your page works now.* Then she added a step to the upgrade checklist for the next release: diff every file in `/etc` against the one it replaced, including ones that consist almost entirely of comments.
