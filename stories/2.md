# The Account No ACI Can Touch

*Theme: Hardening and least privilege*

Finding 7 in the pentest report was three lines long, and I'd have scrolled past it if
Noor hadn't highlighted it in yellow before forwarding:

> **LDAP-03 (Medium).** `cn=Directory Manager` on `ldap01.example.net:636` accepts
> simple binds from any routed network, including the guest wireless VLAN
> (10.99.0.0/16). The server answers wrong passwords with `invalidCredentials (49)`,
> which makes online password guessing against the directory's most privileged
> identity practical from an unauthenticated network segment.

The tester hadn't got the password. They'd sat in the lobby, joined the guest Wi-Fi,
and shown that the door was there and would tell them each time a key didn't fit.

My first reply in the ticket was the one I'm least proud of: *"Easy fix — I'll add an
ACI that denies everything to Directory Manager unless `ip="10.20.0.*"`."* I had the
LDIF half-written when Noor walked over and read it off my screen.

"That won't do anything," they said. "ACIs don't apply to the root DN. That's the
point of the root DN."

I knew this, in the way you know things you've never had to act on. 389 Directory
Server checks access for every bound identity against the ACIs in the tree, except
one. The template the installer ships with says it in a comment: *"Directory Manager
has all rights on every entry by nature."* It isn't even an entry in the tree. It's a
DN and a password hash in `cn=config`, and the access control code waves it through
before looking at a single `aci` attribute. That's why it exists. It's the identity
you use when the ACIs themselves are wrong, when you've locked every other admin out,
or when the database is too broken to evaluate an ACI in the first place.

So an account that no rule can restrict can't be restricted by a rule. If you want a
fence around it, the fence has to sit somewhere the ACI engine doesn't reach, which
is the bind itself.

"There's a plugin for exactly this," Noor said. "It's been in the tree since 2012.
It ships disabled."

"Or we skip the directory entirely and firewall it," I said. "Only the bastion gets
to 636."

"Only the bastion gets to 636," Noor repeated slowly, "and then four hundred laptops
stop resolving group membership, the mail relay stops authenticating, and the wiki
login page goes blank." They pulled up a chair. "A firewall sees an address and a
port. Every client of this directory comes in on the same port as Directory Manager,
and there's no second listener just for the root DN. The packet doesn't say who it's
going to bind as until it's already inside. You can't firewall an identity."

That was true. It was also only half of it, and the half I'd been about to skip
was the other one: nothing on the guest VLAN had any business reaching the directory
at all, as Directory Manager or as anybody. Before we touched the plugin I opened a
change with the network team to drop 389 and 636 from 10.99.0.0/16 at the guest
edge. That rule would make the lobby a dead end for every account. The plugin was
for everywhere the firewall had to leave open: the server VLAN, the app hosts, the
office networks. On those, a compromised box could still reach the port as easily
as a healthy one, and it could keep guessing the one password that no ACI covered.

---

It's called the RootDN Access Control plugin, and it's already in every instance's
`dse.ldif`, set to `nsslapd-pluginenabled: off`. It hooks the one code path in
`do_bind` that handles simple binds as the root DN. It never sees anyone else, so it
can be as blunt as it likes without affecting a single application account. It
filters on five things: allowed and denied hostnames, allowed and denied IP
addresses, and a daily open/close window with a list of allowed weekdays.

The bastion host everyone uses for directory admin is `bastion01.example.net`. A
hostname felt more readable than an IP, so I started there:

```console
$ sudo dsconf corp plugin root-dn enable
Enabled plugin 'RootDN Access Control'
$ sudo dsconf corp plugin root-dn set --allow-host bastion01.example.net
Successfully changed the cn=RootDN Access Control,cn=plugins,cn=config
$ sudo dsctl corp restart
```

The plugin reads its configuration when the server starts, hence the restart. Then,
from the bastion, the bind that should have been the only one still allowed:

```console
$ ldapwhoami -x -H ldaps://ldap01.example.net -D "cn=Directory Manager" -W
Enter LDAP Password:
ldap_bind: Server is unwilling to perform (53)
	additional info: RootDN access control violation
```

On ldap01, the errors log was more candid than the client:

```
[21/Sep/2026:10:42:17.306518211 +0000] - ERR - rootdn-access-control-plugin - rootdn_check_access - client IP address could not be resolved
```

A hostname rule is a reverse DNS rule. On every root bind the plugin takes the
connection's source address, asks the resolver for its name, and compares that name
against the list. If the lookup fails, it doesn't fall back to anything. It denies.
Nobody had ever added a PTR record for the bastion, because nothing had ever needed
one. I could have added one. But then the most privileged login in the directory
would depend on whoever next edits the reverse zone, and would fail open to anyone
who can make a PTR lookup return `bastion01`. I switched to the address:

```console
$ sudo dsconf corp plugin root-dn set --allow-host delete --allow-ip 10.20.0.14
Successfully changed the cn=RootDN Access Control,cn=plugins,cn=config
$ sudo dsctl corp restart
```

From the bastion:

```console
$ ldapwhoami -x -H ldaps://ldap01.example.net -D "cn=Directory Manager" -W
Enter LDAP Password:
dn: cn=directory manager
```

Then I did what the tester had done. The guest-edge change was still waiting for the
network team's Thursday window, so the lobby could still reach the port, which for
this one test was useful. I sat on the guest Wi-Fi and tried the real password, then
a wrong one:

```console
$ ldapwhoami -x -H ldaps://ldap01.example.net -D "cn=Directory Manager" -W
Enter LDAP Password:
ldap_bind: Server is unwilling to perform (53)
	additional info: RootDN access control violation
$ ldapwhoami -x -H ldaps://ldap01.example.net -D "cn=Directory Manager" -W
Enter LDAP Password:
ldap_bind: Server is unwilling to perform (53)
	additional info: RootDN access control violation
```

Both got the same answer, and that half of the finding closed itself without my
doing anything. The check runs *before* the password is compared, and a comment in
`bind.c` says why: returning `53` for a right password and `49` for a wrong one
would still let someone brute-force a password they could never use from where they
were sitting, and then use it from somewhere else. Outside the allowlist, a guess
now tells you nothing.

---

Noor wanted to go further. "Office hours. `--open-time 0800 --close-time 1800
--days-allowed Mon,Tue,Wed,Thu,Fri`. Nobody should be binding as Directory Manager
on a Saturday."

"Somebody will be," I said. "The Saturday the directory is on fire."

That became the real argument. It's the one that always comes up when you remove
access: not whether the fence is right on an ordinary day, but whether it becomes a
wall on the one day you need to climb over it. So before anyone won, we read what
the plugin does about the local socket, because that's where we'd be standing during
an incident.

Two things in the source settled it. First, the host and IP checks are skipped
entirely when the connection arrives on the LDAPI Unix socket, since there's no
address to check. The time and day checks aren't skipped. They run first, for every
simple root bind, local or not. With Noor's window, `ldapwhoami -H
ldapi://%2frun%2fslapd-corp.socket -x -D "cn=Directory Manager" -W` at 3 a.m. on a
Sunday would be refused like anything else. The clock is compared against the
server's local time, so a host that's quietly on UTC would move the window as well.

Second, and this is the part that made the fence safe to build at all: the plugin
only sees simple binds with a password. When `dsconf corp` runs as root on ldap01,
it doesn't send a password. It connects to the LDAPI socket, and the server maps the
Unix uid on the other end, root or the `dirsrv` account, to the root DN through
autobind, a SASL EXTERNAL bind. That path never reaches the root DN simple-bind
branch in `do_bind`, so the plugin never runs:

```console
$ sudo ldapwhoami -H ldapi://%2frun%2fslapd-corp.socket -Y EXTERNAL
SASL/EXTERNAL authentication started
SASL username: gidNumber=0+uidNumber=0,cn=peercred,cn=external,cn=auth
SASL SSF: 0
dn: cn=Directory Manager
```

The code that does this mapping has its own justification written next to it: if
you're root on the machine, you could rewrite the password hash in `dse.ldif` anyway,
so trusting root over the socket gives nothing away.

So the break-glass path is `ssh` to ldap01 and `sudo`, and the plugin can't close it,
whatever we put in the time fields. That reframed the question. A time window
wouldn't lock us out during an incident, but it wouldn't add much either. The
IP allowlist already means that nobody off the bastion can get a useful answer to
a password guess, and the one person who can bypass everything needs root on the directory
host, which no plugin can defend against. We left the window off and wrote down
why.

The ticket reply I actually sent:

> LDAP-03: `cn=Directory Manager` simple binds are now restricted to 10.20.0.14 by
> the RootDN Access Control plugin (enabled, `rootdn-allow-ip`). Binds from any other
> address get `unwillingToPerform (53)` before the password is checked, so the
> response no longer distinguishes right from wrong passwords. Separately, 389/636
> are being closed to 10.99.0.0/16 at the guest edge (network change linked); the
> plugin covers the segments that must keep reaching the directory. Local administration
> on ldap01 uses LDAPI autobind as root, which this plugin does not govern by
> design; access to that path is controlled by SSH and sudo on the host.
> Time-of-day restriction considered and declined, reasoning in the linked runbook.
> Hostname-based allow rules rejected: they depend on reverse DNS and deny on lookup
> failure.

The runbook got one new line, near the top, where people look when they're
panicking: *If Directory Manager says "RootDN access control violation", you are on
the wrong host. Go to ldap01 and use `sudo dsconf corp`.*
