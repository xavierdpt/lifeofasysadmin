# Two Lines in pp.sh

*Theme: Secrets handling*

The finding came in on a Thursday with Petra's name in the blame column. The secret
scanner that security had pointed at the configuration repositories flagged a
high-entropy string in `web-etc`, the repo the Ansible role for the web hosts was
built from:

```
roles/apache/files/pp.sh:2   generic-high-entropy   'Kestrel-Harbour-Tin-4417'
```

Oluwaseun, who ran the scanner, had written one line under it in the ticket: *What
does this open?*

Petra knew without looking. The file had two lines:

```sh
#!/bin/sh
echo 'Kestrel-Harbour-Tin-4417'
```

and the Apache role deployed it to `/etc/apache2/pp.sh`, mode 0755, next to a one-line
change to `mods-available/ssl.conf`:

```apache
SSLPassPhraseDialog  exec:/etc/apache2/pp.sh
```

What it opened was `/etc/ssl/private/shop.example.org.key`, the private key behind the
TLS certificate for the shop. The key file began `-----BEGIN ENCRYPTED PRIVATE
KEY-----`. Whoever set up the shop had generated it with a passphrase, before Petra
joined the team. The passphrase had lived in the team's vault, and for eight months it
had also lived in git, readable by the forty-odd people with access to `web-etc`. She
opened the commit that had added it.

---

It was from the March patch night, and its message said *stop apache hanging on
reboot*.

She had rebooted `web01` over ssh after the kernel update, the session dropped, and
when she got back in the shop was down. The journal had it:

```
apache2.service: start operation timed out. Terminating.
apache2.service: Failed with result 'timeout'.
Failed to start apache2.service - The Apache HTTP Server.
```

The service had sat for ninety seconds, systemd's default start timeout, and been
killed. She ran `sudo systemctl start apache2` by hand, got a passphrase prompt in her
terminal, pasted the passphrase from the vault, and the shop came back. Then, at a
quarter to three, she wrote `pp.sh` so that the next reboot would not need her, and
committed it to the role so that the next Ansible run would not put the old line back.

At the time she had not looked at what prompted for the passphrase, or why the prompt
reached her terminal when she started the service by hand but not at boot. The stock
`ssl.conf` in the `apache2` package does not use mod_ssl's default, `builtin`. It
sets:

```apache
SSLPassPhraseDialog  exec:/usr/share/apache2/ask-for-passphrase
```

`builtin` is mod_ssl's own terminal dialog: Apache prints a prompt on the terminal it
was started from and reads the answer before it detaches. That works when someone
types `apache2 -k start` at a shell. Under systemd there is no such terminal, because
`apachectl start` runs with its standard input on `/dev/null`. Debian's changelog
records the fix, in `2.4.10-9` from December 2014: *Include ask-for-passphrase script
from Ubuntu with some tweaks. This fixes asking for certificate passphrases if started
via systemd. Closes: #773405.*

The helper works out whether Apache has a terminal by asking `tty` about the parent
process's standard input:

```bash
tty=`tty < /proc/${PPID}/fd/0`
if [ "$tty" = "not a tty" ] ; then
	if [ -x /bin/systemd-ask-password ] ; then
		exec /bin/systemd-ask-password --timeout=0 "$prompt"
```

If there is a terminal, it prompts there with `read -s`. If there isn't, it hands the
question to `systemd-ask-password`, which queues it for whatever password agent is
listening. When she typed `sudo systemctl start apache2` in an ssh session,
`systemctl` itself acted as the agent and asked her on her own terminal;
`systemctl(1)` describes this under `--no-ask-password`, the option that turns it off.
At boot nobody was logged in to answer.

She reproduced the boot on staging, which ran the same role with its own key and its
own passphrase. With the stock line back in staging's `ssl.conf`, she ran `sudo
systemctl start --no-ask-password apache2` in one ssh session, so that nothing on that
terminal would answer. A second ssh session to the same host got this:

```
Password entry required for 'Enter passphrase for SSL/TLS keys for shop-staging.example.org:443 (RSA):' (PID 1187).
Please enter password with the systemd-tty-ask-password-agent tool.
```

That came from `systemd-ask-password-wall.path`. She ran `sudo
systemd-tty-ask-password-agent` in the second session, typed staging's passphrase, and
the `systemctl` command in the first one returned.

---

Before replying to Oluwaseun she tried the `exec:` interface on staging. `mod_ssl`'s
documentation says the program is called with two arguments, `servername:portnumber`
and the key type, and that whatever it prints on standard output is the passphrase.
She put a copy of `pp.sh` there, echoing staging's passphrase, with a line in front
that recorded what it was given:

```sh
#!/bin/sh
logger -t pp "called with: $*"
echo 'staging-Wren-0921'
```

and added `ssl:info` to the log level:

```apache
LogLevel warn ssl:info
```

A `sudo systemctl restart apache2` produced this in the journal:

```
pp[2291]: called with: shop-staging.example.org:443 RSA
```

and this in the Apache error log:

```
[ssl:info] [pid 2288] AH01969: Init: Requesting pass phrase from dialog filter program (/etc/apache2/pp.sh)
```

Then she ran `sudo systemctl reload apache2`. That did not call `pp.sh`, and the error
log showed:

```
[ssl:info] [pid 2288] AH02575: Reusing existing private key from /etc/ssl/private/shop-staging.example.org.key on restart
```

In `ssl_engine_pphrase.c`, on a graceful restart, mod_ssl keeps the key it already
decrypted if the key file's modification time hasn't changed, and a comment there says
this is done for `exec:` and pipe dialogs "to minimize chances to snoop the password".
So a reload for a config change never asks. A new key file does, and so does a cold
start of the process, which on `web01` meant a reboot.

She also read `ssl_util_readfilter`, which takes the program's output one byte at a
time and stops at the first newline. That was why `ask-for-passphrase` carries the
comment *We must not print anything on stdout except the passphrase*.

The mod_ssl documentation gives the intent: "that this external program first runs
security checks to make sure that the system is not compromised by an attacker, and
only when these checks were passed successfully it provides the Pass Phrase." It adds:
"Both these security checks, and the way the Pass Phrase is determined, can be as
complex as you like." `pp.sh` used the interface, but it put no check in between.

---

"The encrypted key goes where `/etc/ssl` goes," Oluwaseun said, when Petra brought the
notes over. "Nightly backups, the VM snapshots, the image we cloned `web02` from. The
passphrase is meant to stay out of all of those. Is `/etc/apache2` in the same
backups?"

It was. Since March, every backup that held the encrypted key had also held `pp.sh`.
As far as Petra could tell the key file itself had never been committed to `web-etc`,
but every backup of `web01` since the shop was set up had a copy, and the backup
server had its own list of readers.

"So a backup from after March has the key and its passphrase together," Oluwaseun
said. "And the repo plus any older backup does too. Deleting `pp.sh` doesn't take it
out of git history. Rotate it."

They agreed on the rest in ten minutes. A new key and certificate for the shop, with
the old one revoked. A new passphrase, in the vault only. `pp.sh` removed from the
role, and the stock `SSLPassPhraseDialog` line restored. They also talked about
dropping the passphrase altogether: the Apache SSL FAQ gives the `openssl rsa` command
for it, with the warning that it "removes a layer of security from your server", and
in the backups an unencrypted key would have been exposed the same way as the
encrypted one with `pp.sh` beside it. They kept the passphrase, because the shop could
stay down for the few minutes after a planned reboot, and the reason to encrypt the
key was that its file went into backups.

The patch-night runbook got a new step after the reboot of `web01`: *log in, run `sudo
systemctl start apache2`, enter the passphrase from the vault at the prompt.*

In April Petra rebooted `web01` at ten past two, waited for ssh, and typed the
command. `systemctl` asked for the passphrase for `shop.example.org:443 (RSA)` on her
terminal. She pasted it, and the shop's health check went green at 02:13.
