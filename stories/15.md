# Segfault at 128 kilobytes

*Theme: Portability*

The bug report was four lines long and ended with a core dump. Someone packaging
`indexd` for Alpine had run the test suite and watched it die in
`indexd --reindex`, every time, at the same place. On the project's own CI — Ubuntu
24.04, the same suite, the same commit — it had been green for eleven months.

Teodora had the reporter's exact command, the reporter's exact version tag, and no
Alpine machine. The build fleet was Ubuntu. The laptop was Ubuntu. The container
runtime on the runners had been taken away in the spring for reasons nobody had
written down, which meant `docker run -it alpine` was not the two-second answer it
would have been the year before.

## Five seconds

What she did have was `alpine-chroot-install`, which a colleague had left in the
repo's `ci/` directory years earlier with no comment beyond the URL it came from.
It is a single POSIX shell script. It does not need Docker, and it does not start
from a prebuilt rootfs image; it downloads `apk.static` — Alpine's package manager,
built as one static binary — verifies it against a SHA-256 checksum baked into the
script, writes out the Alpine signing keys it also carries inline, and then lets
`apk` install a base system into a directory the same way `apk` would install into
`/`. That is the whole trick, and the README's claim for it is five seconds from
nothing to a chroot with a working compiler.

The script exists because CI services hand you one distribution and no root over
the image. Travis gave you Ubuntu; if what you shipped was a musl binary, your
options were to trust that it worked, to keep a machine of your own somewhere and
push to it, or to assemble a rootfs by hand with `debootstrap`'s Alpine-shaped
cousin, which is not a thing that exists. `alpine-chroot-install` is the fourth
option, and it needs nothing from the host but root, a shell, and `curl` or `wget`.

Her first attempt was impatient:

```
$ sudo ci/alpine-chroot-install -p build-base -p cmake
ERROR: Please specify where to install to (such as -d /alpine)
```

Fair. With `-d`:

```
$ sudo ci/alpine-chroot-install -d /alpine -p build-base -p cmake

> Downloading static apk-tools
fetch https://gitlab.alpinelinux.org/api/v4/projects/5/packages/generic/v2.12.10/x86_64/apk.static
apk.static: OK

> Installing Alpine Linux latest-stable () into chroot
...
> Binding filesystems into chroot
mount: none mounted on /alpine/proc.
mount: /sys bound on /alpine/sys.
mount: /dev bound on /alpine/dev.
mount: /home/teodora/src/indexd bound on /alpine/home/teodora/src/indexd.
```

That last line was not something she had asked for. The script binds the current
directory into the chroot at the same path when the current directory is somewhere
under `/home`, and the comment in the source is refreshingly blunt about why: it
was convenient on Travis, every existing `.travis.yml` came to depend on it, and so
it stays. She read it twice, decided she wanted it today, and made a note to pass
`-i` explicitly in anything she committed.

The chroot came with an `enter-chroot` script in its root. Running the build was
one line:

```
$ /alpine/enter-chroot -u teodora sh -c 'cd src/indexd && make && ./indexd --reindex'
```

It segfaulted on the first run.

## What the two libcs disagree about

`enter-chroot` does more than `chroot`. It scrapes the environment variables whose
names match `CHROOT_KEEP_VARS` — by default `ARCH`, `CI`, `QEMU_EMULATOR` and
anything starting with `TRAVIS_` — into an `env.sh`, then runs
`chroot . /usr/bin/env -i su -l "$user"` and sources that file back on the other
side. The `env -i` is the point: you get the target system's environment rather
than a smear of the host's. It also cost Teodora ten minutes, because `indexd`'s
makefile reads `BUILD_TAG` and inside the chroot `BUILD_TAG` was empty. Adding
`-k BUILD_TAG` to the install line put it back.

With the build reproducing, `gdb` was already available — `apk add gdb` into a
chroot is the same command it is anywhere — and the backtrace pointed at the
worker thread that parses a segment header. That function declares a 96 KiB buffer
on the stack. On glibc a thread gets 8 MiB by default, the same as the main
thread's `ulimit -s`, and a 96 KiB frame is invisible. musl's number is in
`src/internal/pthread_impl.h`:

```c
#define DEFAULT_STACK_SIZE 131072
#define DEFAULT_GUARD_SIZE 8192
```

128 KiB, with an 8 KiB guard page under it. The buffer plus the frames around it
crossed the guard page, and the guard page did exactly what it is there for.

The fix had two shapes. `pthread_attr_setstacksize()` on the attribute used to
create the worker is the explicit one. The other is a link flag: musl reads the
`PT_GNU_STACK` program header at startup and raises its default thread stack to
`p_memsz`, capped at `DEFAULT_STACK_MAX`, which is 8 MiB — so
`-Wl,-z,stacksize=1048576` moves the default for every thread in the binary
without touching the code. `indexd` took the first, because the buffer was
one function's business and the reviewers wanted it to say so.

## The second report

A week later the same bug tracker produced an armhf build failure from someone
running Alpine on a Raspberry Pi. Teodora had no ARM hardware either. The script's
other half handles that: `-a armhf` installs the chroot for a foreign
architecture, and when the requested architecture differs from `uname -m` it
checks for `/usr/bin/qemu-arm-static` and `/proc/sys/fs/binfmt_misc/qemu-arm`,
installs `qemu-user-static` and `binfmt-support` with `apt-get` if either is
missing, and copies the emulator binary into the chroot so the kernel can find it
after the `chroot`.

```
$ sudo ci/alpine-chroot-install -d /alpine-armhf -a armhf -p build-base -k BUILD_TAG
```

It ran slower than the native one by a wide margin and it worked. The README warns
that Alpine's binaries need a recent QEMU and that `qemu: Unsupported syscall` is
the symptom of one that is too old, with `-b v3.11` as the fallback to an older
Alpine branch; the runner's QEMU was new enough that she never found out.

Tearing down is the chroot's own `destroy` script, which walks `/proc/mounts` in
reverse order and unmounts everything under itself before it will consider
deleting anything:

```
$ sudo /alpine/destroy --remove
Unmounting /alpine/home/teodora/src/indexd
Unmounting /alpine/dev/pts
...
Removing /alpine
```

Teodora added twelve lines to `.github/workflows/test.yml`: install the chroot at
`/alpine` with `-i "$GITHUB_WORKSPACE"` and `-k BUILD_TAG`, run the suite through
`enter-chroot`, then `/alpine/destroy -r`. The armhf job she marked
`continue-on-error: true` for a month, to see how often the emulation flaked
before anyone was allowed to gate a merge on it. The packager who filed the
original report got a link to the workflow file and closed the issue themselves.
