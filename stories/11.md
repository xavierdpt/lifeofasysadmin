# Sixty-four minutes and a few seconds

*Theme: Heisenbug*

The health post at Saint-Aubin-les-Combes has one telephone line, and it is not a line. It is a grey analogue adapter under the reception desk, plugged into a rooftop router, which talks by radio to another rooftop router on the bakery, which talks to the one on the church tower, and so on down the valley, eleven hops in all, to the only wired internet connection for twelve kilometres, in the back room of the cooperative dairy.

In May 2012, Solène, the nurse who ran the post, started keeping a list on the back of a prescription pad. Every time a call dropped she wrote down the time. She handed the list to Bastien Morel, who looked after the mesh on weekends, as if it were a symptom chart. In a way it was.

```
mardi   09:14   11:21   12:26
mercredi 10:02  11:07   14:44 (?)
jeudi   08:51   09:56   11:00   12:05
```

"About once an hour," she said. "But not on the hour. And some days it leaves us alone all afternoon."

---

The mesh existed because nothing else would reach the upper hamlets. Twenty-three small routers ran the same image. Each one had babeld for routing and ahcpd for addressing, both started from `/etc/rc.local`:

```
babeld -D wlan0 eth0
ahcpd -D wlan0
```

Bastien had not chosen ahcpd. The volunteer who built the first image had, in the autumn of 2011, and had left a note in the image's README explaining why. The note was more useful than most:

> Don't try to put dnsmasq on the dairy box and expect it to work. A DHCP
> DISCOVER is a link-layer broadcast. On the mesh it reaches the routers
> that can hear the one sending it, i.e. one hop. The dairy is eleven hops
> from the health post. You can put a relay on every node, but the relay
> needs a route to the server, and the node needs an address before babel
> will give it one. Router advertisements have the same problem: they
> assume everyone on the link shares a prefix, and a mesh is not one link.

The ahcpd README says the same thing in one line: AHCP "is designed for wireless mesh networks, where DHCP and IPv6 autoconfiguration do not work". The way it gets around the problem is to carry its own flooding layer. A new node sends a DISCOVER to the link-local group `ff02::cca6:c0f9:e182:5359` on UDP port 5359 with a hop count of one. Every ahcpd that hears it, on any node, drops duplicates, decrements the count and re-sends it on its own interfaces. If no server answers, the client tries again with a count of two, then three, a ring that widens across the valley until it reaches the dairy. The server there had a short configuration:

```
mode server
prefix fd4b:6e1a:2c07:1::/64
prefix 10.42.0.0/24
lease-dir /var/lib/ahcpd/leases
name-server 10.42.0.1
ntp-server 10.42.0.1
```

The answer comes back along the same flood, and the config script turns it into addresses. There is no netmask and no default gateway in AHCP. The man page says those are left to "a full-fledged routing protocol", so the script gives the node its addresses as host routes and babel handles everything else:

```
root@sante:~# ip addr show dev wlan0 | grep inet
    inet 10.42.0.37/32 scope global wlan0
    inet6 fd4b:6e1a:2c07:1:21a:2bff:fe17:9c04/128 scope global
    inet6 fe80::21a:2bff:fe17:9c04/64 scope link
```

The node NATs its wired side, where the phone adapter lives, out through that `/32`. Nothing about any of this had changed since November.

---

Bastien's first theory was radio. The church-tower link was the weakest in the chain, and a drop once an hour could plausibly be the bell-ringing mechanism, a tractor or a microwave. He drove up on a Saturday with a laptop, logged into the health post's router, and did what he always did to see what a daemon was thinking. He stopped it and ran it in the foreground at a higher debug level:

```
root@sante:~# kill $(cat /var/run/ahcpd.pid)
root@sante:~# ahcpd -d 2 wlan0
```

He watched the hop count on its DISCOVERs climb, one, two, three, until the eleventh reached the dairy, and then watched it settle into state 5. Then he rang the post's number from his mobile, and Solène put him on speaker next to the fridge. They talked about her garden for forty minutes. The call held, and the log showed packets forwarded for other nodes but no change of state. He decided it was the radio after all, restarted the daemon properly, and went home.

The next Tuesday the list read 10:48, 11:53, 12:57.

He tried again the following weekend and changed the channel on the church link. For good measure he rebooted the health-post router, whose uptime was nineteen days. That afternoon was clean. So was the evening. Monday morning started again at 08:40.

Looking back, this was the part that made the problem feel malicious. Every time Bastien went to look, it stopped. He rebooted the node and it stopped, and when he sat and watched the daemon it stopped again. It came back as soon as he stopped paying attention, never at the same minute twice.

---

It was Solène's list that gave him the pattern. Bastien typed it into a spreadsheet one evening, mostly to feel he was doing something. Then he added a column with the difference between consecutive drops on the same day:

```
09:14 → 11:21   2h07
11:21 → 12:26   1h05
08:51 → 09:56   1h05
09:56 → 11:00   1h04
11:00 → 12:05   1h05
```

A two-hour gap was a missed entry: Solène was not always on the phone. The rest were sixty-four or sixty-five minutes apart. That interval could not come from a tractor. It looked like a timer.

He opened `/var/log/ahcpd.log` on the node. He had looked at it before and found it unhelpful, because ahcpd's debug output goes straight to stderr through `vfprintf` without timestamps. At the default debug level of 1, the useful lines were these, repeated all the way down the file:

```
Running ``/etc/ahcp/ahcp-config.sh start''
Running ``/etc/ahcp/ahcp-config.sh stop''
Running ``/etc/ahcp/ahcp-config.sh start''
Running ``/etc/ahcp/ahcp-config.sh stop''
Running ``/etc/ahcp/ahcp-config.sh start''
```

He had always read each stop/start pair as a restart, whether his own or a reboot after a power cut. He counted them this time. Since the reboot six days earlier there were a hundred and thirty-four pairs, twenty-two a day, and the router's uptime said it had not restarted once.

He stopped restarting things. The daemon had been running unobserved since his last reboot, and he wanted to see its state without disturbing it. ahcpd answers `SIGUSR1` by printing its status into the same log. He left it running, added the timestamps the log lacked, and asked it every few minutes:

```
root@sante:~# tail -f /var/log/ahcpd.log | while read l; do echo "$(date +%T) $l"; done &
root@sante:~# while sleep 120; do kill -USR1 $(cat /var/run/ahcpd.pid); done &
```

Most of the reports looked sensible. The countdown fell by about a hundred and twenty seconds each time, from a lease of a little over an hour:

```
14:31:07 Forwarder forwarding.
14:31:07 Client in state 5, server selected, configuration valid for 1925s (originally 3874s since 1336651118).
```

At 14:52 the lease was five-sixths used, and the client renewed it with a REQUEST sent straight to the server. At debug level 1 that leaves no line in the log, but the next report showed it, and it was the one he printed out and taped above his desk:

```
14:53:08 Client in state 5, server selected, configuration valid for 604s (originally 3871s since 1336654346).
```

A lease of 3871 seconds, granted less than a minute earlier, had ten minutes left. The "since" figure had moved forward to the renewal, but "valid for" was still counting down to the old deadline. Ten minutes later:

```
15:03:12 Running ``/etc/ahcp/ahcp-config.sh stop''
15:03:13 Running ``/etc/ahcp/ahcp-config.sh start''
```

Solène's list for that day read 15:03.

---

The source settled the rest. Bastien had the 0.52 tarball the image was built from, and `configure.c` is short enough to read on a train. When a client receives an ACK while it already holds a configuration, and the new configuration is compatible with the old one (same addresses, same prefix), it doesn't re-run the script. It copies the new timing onto the existing lease:

```c
        } else {
            config_data->origin = config->origin;
            config_data->origin_m = config->origin_m;
            config_data->expires = config->expires;
        }
```

These are the start of the lease in real time, the start in monotonic time, and its length. The renewal time is computed from them, as `origin_m + expires * 5 / 6`, so renewals happened on schedule. The fourth field, `expires_m`, is the monotonic deadline, and it was left as it was. The main loop in `ahcpd.c` checks exactly that field:

```c
        if(config_data) {
            if(now.tv_sec >= config_data->expires_m) {
                unconfigure(interfaces);
                server_hopcount = 0;
                SWITCH(STATE_INIT);
            }
        }
```

So each node got its lease, renewed it at fifty-four minutes, and ten minutes later reached the deadline of the lease it had already replaced. `unconfigure()` ran the script with `stop`, which ran `ip addr del` on both addresses and put the old `resolv.conf` back. The client went back to searching. The server was still holding its lease, so within a second or two it got the same address back and ran `start`.

For a web page, a gap of a second or two is a retry nobody notices. A phone call is different. The adapter's call was NATed out through `10.42.0.37`, and when that address disappeared, the kernel threw away the masquerade state it had built on it. The voice stream came back from the far end addressed to a mapping that no longer existed. The call was dead before the address returned.

The pattern of the list made sense now too. The period was one lease length, about sixty-four and a half minutes, which is why the drops drifted a few minutes later every hour instead of landing on the hour. Each node ran its own cycle, starting from whenever it had last bound. That explained why every one of Bastien's observations had fixed it. Killing the daemon made it release its lease and unconfigure, and a restart or a reboot bound a fresh one, which gave a clean hour. He had watched each clean hour for forty minutes and gone home.

The upstream history had the fix, dated 8 December 2011, three weeks after the image was built:

```
commit 70ffd95723a5929bcd1aa164b21849df9aa10c51
    Update expires_m when renewing a lease.

    This is a long-standing bug that would cause a client to immediately
    deconfigure itself after successfully renewing a lease.

+            config_data->expires_m = config->expires_m;
```

It was released as ahcpd 0.53, and the CHANGES file lists it first. Nobody had rebuilt the image, because on a mesh carrying web browsing and email a two-second outage every hour doesn't show. It showed only once a long-lived call started crossing a NAT at the edge of it.

---

Bastien cross-compiled 0.53 the way the README describes (`make CC=mipsel-linux-gcc PLATFORM_DEFINES='-march=mips32'`) and flashed the health post first, on a Saturday night. On Sunday he left the timestamping loop running and didn't touch anything. The renewal at fifty-four minutes was followed by a report he checked twice:

```
Client in state 5, server selected, configuration valid for 3748s (originally 3872s since 1336917503).
```

By the following weekend all twenty-three nodes were on 0.53. Solène kept the prescription pad by the phone for another month. The last entry on it was a Thursday, 11:40: a storm, and the church link went down for real.

Bastien kept one habit from those weeks. When a problem only showed itself while nobody was looking, the first thing he checked was whether his way of looking restarted the thing. Before he rebooted or restarted anything, he asked the daemon for its state and wrote the time next to the answer.
