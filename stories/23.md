# A tab, a space, and the word prod

*Theme: Hardening and least privilege*

Every app server in the account runs on one launch template and one instance role,
`AppServerInstance`. When the access review got to that role, the statement that
stopped me was four lines long.

```json
{
  "Effect": "Allow",
  "Action": "ec2:DescribeTags",
  "Resource": "*"
}
```

The `"*"` is not laziness. `ec2:DescribeTags` takes no resource constraint — there
is no way to write a policy meaning "this instance may read its own tags". Grant it
and you have granted every tag on every resource in the account: the owner's email
address, the cost centre, the ticket the box was built for, and on about forty
instances a tag called `Runbook` holding an internal wiki URL. Anything with a shell
on any app server could read all of it.

That permission was not decoration. It was there for `/usr/local/bin/deploy-config`,
which begins:

```bash
IID=$(ec2-metadata -i | cut -d' ' -f2)
ENV=$(aws ec2 describe-tags \
        --filters "Name=resource-id,Values=${IID}" "Name=key,Values=Environment" \
        --query 'Tags[0].Value' --output text)
```

An instance that wants to know which config to pull has to find out what it is, and
what it is has been written down exactly once, on a tag. The instance id it can get
locally — `ec2-metadata` is on every box, from `amazon-ec2-utils`, and reads that
off the link-local metadata address. But to turn the instance id into the tag, the
script made a signed API call across the internet, with credentials, to ask Amazon a
question about itself. That round trip is what the policy statement paid for.

So the review turned into a question: can the box learn its own `Environment`
without holding a key to everyone else's tags?

It can, and the answer was in a man page already installed on all of them. From
`ec2-metadata(8)`:

```
       -t/--tags
              Print EC2 resource tags if permitted in EC2 Instance Metadata
              Options.
```

Tags are served over `169.254.169.254` alongside the instance id and the AMI id.
No credentials, no API call, no IAM permission — the metadata service already knows
which instance is asking, because of which instance it is answering. The whole
awkwardness of `DescribeTags` is that it has to be told who you are and then decide
whether to believe you; the metadata service is on the other side of that problem.

The qualifier in the man page is the hardening: *if permitted in EC2 Instance
Metadata Options*. Tags in metadata are off by default and enabled per instance, so
an account that has not asked for this is not quietly handing tags to every process
on the box.

I enabled it on one staging instance to see what came back:

```
$ aws ec2 modify-instance-metadata-options \
    --instance-id i-0d4f1a6c9e2b7a350 --instance-metadata-tags enabled
$ ec2-metadata -g
tags:
	 Environment: staging
	 Owner: platform
	 Runbook: https://wiki.internal/rb/appserver
```

`-g`, not `-t`. The man page in 2.1.0 gives the short option as `-t`, but `-t` is
`--instance-type` and always has been; the script's `getopt` string spells tags `g`.
I found that out by typing the documented letter and getting `instance-type:
m6i.large` back.

Underneath, `ec2-metadata` is doing the IMDSv2 handshake on my behalf: a `PUT` to
`/latest/api/token` carrying `X-aws-ec2-metadata-token-ttl-seconds: 900`, then that
token on the header of every `GET` that follows. Fifteen minutes of token, fetched
fresh each run. Keeping the tool rather than hand-rolling `curl` in the deploy script
meant one place for that to be wrong instead of nine.

The replacement line for `deploy-config`:

```bash
ENV=$(ec2-metadata --quiet -g | awk '$1 == "Environment:" {print $2}')
```

The `awk` is not decoration either. `--quiet` is documented as "don't print metadata
keys", and for `-i` or `-z` it does that. For `-g` it drops the `tags:` header and
then prints each tag as `\t Environment: staging` anyway — the loop inside
`print_tags` is the one printer in the file that never checks `$QUIET`. There is no
way to ask for a single tag by name, so the script parses a list either way.

Rolling it out, the order mattered, because getting it wrong is quiet. On an instance
where metadata tags are still disabled, the path under `meta-data/tags/instance/`
returns nothing and `print_tags` prints:

```
tags:
not available
```

That is also what it prints for an instance that has no tags at all. When the second
box I tried came back `not available` I spent twenty minutes sure the feature was
missing in the region, and it was not: I had enabled it on one instance id and ssh'd
to a different one, a digit apart. Since the failure looks like an absence rather
than an error, we enabled tags on the whole fleet from a loop over
`describe-instances` output and confirmed every box answered before anyone touched
IAM.

The `DescribeTags` statement came out of the policy on Tuesday. `AppServerInstance`
now has S3 and the queue on it, and grepping the account's policies for `ec2:`
returns nothing attached to that role.

Before closing the ticket I ssh'd to one of the forty boxes with a `Runbook` tag and
ran the old query by hand:

```
$ aws ec2 describe-tags --filters "Name=key,Values=Runbook"

An error occurred (UnauthorizedOperation) when calling the DescribeTags operation:
You are not authorized to perform this operation.
```

Then `deploy-config --dry-run`, which printed `environment: prod` and exited 0. Both
outputs went in the ticket.
