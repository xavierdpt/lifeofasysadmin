# A tab, a space, and the word prod

*Theme: Hardening and least privilege*

The access review had been going well until we got to the instance role, which is
to say it had been going well because nobody had looked at the instance role yet.

Everything in that account runs on one launch template and one role,
`AppServerInstance`, and the policy attached to it had grown the way policies grow:
somebody needed something at some point, and the change that gave it to them was
reviewed by somebody who also needed something. Most of it was S3 and a queue. The
statement that stopped me was four lines long.

```json
{
  "Effect": "Allow",
  "Action": "ec2:DescribeTags",
  "Resource": "*"
}
```

`Resource: "*"` is not laziness there. `ec2:DescribeTags` does not take a resource
constraint — you cannot write a policy that says "this instance may read its own
tags and no others", because the API has no notion of the caller being one of the
things it describes. Grant it and you have granted every tag on every resource in
the account. Ours are not secret in the way a key is secret, but they carry the
owner's email address, the cost centre, the ticket the box was built for, and on
about forty instances a tag called `Runbook` whose value is an internal wiki URL.
Anything with a shell on any app server could read all of it.

So: delete the statement. Except that the statement was there for a reason, and the
reason was in the first ten lines of `/usr/local/bin/deploy-config`:

```bash
IID=$(ec2-metadata -i | cut -d' ' -f2)
ENV=$(aws ec2 describe-tags \
        --filters "Name=resource-id,Values=${IID}" "Name=key,Values=Environment" \
        --query 'Tags[0].Value' --output text)
```

An instance that wants to know which config to pull has to find out what it is, and
what it is has been written down exactly once, on the tag. The instance id it can
get locally. To turn the instance id into the tag it made a signed API call across
the internet to `ec2.eu-west-1.amazonaws.com`, with credentials, to ask Amazon a
question about itself. That round trip is the whole reason the permission existed.

It is also, apparently, a question Amazon got asked a lot, because at some point
they made it answerable locally. The clue was sitting in a man page on every one of
those instances, in the options list of `ec2-metadata(8)`, the metadata tool from
`amazon-ec2-utils`:

```
       -t/--tags
              Print EC2 resource tags if permitted in EC2 Instance Metadata
              Options.
```

Tags are served over the link-local metadata address, `169.254.169.254`, alongside
the instance id and the AMI id — no credentials, no API call, no permission. The
qualifier in that sentence is where the hardening lives: *if permitted in EC2
Instance Metadata Options*. It is off by default, and it is set per instance.

```
$ aws ec2 modify-instance-metadata-options \
    --instance-id i-0d4f1a6c9e2b7a350 --instance-metadata-tags enabled
```

Then, on the box:

```
$ ec2-metadata -t
instance-type: m6i.large
```

I read that three times. `-t` is `--instance-type`, and has been forever; the short
letter for tags is `-g`. The man page in 2.1.0 says `-t` and the script's `getopt`
string says `g`, and the script is the one that runs. (While I was in there I found
that `-h` is `--local-hostname`, so `ec2-metadata -h` cheerfully prints the hostname
instead of the help. `--help` works.)

```
$ ec2-metadata -g
tags:
	 Environment: prod
	 Owner: platform
	 Runbook: https://wiki.internal/rb/appserver
```

That is the same data the API call returned, fetched from a virtual address on the
instance's own network stack. Underneath, `ec2-metadata` is doing the IMDSv2
handshake for you — a `PUT` to `/latest/api/token` with a
`X-aws-ec2-metadata-token-ttl-seconds: 900` header, then that token on every
subsequent `GET` — which is the other half of why I was happy to keep using the tool
rather than hand-rolling `curl` in the deploy script. Fifteen minutes of token,
refreshed per invocation, and one place to get it wrong instead of nine.

The rewrite took one line, and then took a second line I did not expect:

```bash
ENV=$(ec2-metadata --quiet -g | awk '$1 == "Environment:" {print $2}')
```

`--quiet` is documented as "don't print metadata keys", and for `-i` or `-z` it does
exactly that. For `-g` it prints the header line `tags:` only when quiet is off, and
then prints every tag as `\t Environment: prod` regardless — the loop inside
`print_tags` never checks `$QUIET`, unlike every other printer in the file. Hence the
`awk`. With multiple tags you are parsing a list anyway; there is no way to ask
`ec2-metadata` for one tag by name.

The rollout order mattered, because the failure mode is quiet. On an instance where
metadata tags are still disabled, the path under `meta-data/tags/instance/` returns
nothing and `print_tags` prints:

```
tags:
not available
```

which is the same thing it prints for an instance that genuinely has no tags. Our
first attempt at a staging box came back `not available`, and for twenty minutes I
was convinced the feature had not shipped in that region. It had; I had enabled tags
on the wrong instance id, one digit off, and the instance I was typing on was still
at the default. So we enabled it on every instance in the fleet first — a loop over
`describe-instances` output — and confirmed it before touching the policy, rather
than in the other order.

The `DescribeTags` statement came out of the policy last Tuesday. What is left on
`AppServerInstance` is S3 and the queue, and grep for `ec2:` in the account's
policies now returns nothing on that role.

The last thing I did before closing the ticket was ssh to one of the forty boxes
with the `Runbook` tag, run `aws ec2 describe-tags --filters
"Name=key,Values=Runbook"`, and paste the response into the ticket:

```
An error occurred (UnauthorizedOperation) when calling the DescribeTags operation:
You are not authorized to perform this operation.
```

Then `deploy-config --dry-run`, which printed `environment: prod` and exited 0.
