# TICK=9997

*Theme: Configuration drift*

Dev Marsh phoned from the control room at Cwm Tawel treatment works at twenty to nine on Tuesday morning. He sounded more amused than annoyed.

"Your new computer's slow."

Rhiannon Price asked him what he meant by slow.

"Chlorine dosing pump two tripped this morning. I wrote it in the shift log off the wall clock: 08:43:00. The historian's got it at 08:41:08. I thought I'd fat-fingered it, but it's the same on the other alarms since the weekend. Nearly two minutes, and it's getting worse."

The historian was `hist01`, the machine that records every tag value and alarm the plant's PLCs produce. It sits on the control network, which has no route to the corporate LAN or to the internet. That has been deliberate for years and it's written into the site's security policy. The previous `hist01` had been a tower PC bought in 2013. Rhiannon had replaced it the Wednesday before, following the "rebuild from backup" page in the IT runbook: install Ubuntu 24.04 on the new hardware, restore the package selections from the old machine with `dpkg --set-selections` and `apt-get dselect-upgrade`, restore `/etc` from the nightly tarball minus a list of host-specific files, and restore the historian's data volume. The cutover went smoothly. The old tower went into the recycling cage.

She drove over, because the control network can only be reached from a console inside the building.

## The two clocks

```
$ timedatectl
               Local time: Tue 2026-09-15 08:50:18 BST
           Universal time: Tue 2026-09-15 07:50:18 UTC
                 RTC time: Tue 2026-09-15 07:52:10
                Time zone: Europe/London (BST, +0100)
System clock synchronized: no
              NTP service: active
          RTC in local TZ: no
```

The radio-controlled clock on the control-room wall showed 08:52 and some seconds. That agreed with the RTC line and disagreed with everything above it.

A PC has two clocks. The real-time clock, the RTC, is a small battery-backed chip that keeps counting while the machine is off. The system clock is the kernel's count, set from the RTC at boot and then advanced by the kernel for as long as the machine runs. Every timestamp the historian writes comes from the system clock. On this box the RTC was right and the system clock had lost 112 seconds since Wednesday's boot.

Rhiannon's first guess, a failing CMOS battery, didn't fit, because the battery-backed clock was the correct one. A time-zone or summer-time mistake would show up as a whole hour, and this was under two minutes. "NTP service: active" referred to `systemd-timesyncd`, which the installer had enabled. It had spent six days failing to reach `ntp.ubuntu.com` from a network with no way out. It had never synchronised, so it had never touched the clock, and "synchronized: no" confirmed that.

That meant something was running the system clock slow on purpose, or the new hardware was very bad. She checked what ran at boot:

```
$ systemctl list-unit-files | grep -i time
adjtimex.service                            enabled         enabled
systemd-time-wait-sync.service              disabled        enabled
systemd-timedated.service                   static          -
systemd-timesyncd.service                   enabled         enabled
...
```

```
$ systemctl cat adjtimex

Description=the kernel time variables setting
Documentation=man:adjtimex(8)
DefaultDependencies=no

```

```
$ ls -l --time-style=long-iso /etc/default/adjtimex
-rw-r--r-- 1 root root 213 2014-03-11 16:02 /etc/default/adjtimex
$ cat /etc/default/adjtimex

```

The file was dated March 2014 and had come back with the rest of `/etc`. The package had come back because it was in the old machine's selections list. Nobody reading that list during the rebuild had asked why a historian needed `adjtimex`, and Rhiannon hadn't either. Note the `ConditionPathExists` line: with the package installed and no config file, the unit would have done nothing. The restored file was what switched it on.

## What the numbers do

```
$ adjtimex --print
         mode: 0
       offset: 0
    frequency: 5583667
     maxerror: 16000000
     esterror: 16000000
       status: 64
time_constant: 2
    precision: 1
    tolerance: 32768000
         tick: 9997
     raw time:  1789458610s 402113us = 1789458610.402113
 return value = 5
```

Status 64 is the kernel's "clock unsynchronized" bit, and return value 5 means the same thing. What mattered were `tick` and `frequency`, the two lines the service had set at boot.

The kernel advances the system clock from a hardware counter. It converts counter cycles into nanoseconds using a rate measured at boot, and that rate is never perfectly right. Every oscillator runs a little fast or slow. Some motherboards get it wrong by a large margin, and a clock that is off by 100 parts per million loses or gains 8.64 seconds a day. To make that correctable, the kernel exposes the length of its second through the `adjtimex(2)` system call. `tick` is the number of microseconds the kernel counts per 1/100 of a second. It defaults to 10000, which adds up to exactly one second. In `kernel/time/ntp.c` the length of a second is literally computed as `tick_usec * NSEC_PER_USEC * USER_HZ`. On a modern tickless kernel no interrupt actually fires 100 times a second, but the knob keeps its old name and scale. `frequency` is a much finer adjustment on top of that, in units of 1/65536 ppm.

The system call exists mainly for NTP. `ntpd`, `chronyd` and `timesyncd` compare the machine against a time server and keep correcting the frequency. The man page says as much: for a machine on a network, "the best way is to regulate the system clock with ntpd(8)." The `adjtimex` program was written in 1995 for machines that can't do that. Its man page puts it plainly: "For a standalone or intermittently connected machine, where it's not possible to run ntpd, you may use adjtimex instead to correct the system clock for systematic drift." Without the program, the only fix on a box like that is to keep resetting the time by hand and live with a sawtooth of errors. With it, you measure how fast this particular machine's clock runs, tell the kernel once, and the clock stays close. You still need a reference to measure against, and on a machine with no network the handiest one is the RTC chip on the board.

Rhiannon did the arithmetic in the margin of Dev's shift log. A tick of 9997 is 3 microseconds short per 10000, which is -300 ppm. A frequency of 5583667 divided by 65536 is +85.2 ppm. Together that is -214.8 ppm, or 18.6 seconds a day slow. Over the six days since Wednesday's boot it came to about 112 seconds, matching `timedatectl`.

The value was a correction someone had once needed. The old tower's system clock must have run about 215 ppm fast, 18 seconds a day, and in 2014 someone had measured that and made the kernel slow it down by exactly the same amount. The new server's clock didn't have that fault, so the 2014 correction was now pulling a healthy clock 18 seconds a day slow.

The handover folder filled in who had done it. An email from Colin Beddoe, who had looked after the site's IT for twenty years before retiring, dated the same afternoon as the file:

> hist01 clock gaining about 18s a day vs the RTC, operators noticed alarm times drifting. No NTP on the control network so installed adjtimex and ran adjtimexconfig, it's steady now. Values are in /etc/default/adjtimex.

`adjtimexconfig` is a script that ships with the Debian package. It runs `adjtimex --adjust` against the RTC for about 70 seconds and writes the resulting `TICK` and `FREQ` into `/etc/default/adjtimex`. Colin had done the right thing for the old tower. What made it a problem was that the result had gone into `/etc`, the directory everyone treats as configuration to carry forward. It was really a calibration: a measurement of one specific oscillator, and wrong on any other hardware.

## Measuring this machine instead

`--compare` reads the RTC every ten seconds and reports how quickly the system clock is gaining or losing on it. Rhiannon ran it with the inherited settings still in place:

```
# adjtimex --compare=5
                                      --- current ---   -- suggested --
cmos time     system-cmos  error_ppm   tick      freq    tick      freq
1789458730    -111.702415              9997   5583667
1789458740    -111.704543     -212.8   9997   5583667
1789458750    -111.706673     -213.0   9997   5583667    9999   6435635
1789458760    -111.708802     -212.9   9997   5583667    9999   6429081
1789458770    -111.710931     -212.9   9997   5583667    9999   6429081
```

The `system-cmos` column is the 112 seconds, and it shrank by about two milliseconds every ten seconds. The measured error, -212.9 ppm, was 1.9 ppm less than the -214.8 ppm the settings were applying. That meant the new hardware ran 1.9 ppm fast on its own, about 0.16 seconds a day. The suggested values of tick 9999 and freq 6429081 work out to -100 + 98.1 = -1.9 ppm: stop slowing the clock by 213 ppm and nudge it down by 1.9. The program's formula prefers a positive frequency, which is why the suggestion looks odd. The man page lists equivalent pairs, and the more readable way to write the same correction is tick 10000 and frequency -1.9 × 65536 = -124518.

She set the kernel back to its defaults with `adjtimex --tick 10000 --frequency 0` and ran `--compare` again. The error settled at +1.9 ppm, with the suggestion unchanged. That was a small, ordinary crystal error. Had she left the machine at its defaults, the historian would have drifted about a minute a year.

That left the 112 seconds already lost. Correcting the rate doesn't correct time that has already slipped. Dev and the shift lead agreed to reboot the historian at the 14:00 shift change, since the PLCs buffer their events. At boot the kernel would set the system clock from the RTC, and the service would load whatever was in `/etc/default/adjtimex` by then. Rhiannon rewrote the file before the reboot:

```
#  /etc/default/adjtimex - configuration file for adjtimex(8)
#
#  CALIBRATION FOR THIS HARDWARE ONLY (hist01, Dell R260, serial 7QK...).
#  The control network has no time source, so this corrects the system
#  clock's rate against the RTC. Measured 2026-09-15 with
#  `adjtimex --compare`: system clock +1.9 ppm fast vs RTC at defaults.
#  Replacing the machine? Delete this file, or re-measure with
#  adjtimexconfig. Do NOT restore it from a backup of another box.
#  Previous values (TICK=9997 FREQ=5583667) belonged to the 2013 tower.
#
TICK=10000
FREQ=-124518
```

After the reboot, `adjtimex --print` showed `tick: 10000` and `frequency: -124518`, and `timedatectl` showed the local time and the RTC agreeing to the second. At 14:20 Dev read a pump start off the wall clock, and it matched the alarm list.

## The RTC is a reference too

The RTC isn't perfect either. It is a cheap 32 kHz crystal and drifts with temperature, so calibrating the system clock against it only moves the question down a level. `adjtimex` has an answer for that as well. `--watch` asks you to press Enter at a moment when you know the time from some better source, then asks what that time was:

```
# adjtimex --watch
Please press <enter> when you know the time of day:
  system time then was Thu Sep 17 06:00:00 2026 BST
What time was that according to your reference (BST)?
(hh:mm:ss, or `r' to retry, or `q' to quit): 06:00:00
```

Each answer goes into `/var/log/clocks.log` along with the system and RTC times at that moment. Once there are enough entries, `adjtimex --review` estimates the error of both clocks against the reference. Rhiannon asked the shift leads to run it at each 06:00 handover for a month, against the radio clock on the wall. That clock gets its time from the MSF transmitter at Anthorn and is the most accurate thing in the building. After a month, `--review` would show whether the RTC needed its own correction.

The runbook page gained a line in the list of files never to restore across hardware, next to the SSH host keys and `/etc/machine-id`:

```
/etc/default/adjtimex    per-machine clock calibration, see file header
```

She also added a paragraph to the capital request for a GPS time server on the control network, which had been deferred three budget rounds running. It pointed out that the plant's alarm timestamps currently depend on a correction someone measured by hand, and that one has already been restored onto the wrong machine. With a real time source, `timesyncd` would keep the clock's frequency corrected all the time, and `adjtimex` could come off the machine.
