# Exit 137 at Twenty Minutes

*Theme: The one-character bug*

The request came in on a Tuesday afternoon and it was not, by any standard, a
difficult one. `bench03` is the shared compute box in the corner of the second
floor — twelve cores, no scheduler, whoever gets there first — and the
photogrammetry group had started running `meshsolve` on it. `meshsolve` is
single-threaded, runs for hours, and cheerfully takes whatever core it lands on.
Nobody minded that. What they minded was that the interactive work on the same
box had started to feel like typing through syrup.

Priya had inherited `bench03` along with the rest of the second floor, and
`bench03` had been running the auto nice daemon since before she arrived. That
is what `and` is for: it wakes up every sixty seconds, walks every process on
the machine, adds up the CPU time each one has burned, and looks the process up
in `/etc/and.priorities` to decide what its nice level ought to be by now. Short
things are left alone. Long things sink. It is a policy engine for the one
question nobody wants to be paged about, which is who gets the core when two
people want it.

So she opened the file and did what she had done a dozen times before, which was
find the nearest existing line and copy it. The file that ships with the package
has exactly one line in it that isn't a row of asterisks in the command column,
and that line is the one about the web browser:

```
*	*	.*netscape.*	*       2	-9	-9
```

She yanked it, changed the command pattern, and set the three levels she wanted:
untouched for the first couple of minutes, held down after twenty, buried after
an hour.

```
*	*	.*meshsolve.*	*	2	9	15
```

Then `kill -HUP` on the daemon, because `and` reloads the config and the priority
database on HUP rather than making you restart it, and back to the ticket queue.
Syslog recorded the one line it always records at that point:

```
and[1184]: Re-reading configuration and priority database...
```

It was correct. That is worth saying plainly, because the thing that went wrong
was not that line. The thing that went wrong was the line she wrote two days
later, on the Thursday, when the other group asked for the same treatment for
their nightly `ingest` run and she copied her own `meshsolve` line instead of the
netscape one — copied it, edited the pattern, edited the middle number, and
pushed HUP.

## What the wrapper saw

Friday morning there was a ticket. The nightly `ingest` had not finished. It had
not failed either, in the sense of writing an error; the wrapper script that runs
it had logged what wrappers log:

```
ingest exited with status 137
```

The photogrammetry group had filed a near-identical ticket an hour earlier for a
`meshsolve` run that had gone the same way. Both jobs had been running for a
little over twenty minutes.

Priya knows what 137 is the way everyone eventually knows what 137 is: 128 plus
9, a shell reporting a process killed by signal 9. So the first theory was the
OOM killer, which is where everybody's first theory goes, and `dmesg` had nothing
in it at all. No out-of-memory report, no segfault, no oops. `bench03` had 40 GB
free.

The second theory was that somebody was reaping jobs by hand, and that one lasted
until she checked the interval. Twenty minutes of CPU time. Both jobs. The
`lv2time` in `/etc/and.conf` is the stock 1200 seconds.

## The dry run

`and` has a test mode, and the reason to reach for it here is that it answers
the question directly rather than by inference. With `-t` the daemon does
everything it normally does — reads the config, walks the process table, works
out the verdict for every process — and then declines to carry any of it out,
logging what it would have done instead. `-s` sends that to stdout instead of the
`./debug.and` file it otherwise writes, and each `-v` raises the verbosity by one.

```
# and -t -s -vv -d /etc/and.priorities
```

Two `-v` is the level at which `and` dumps the priority database it just parsed,
as a table, before it starts looking at processes. Not the text of the file — the
table it built out of the file:

```
UID:   GID:   Command               Parent:                             NLs:
   -1     -1  *                     *                    (parent)        4, 8,12
   -1     -1  .*meshsolve.*         *                    (parent)        2, 9,15
   -1     -1  .*ingest.*            *                    (parent)        2,-9,15
```

Every wildcard in that file comes out as `-1`, which is why the eye slides over
a minus sign in the last column. The pattern she had copied from was the one she
wrote on Tuesday. The number she had failed to copy from it was the middle one.

The nice level column in `and.priorities` is not only a nice level column.
`and.priorities(5)` puts it in one sentence: positive numbers and zero are nice
levels, negative numbers are signals to be sent to the command. A level of 19
will almost stop a job; `-9` will actually kill it, like `kill -9`. Internally
it is the same branch either way — if the number the lookup returns is above
zero it goes to `setpriority`, and if it is below zero it goes to `kill` with the
sign flipped off.

The column is overloaded on purpose, and `and(8)` says what for: *a certain web
browser who shall remain unnamed tends to go berserk once in a while*, and for a
job that has stopped making progress, renicing is not a remedy. Nice 19 still
holds the memory, still holds the licence token, still holds the scratch
directory open. Before that number could go negative, killing a runaway meant a
second tool — a cron job with `ps`, an `awk` field or two, a `kill` and a
carefully-worded comment explaining why the `ps` output was being parsed. Putting
the signal in the same column as the nice level means one file describes the
whole policy: how far down a job sinks, and the point at which it stops sinking
and goes away.

The cost of that convenience is what a minus sign does to a line of config that
otherwise parses perfectly. `and` reads the three levels with a plain `%i` and
does not range-check them, because there is no range to check against: `-9` is as
legal as `9`. The file loaded without a complaint. The daemon logged its reload
line and got on with it.

And it had not said a word since, because in normal operating mode the `kill`
message is written at verbosity one, and the verbosity starts at zero. The
daemon had killed two jobs and told syslog nothing. Priya put `DAEMON_OPTS="-v"`
in `/etc/default/and` before she touched anything else.

Then she fixed the line, and while she was in there she added one below it on
purpose, because the group that runs `ingest` had mentioned that its exporter
stage sometimes spins forever on a malformed tile and has to be found and killed
by hand on Monday:

```
# nice levels are levels; negative numbers are signals. -15 is SIGTERM.
*	*	.*ingest.*	*	2	9	15
*	*	.*tile-export.*	*	0	15	-15
```

`kill -HUP 1184`, and then the same dry run again to read the table back:

```
   -1     -1  .*ingest.*            *                    (parent)        2, 9,15
   -1     -1  .*tile-export.*       *                    (parent)        0,15,-15
```

The nightly run went through that night and finished at 04:12. She closed both
tickets with the same three sentences, and pinned the table above her desk with
the middle column circled.
